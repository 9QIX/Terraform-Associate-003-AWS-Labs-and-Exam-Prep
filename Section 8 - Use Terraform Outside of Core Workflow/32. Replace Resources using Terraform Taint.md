# Terraform Taint and Replace

## Overview

This lab demonstrates how to force Terraform to recreate resources without modifying configuration files. It covers the legacy `terraform taint` command and the modern `-replace` option, along with automatic tainting behavior when provisioners fail.

---

## Concepts

### Resource Tainting

**Tainting** marks a resource in Terraform state as requiring recreation during the next apply operation, even when no configuration changes exist. This is useful when:

- A server needs to rerun its bootstrap process
- A resource is in a semi-configured or unknown state
- Manual intervention requires a clean rebuild

### Automatic Tainting

Terraform automatically taints resources when:

- A **creation-time provisioner** fails during resource creation
- Terraform cannot verify the resource was properly configured
- An error occurs that leaves the resource in an indeterminate state

### Deprecation Notice

As of **Terraform v0.15.2**, the `terraform taint` command is deprecated. The recommended approach is using `terraform apply -replace=<resource_address>`.

---

## Terraform Workflow

### Legacy Workflow (Deprecated)

1. Identify the resource address using `terraform state list`
2. Mark the resource as tainted: `terraform taint <resource_address>`
3. Run `terraform plan` to verify the replacement
4. Execute `terraform apply` to destroy and recreate the resource

### Modern Workflow (Recommended)

1. Identify the resource address using `terraform state list`
2. Execute replacement directly: `terraform apply -replace="<resource_address>"`
3. Confirm the action when prompted

```hcl
# Define an AWS EC2 instance resource named "web_server"
resource "aws_instance" "web_server" {
  # Use Ubuntu AMI from data source
  ami                         = data.aws_ami.ubuntu.id
  # Set instance size to t3.micro (free tier eligible)
  instance_type               = "t3.micro"
  # Place instance in the first public subnet
  subnet_id                   = aws_subnet.public_subnets["public_subnet_1"].id
  # Attach three security groups for ping, SSH, and web traffic
  security_groups             = [
    aws_security_group.vpc-ping.id,
    aws_security_group.ingress-ssh.id,
    aws_security_group.vpc-web.id
  ]
  # Assign a public IP address for internet access
  associate_public_ip_address = true
  # Use the generated SSH key pair for authentication
  key_name                    = aws_key_pair.generated.key_name

  # Define SSH connection parameters for provisioners
  connection {
    user        = "ubuntu"
    private_key = tls_private_key.generated.private_key_pem
    host        = self.public_ip
  }

  # Local provisioner: set correct permissions on private key file
  provisioner "local-exec" {
    command = "chmod 600 ${local_file.private_key_pem.filename}"
  }

  # Remote provisioner: install web application on the instance
  provisioner "remote-exec" {
    inline = [
      "sudo rm -rf /tmp",
      "sudo git clone https://github.com/hashicorp/demo-terraform-101 /tmp",
      "sudo sh /tmp/assets/setup-web.sh",
    ]
  }

  # Apply resource tags
  tags = {
    Name = "Web EC2 Server"
  }

  # Prevent Terraform from detecting security group changes as drift
  lifecycle {
    ignore_changes = [security_groups]
  }
}
```

#### Code Walkthrough

**Purpose**: Creates an Ubuntu EC2 instance in a public subnet with automated web application deployment.

**Key Components**:

- **AMI Selection**: References a data source for the latest Ubuntu image
- **Network Configuration**: Places the instance in a public subnet with internet access via public IP
- **Security**: Applies three security groups controlling ICMP, SSH, and HTTP/HTTPS traffic
- **SSH Access**: Uses a dynamically generated key pair for authentication
- **Provisioners**:
  - `local-exec`: Secures the private key file on the local machine
  - `remote-exec`: Clones a demo repository and executes a setup script to install a web service

**Dependencies**:

- `data.aws_ami.ubuntu` — Ubuntu AMI data source
- `aws_subnet.public_subnets["public_subnet_1"]` — Public subnet resource
- `aws_security_group.*` — Security group resources
- `aws_key_pair.generated` — SSH key pair resource
- `tls_private_key.generated` — TLS private key resource
- `local_file.private_key_pem` — Local file containing the private key

**Assumptions**:

- The VPC, subnets, and security groups already exist
- The instance has internet access for cloning the GitHub repository
- The setup script (`setup-web.sh`) is idempotent and handles dependencies

## Task 1: Manual Tainting (Deprecated Method)

### Step 1: Identify the Resource

```bash
terraform state list
```

Locate the resource address (e.g., `aws_instance.web_server`).

### Step 2: Taint the Resource

```bash
terraform taint aws_instance.web_server
```

**Output**:

```
Resource instance aws_instance.web_server has been marked as tainted.
```

### Step 3: Verify the Plan

```bash
terraform plan
```

**Output**:

```
# aws_instance.web_server is tainted, so must be replaced
-/+ resource "aws_instance" "web_server" {
    ...
}

Plan: 1 to add, 0 to change, 1 to destroy.
```

### Step 4: Apply the Changes

```bash
terraform apply
```

Terraform will:

1. Destroy the existing instance
2. Create a new instance with identical configuration
3. Re-run all provisioners

## Task 2: Automatic Tainting on Provisioner Failure

### Simulating a Provisioner Failure

Modify the `remote-exec` provisioner to include a failing command:

```hcl
provisioner "remote-exec" {
  inline = [
    "exit 2",  # Intentional failure
    "git clone https://github.com/hashicorp/demo-terraform-101",
    "cp -a demo-terraform-101/. /tmp/",
    "sudo sh /tmp/assets/setup-web.sh",
  ]
}
```

#### Line-by-line Comments

```hcl
provisioner "remote-exec" {
```

## Pitfalls & Best Practices

### Pitfalls

| Issue                                | Description                                                            | Impact                                                                |
| ------------------------------------ | ---------------------------------------------------------------------- | --------------------------------------------------------------------- |
| **Using deprecated `taint` command** | `terraform taint` is deprecated since v0.15.2                          | May be removed in future versions                                     |
| **Forgetting to untaint**            | Tainted resources remain marked until explicitly untainted or replaced | Unintended resource recreation on next apply                          |
| **Provisioner failures**             | Failed provisioners automatically taint resources                      | Resource will be replaced on next apply, potentially causing downtime |
| **State file corruption**            | Manual state file edits can cause tainting issues                      | State inconsistencies and apply failures                              |
| **Ignoring taint warnings**          | Not reviewing plan output before apply                                 | Unexpected resource destruction                                       |

### Best Practices

1. **Use `-replace` instead of `taint`**

   - More explicit and integrated into the apply workflow
   - Avoids the two-step process of taint + apply

2. **Review plans carefully**

   - Always run `terraform plan` before `apply`
   - Look for `(tainted)` markers or replacement indicators

3. **Handle provisioner failures gracefully**

   - Use `on_failure = continue` for non-critical provisioners
   - Implement idempotent provisioner scripts
   - Consider using configuration management tools (Ansible, Chef) instead

4. **Verify resource state after failures**

   - Use `terraform state show` to check taint status
   - Untaint resources if the failure was transient

5. **Avoid manual state manipulation**

   - Use Terraform commands (`taint`, `untaint`, `state rm`) instead of editing state files
   - Always backup state before manual operations

6. **Test provisioners independently**
   - Validate scripts outside Terraform before integration
   - Use `null_resource` for testing provisioner logic

## Key Terms & Definitions

| Term                          | Definition                                                                                      |
| ----------------------------- | ----------------------------------------------------------------------------------------------- |
| **Taint**                     | A marker in Terraform state indicating a resource must be recreated on the next apply           |
| **Provisioner**               | A Terraform construct that executes scripts or commands during resource creation or destruction |
| **Creation-time provisioner** | A provisioner that runs only when a resource is first created                                   |
| **Resource address**          | The unique identifier for a resource in Terraform (e.g., `aws_instance.web_server`)             |
| **State file**                | A JSON file tracking all resources managed by Terraform and their current attributes            |
| **local-exec**                | A provisioner that executes commands on the machine running Terraform                           |
| **remote-exec**               | A provisioner that executes commands on a remote resource via SSH or WinRM                      |
| **Idempotent**                | A script or operation that produces the same result regardless of how many times it's executed  |
| **Replace**                   | The action of destroying and recreating a resource with the same configuration                  |

## Common Exam Traps

### Terraform Associate 003 Exam Considerations

1. **Taint Command Deprecation**

   - **Trap**: Exam may test knowledge of both old and new methods
   - **Key Point**: Know that `taint` is deprecated but understand its behavior
   - **Correct Answer**: Use `terraform apply -replace` in modern Terraform

2. **Automatic Tainting Behavior**

   - **Trap**: Assuming all provisioner failures cause tainting
   - **Key Point**: Only creation-time provisioners cause automatic tainting when they fail
   - **Correct Answer**: Destroy-time provisioner failures do not taint resources

3. **Taint vs. Configuration Changes**

   - **Trap**: Confusing tainting with configuration drift
   - **Key Point**: Tainting forces replacement without configuration changes
   - **Correct Answer**: Taint is a state-level marker, not a configuration change

4. **Untaint Behavior**

   - **Trap**: Thinking untaint repairs a broken resource
   - **Key Point**: Untaint only removes the marker; it doesn't fix the resource
   - **Correct Answer**: Untaint prevents replacement but doesn't modify the resource

5. **Replace Option Scope**

   - **Trap**: Believing `-replace` modifies the resource in place
   - **Key Point**: `-replace` always destroys then recreates
   - **Correct Answer**: It's a full replacement, not an update

6. **State File Modification**

   - **Trap**: Manually editing state files to remove taint markers
   - **Key Point**: State files should only be modified via Terraform commands
   - **Correct Answer**: Use `terraform untaint` or `terraform state` commands

7. **Provisioner Failure Recovery**
   - **Trap**: Assuming a failed apply can be retried without consequences
   - **Key Point**: Failed provisioners leave resources tainted
   - **Correct Answer**: Must untaint or fix the provisioner before retrying

## Comparison: Taint vs. Replace

| Aspect                 | `terraform taint` (Deprecated)     | `terraform apply -replace` (Recommended) |
| ---------------------- | ---------------------------------- | ---------------------------------------- |
| **Terraform Version**  | < 0.15.2                           | ≥ 0.15.2                                 |
| **Workflow**           | Two-step: taint, then apply        | Single-step: apply with flag             |
| **Explicitness**       | Implicit (requires checking state) | Explicit (specified in command)          |
| **State Modification** | Modifies state immediately         | No state change until apply              |
| **Reversibility**      | Requires `untaint` before apply    | Can cancel before confirming apply       |
| **Best Practice**      | Avoid in new code                  | Use for all replacement scenarios        |
| **Exam Relevance**     | Know for historical context        | Primary method tested                    |

## Updated Information (as of 2024)

### Deprecation of `terraform taint`

- **Change**: The `terraform taint` and `terraform untaint` commands were deprecated in Terraform v0.15.2 (April 2021)
- **Current Recommendation**: Use `terraform apply -replace="<resource_address>"` for all resource replacement scenarios
- **Rationale**: The `-replace` option provides a more explicit, safer workflow by combining the marking and replacement into a single operation
- **Backward Compatibility**: The `taint` command still functions in current versions but may be removed in future major releases

### Provisioner Best Practices

- **Current Guidance**: HashiCorp recommends minimizing provisioner usage in favor of:
  - **User data / cloud-init** for instance bootstrapping
  - **Configuration management tools** (Ansible, Chef, Puppet) for complex setups
  - **Custom AMIs / images** with pre-installed software
- **Reason**: Provisioners break Terraform's declarative model and can cause state inconsistencies

### Remote-exec Provisioner Considerations

- **Security**: SSH connections should use bastion hosts or AWS Systems Manager Session Manager instead of direct public IP access
- **Idempotency**: Scripts should handle multiple executions gracefully
- **Error Handling**: Consider using `on_failure = continue` for non-critical provisioners to prevent automatic tainting

### State Management

- **Remote State**: Always use remote state backends (S3, Terraform Cloud) for team environments
- **State Locking**: Enable state locking to prevent concurrent modifications
- **Sensitive Data**: Use `terraform state pull` with caution as it may expose sensitive values
