# Terraform Import

## Overview

This lab demonstrates how to bring existing infrastructure—created manually or by other tools—under Terraform management using the `terraform import` command. The process involves creating an empty resource block in configuration, importing the resource into state, and then populating the required attributes.

---

## Concepts

### What is Terraform Import?

**Terraform Import** is a command that allows you to add existing infrastructure resources to Terraform state and configuration. This is essential when:

- Resources were created manually through cloud provider consoles
- Infrastructure was provisioned by other automation tools or scripts
- You're migrating from another IaC (Infrastructure as Code) tool to Terraform
- You need to adopt existing infrastructure into a Terraform-managed workflow

### Import Workflow

The import process follows three key steps:

1. **Prepare Configuration**: Create an empty resource block with the correct resource type and name
2. **Import to State**: Use `terraform import` to add the resource to Terraform state
3. **Populate Attributes**: Query state and add required attributes to the configuration

### Important Limitations

- Import only adds resources to **state**, not configuration
- You must manually write the configuration after import
- Import does not create relationships between resources automatically
- Each resource type has a unique identifier format for import

---

## Terraform Workflow

### Step-by-Step Import Process

1. **Identify the Resource**

   - Locate the existing resource in your cloud provider
   - Note its unique identifier (instance ID, bucket name, etc.)

2. **Create Empty Resource Block**

   - Add a resource block to your configuration with the correct type and name
   - Leave the block empty initially

3. **Execute Import Command**

   - Run `terraform import <resource_address> <unique_identifier>`
   - Verify successful import

4. **Query State for Attributes**

   - Use `terraform state show <resource_address>` to view imported attributes
   - Identify required attributes from the output

5. **Populate Configuration**

   - Add required attributes to your resource block
   - Run `terraform plan` to verify configuration matches state

6. **Apply Changes (Optional)**
   - Use `terraform apply` to bring the resource fully under Terraform management
   - Apply any additional configuration changes (tags, settings, etc.)

## Providers & Resources

### Provider Configuration

Ensure your provider is configured for the region where the resource exists:

```hcl
provider "aws" {
  region = "us-west-2"
}
```

#### Line-by-line Comments

```hcl
# Configure the AWS provider
provider "aws" {
  # Specify the AWS region where resources will be managed
  region = "us-west-2"
}
```

#### Code Walkthrough

**Purpose**: Establishes connection to AWS and specifies the region for resource operations.

**Key Points**:

- The region must match where your existing resource was created
- This configuration should already exist from previous labs
- Multiple provider blocks can target different regions if needed

**Dependencies**: None (provider configuration is the foundation)

### Empty Resource Block for Import

```hcl
resource "aws_instance" "aws_linux" {}
```

#### Line-by-line Comments

```hcl
# Create an empty EC2 instance resource block as the import destination
resource "aws_instance" "aws_linux" {}
```

#### Code Walkthrough

**Purpose**: Provides a destination in configuration for the imported resource.

**Key Points**:

- The resource type (`aws_instance`) must match the actual resource being imported
- The resource name (`aws_linux`) is arbitrary but should be descriptive
- The block is intentionally empty before import
- This serves as the "address" for the import command

**Assumptions**:

- You know the correct resource type for what you're importing
- The resource name doesn't conflict with existing resources in your configuration

---

### Completed Resource Block After Import

```hcl
resource "aws_instance" "aws_linux" {
  ami           = "ami-013a129d325529d4d"
  instance_type = "t3.micro"
}
```

#### Line-by-line Comments

```hcl
# EC2 instance resource now populated with required attributes
resource "aws_instance" "aws_linux" {
  # Amazon Machine Image ID for Amazon Linux 2
  ami           = "ami-013a129d325529d4d"
  # Instance size (free tier eligible)
  instance_type = "t3.micro"
}
```

#### Code Walkthrough

**Purpose**: Defines the minimum required configuration for the imported EC2 instance.

**Key Points**:

- `ami` and `instance_type` are required attributes for `aws_instance`
- Values are obtained from `terraform state show` output after import
- Additional optional attributes can be added (subnet, security groups, tags, etc.)
- Configuration must match the actual resource to avoid unwanted changes

**Dependencies**:

- The resource must already exist in Terraform state (via import)
- AMI must be valid in the specified region

**Assumptions**:

- The instance was created with these specific values
- No other required attributes are needed for your use case

## Import Command Syntax

### Basic Import Command Structure

```bash
terraform import <resource_address> <unique_identifier>
```

**Components**:

- `terraform` — The Terraform CLI binary
- `import` — The import subcommand
- `<resource_address>` — The resource location in your configuration (format: `resource_type.resource_name`)
- `<unique_identifier>` — The cloud provider's unique ID for the resource

### EC2 Instance Import Example

```bash
terraform import aws_instance.aws_linux i-0bfff5070c5fb87b6
```

#### Command Breakdown

```bash
# Import an existing EC2 instance into Terraform state
terraform import aws_instance.aws_linux i-0bfff5070c5fb87b6
```

**Explanation**:

- `aws_instance.aws_linux` — The resource address in your `main.tf` file
- `i-0bfff5070c5fb87b6` — The EC2 instance ID from AWS console

**Expected Output**:

```
aws_instance.aws_linux: Importing from ID "i-0bfff5070c5fb87b6"...
aws_instance.aws_linux: Import prepared!
  Prepared aws_instance for import
aws_instance.aws_linux: Refreshing state... [id=i-0bfff5070c5fb87b6]

Import successful!

The resources that were imported are shown above. These resources are now in
your Terraform state and will henceforth be managed by Terraform.
```

Different AWS resources require different identifier formats for import. Always consult the provider documentation.

| **Security Group** | Security group ID      | `terraform import aws_security_group.example sg-0123456789abcdef0` |

## Post-Import Workflow

### Handling Missing Required Attributes

After import, running `terraform plan` may produce errors:

```bash
terraform plan
```

**Error Example**:

```
Error: Missing required argument

  on main.tf line 5, in resource "aws_instance" "aws_linux":
   5: resource "aws_instance" "aws_linux" {

The argument "ami" is required, but no definition was found.

Error: Missing required argument

  on main.tf line 5, in resource "aws_instance" "aws_linux":
   5: resource "aws_instance" "aws_linux" {

The argument "instance_type" is required, but no definition was found.
```

**Solution**: Use `terraform state show` to find the required values and add them to your configuration.

### Applying Default Tags

If you have default tags configured in your provider, Terraform will detect them as changes:

```bash
terraform plan
```

**Output**:

```
# aws_instance.aws_linux will be updated in-place
~ resource "aws_instance" "aws_linux" {
      id                                   = "i-0bfff5070c5fb87b6"
      tags                                 = {}
    ~ tags_all                             = {
        + "Owner"       = "Acme"
        + "Provisioned" = "Terraform"
      }
      # (27 unchanged attributes hidden)
}

Plan: 0 to add, 1 to change, 0 to destroy.
```

Apply the changes to add the tags:

```bash
terraform apply
```

This confirms Terraform now has full management control over the imported resource.

### Removing Imported Resources

To remove an imported resource from Terraform management:

1. **Delete from Configuration**: Remove the resource block from your `.tf` files
2. **Run Plan**: `terraform plan` will show the resource marked for destruction
3. **Apply Changes**: `terraform apply` will destroy the resource in the cloud

**Warning**: Removing a resource from configuration will destroy it in your cloud environment. Use `terraform state rm` if you want to remove it from state without destroying it.

## Pitfalls & Best Practices

### Pitfalls

| Issue                                 | Description                                                      | Impact                                              |
| ------------------------------------- | ---------------------------------------------------------------- | --------------------------------------------------- |
| **Incomplete Configuration**          | Only importing to state without adding required attributes       | `terraform plan` fails with missing argument errors |
| **Wrong Identifier Format**           | Using incorrect ID format for the resource type                  | Import fails with "resource not found" error        |
| **Region Mismatch**                   | Provider region doesn't match resource location                  | Import fails or imports wrong resource              |
| **Missing Dependencies**              | Not importing related resources (security groups, subnets, etc.) | Configuration is incomplete and may cause drift     |
| **Overwriting State**                 | Importing to an address that already exists                      | Existing state is overwritten, causing data loss    |
| **Removing Without State Management** | Deleting resource from config without understanding consequences | Unintended resource destruction                     |

### Best Practices

1. **Always Backup State Before Import**

   ```bash
   terraform state pull > backup.tfstate
   ```

2. **Use Descriptive Resource Names**

   - Choose names that clearly identify the resource's purpose
   - Follow your team's naming conventions

3. **Import Related Resources Together**

   - Import VPCs, subnets, security groups, and instances as a set
   - Maintain resource relationships in configuration

4. **Verify Import Success**

   ```bash
   terraform state list
   terraform state show <resource_address>
   ```

5. **Start with Minimum Required Attributes**

   - Add only required attributes initially
   - Run `terraform plan` to identify what's needed
   - Gradually add optional attributes as needed

6. **Document Import Process**

   - Keep notes on which resources were imported and when
   - Document the original resource IDs for reference

7. **Use Terraform Format**

   ```bash
   terraform fmt
   ```

   - Clean up formatting after adding attributes

8. **Test in Non-Production First**

   - Practice import workflow in development environments
   - Understand the impact before importing production resources

9. **Check Provider Documentation**

   - Always verify the correct import identifier format
   - Review resource-specific import requirements

10. **Plan Before Apply**
    - After import, always run `terraform plan` before `terraform apply`
    - Verify that no unexpected changes will occur

## Key Terms & Definitions

| Term                    | Definition                                                                                              |
| ----------------------- | ------------------------------------------------------------------------------------------------------- |
| **Import**              | The process of adding existing infrastructure to Terraform state and configuration                      |
| **Resource Address**    | The unique identifier for a resource in Terraform configuration (format: `resource_type.resource_name`) |
| **Unique Identifier**   | The cloud provider's ID for a resource (e.g., instance ID, bucket name)                                 |
| **State**               | Terraform's record of managed infrastructure, stored in `terraform.tfstate`                             |
| **Required Attributes** | Configuration parameters that must be specified for a resource to be valid                              |
| **Optional Attributes** | Configuration parameters that have default values and don't need to be explicitly set                   |
| **Resource Type**       | The kind of infrastructure resource (e.g., `aws_instance`, `aws_s3_bucket`)                             |
| **Resource Name**       | The local name you assign to a resource in your configuration                                           |
| **Provider**            | A plugin that enables Terraform to interact with a cloud platform or service                            |
| **Configuration Drift** | Differences between Terraform configuration and actual infrastructure state                             |

## Common Exam Traps

### Terraform Associate 003 Exam Considerations

1. **Import Only Affects State, Not Configuration**

   - **Trap**: Believing import automatically generates configuration code
   - **Key Point**: Import adds resources to state; you must manually write configuration
   - **Correct Answer**: After import, you must populate the resource block with required attributes

2. **Import Identifier Varies by Resource**

   - **Trap**: Assuming all resources use the same identifier format
   - **Key Point**: Each resource type has a specific identifier (instance ID, name, ARN, etc.)
   - **Correct Answer**: Always check provider documentation for the correct import syntax

3. **Import Doesn't Create Relationships**

   - **Trap**: Expecting Terraform to automatically discover and import related resources
   - **Key Point**: Import is per-resource; dependencies must be imported separately
   - **Correct Answer**: You must import each related resource individually and define relationships in configuration

4. **Required vs. Optional Attributes**

   - **Trap**: Thinking all attributes from `terraform state show` must be in configuration
   - **Key Point**: Only required attributes must be specified; optional ones have defaults
   - **Correct Answer**: Start with required attributes; add optional ones only if you need non-default values

5. **Import Command Syntax**

   - **Trap**: Reversing the order of resource address and identifier
   - **Key Point**: Syntax is always `terraform import <address> <id>`
   - **Correct Answer**: Resource address comes first, then the unique identifier

6. **State vs. Configuration**

   - **Trap**: Confusing state file with configuration files
   - **Key Point**: State tracks actual infrastructure; configuration defines desired state
   - **Correct Answer**: Import adds to state; you must update configuration to match

7. **Removing Imported Resources**

   - **Trap**: Thinking removing from configuration only removes from Terraform management
   - **Key Point**: Removing from configuration causes Terraform to destroy the resource
   - **Correct Answer**: Use `terraform state rm` to remove from state without destroying

8. **Import and Terraform Plan**
   - **Trap**: Expecting `terraform plan` to work immediately after import
   - **Key Point**: Plan will fail until required attributes are added to configuration
   - **Correct Answer**: Query state, add required attributes, then plan will succeed

## Updated Information (as of 2025)

### Import Block (Terraform 1.5+)

- **Change**: Terraform 1.5 introduced the `import` block as a declarative alternative to the `terraform import` command
- **Current Recommendation**: Use `import` blocks for new imports when using Terraform 1.5 or later
- **Syntax**:
  ```hcl
  import {
    to = aws_instance.aws_linux
    id = "i-0bfff5070c5fb87b6"
  }
  ```
- **Benefits**: Import configuration is version-controlled, repeatable, and can be reviewed in pull requests
- **Backward Compatibility**: The `terraform import` CLI command still works and is not deprecated

### Configuration Generation (Terraform 1.5+)

- **Change**: Terraform 1.5+ can automatically generate configuration for imported resources
- **Command**: `terraform plan -generate-config-out=generated.tf`
- **Benefit**: Eliminates manual attribute population from `terraform state show` output
- **Limitation**: Generated configuration may include all attributes (not just required ones), requiring cleanup

### Enhanced Import Workflow (Modern Approach)

1. Add `import` block to configuration
2. Run `terraform plan -generate-config-out=imported.tf`
3. Review and refine generated configuration
4. Run `terraform apply` to complete import

### Provider-Specific Import Improvements

- **AWS Provider**: Many resources now support import with additional metadata
- **Documentation**: Import sections in provider docs are more comprehensive and include examples
- **Error Messages**: Improved error messages when import identifiers are incorrect

### State Management Best Practices

- **Remote State**: Always use remote state backends (S3, Terraform Cloud) for team environments
- **State Locking**: Essential for preventing concurrent import operations
- **Backup**: Use `terraform state pull > backup-$(date +%Y%m%d).tfstate` before imports
