# Understanding the Terraform Workflow

## Overview

The core Terraform workflow consists of three fundamental steps: Write, Plan, and Apply. This workflow enables Infrastructure as Code (IaC) by allowing users to author configuration, preview changes, and provision reproducible infrastructure. The Terraform CLI provides commands that support this workflow across multiple operating systems.

## Concepts

### Workflow Fundamentals

- **Write**: Author infrastructure as code using HCL (HashiCorp Configuration Language)
- **Plan**: Preview changes before applying them to infrastructure
- **Apply**: Provision reproducible infrastructure based on configuration
- **Destroy**: Remove infrastructure managed by Terraform (optional cleanup step)

### Key Benefits

- Predictable infrastructure changes through planning
- Version-controlled infrastructure definitions
- Reproducible deployments across environments
- Safe infrastructure modifications with preview capability
- Automated resource lifecycle management

```hcl

  length = 16
```

**Line-by-line Comments:**

**Code Walkthrough:**
This simple configuration demonstrates the Write phase by defining a resource using HCL syntax. The random provider generates a string of specified length, providing a basic example of infrastructure as code.

### Initialization

```bash
terraform init
```

**Line-by-line Comments:**

```bash
# Initialize working directory and download providers
```

**Code Walkthrough:**
Initialization prepares the working directory by downloading required providers, setting up the backend, and creating the `.terraform` directory for managing cached plugins and workspace state.

### Plan Phase - Change Preview

```bash
terraform plan
terraform plan -out myplan
```

**Line-by-line Comments:**

```bash
# Preview changes without applying them
# Save plan to file for later execution
```

**Code Walkthrough:**
The plan command performs a "dry run" showing what changes Terraform will make. The `-out` flag saves the plan to a file, ensuring only reviewed changes are applied later.

### Apply Phase - Infrastructure Provisioning

```bash
terraform apply myplan
terraform apply
```

**Line-by-line Comments:**

```bash
# Apply previously saved plan file
# Apply changes with interactive confirmation
```

**Code Walkthrough:**
Apply executes the planned changes. Using a saved plan file ensures exact execution of reviewed changes. Without a plan file, Terraform shows changes and requests confirmation before proceeding.

### Configuration Updates

```hcl
resource "random_string" "random" {
  length = 10
}
```

**Line-by-line Comments:**

```hcl

# Change string length from 16 to 10
```

**Code Walkthrough:**
Modifying configuration demonstrates the iterative nature of the Terraform workflow. Changes trigger resource updates or replacements based on the resource's update behavior.

### Destroy Phase - Resource Cleanup

```bash
terraform plan -destroy
terraform destroy
```

**Line-by-line Comments:**

```bash
# Preview destruction plan
# Destroy all managed resources
```

**Code Walkthrough:**
The destroy command removes all resources managed by the current configuration. The `-destroy` flag with plan previews what will be destroyed before actual removal.

## State Management

### Workspace Initialization

- **`.terraform` Directory**: Hidden directory containing cached providers, modules, and workspace metadata
- **Backend Configuration**: Stores state file location and configuration
- **Provider Plugins**: Downloaded and cached during initialization
- **Workspace Tracking**: Records active workspace and backend settings

### Plan File Management

- **Plan Storage**: Binary files containing exact change specifications
- **Reproducible Execution**: Ensures applied changes match reviewed plans
- **Security**: Plan files may contain sensitive data and should be handled carefully

## Pitfalls & Best Practices

### Critical Considerations

- **Plan Review**: Always review plans before applying changes
- **State File Security**: Protect state files as they may contain sensitive information
- **Workspace Isolation**: Use separate workspaces for different environments
- **Version Control**: Store configuration files in version control systems

### Common Mistakes

- Applying changes without reviewing plans
- Not initializing workspace after configuration changes
- Ignoring plan output and warnings
- Running destroy without understanding impact
- Not backing up state files before major changes

### Best Practices

- Always run `terraform plan` before `terraform apply`
- Use plan files for production deployments
- Initialize workspace after adding new providers or modules
- Review destroy plans carefully before execution
- Implement proper state file backup and recovery procedures
- Use version control for all Terraform configurations

## Key Terms & Definitions

- **Write Phase**: Creating and authoring Terraform configuration files
- **Plan Phase**: Previewing changes before applying them to infrastructure
- **Apply Phase**: Executing planned changes to provision or modify infrastructure
- **Initialization**: Preparing working directory with providers and backend configuration
- **Plan File**: Binary file containing specific changes to be applied
- **Dry Run**: Previewing changes without making actual modifications

## Common Exam Traps

- **Initialization Requirement**: Must run `terraform init` before other commands
- **Plan vs Apply**: Plan only previews; apply actually makes changes
- **Plan File Usage**: Plan files ensure exact execution of reviewed changes
- **Destroy Behavior**: Destroys resources, not configuration files
- **Interactive Confirmation**: Apply and destroy require "yes" confirmation unless automated
- **Workspace State**: `.terraform` directory manages local workspace state
