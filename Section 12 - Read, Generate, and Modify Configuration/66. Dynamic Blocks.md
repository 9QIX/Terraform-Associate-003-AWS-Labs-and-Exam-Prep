# Dynamic Blocks

## Overview

A **dynamic block** generates repeatable nested blocks inside a `resource`, `data`, `provider`, or `provisioner` block by iterating over a collection — instead of copying the same nested block multiple times. This lab demonstrates building an AWS security group first with static repeated `ingress` blocks, then refactoring to a dynamic block driven by a `locals` list, and finally driving it from a typed `map(object(...))` variable.

---

## Concepts

- A dynamic block is not a top-level block — it only appears **inside** another block (resource, data, provider, provisioner).
- The label on the `dynamic` keyword (`dynamic "ingress"`) must match the name of the nested block being generated.
- Inside a dynamic block, the iterator object defaults to the same name as the dynamic block label (e.g., `ingress.value`). A custom iterator name can be set with `iterator = <name>`.
- Dynamic blocks produce identical state output to manually written nested blocks — the generated configuration is functionally equivalent.
- **Overuse of dynamic blocks reduces readability.** Only use them when the number of nested blocks is variable or driven by an input; write nested blocks literally when the count is fixed and small.

### Dynamic Block vs. Static Nested Blocks

| Aspect       | Static nested blocks                          | Dynamic block                               |
| ------------ | --------------------------------------------- | ------------------------------------------- |
| Use when     | Fixed, small number of blocks                 | Variable or data-driven number of blocks    |
| Readability  | High — explicit, easy to scan                 | Lower — requires understanding the iterator |
| Reusability  | Low — values are hardcoded                    | High — data-driven from locals or variables |
| State output | Identical                                     | Identical                                   |
| Supported in | `resource`, `data`, `provider`, `provisioner` | Same                                        |

## Task 1: Security Group with Static Nested Blocks

```hcl
resource "aws_security_group" "main" {
  name   = "core-sg"
  vpc_id = aws_vpc.vpc.id

  ingress {
    description = "Port 443"
    from_port   = 443
    to_port     = 443
    protocol    = "tcp"
    cidr_blocks = ["0.0.0.0/0"]
  }

  ingress {
    description = "Port 80"
    from_port   = 80
    to_port     = 80
    protocol    = "tcp"
    cidr_blocks = ["0.0.0.0/0"]
  }
}
```

```hcl
# Line-by-line Comments
resource "aws_security_group" "main" {
  name   = "core-sg"           # security group name visible in AWS
  vpc_id = aws_vpc.vpc.id      # associates the SG with the managed VPC

  ingress {                    # first static nested ingress block — allows HTTPS
    description = "Port 443"
    from_port   = 443
    to_port     = 443
    protocol    = "tcp"
    cidr_blocks = ["0.0.0.0/0"] # open to all IPv4 sources
  }

  ingress {                    # second static nested ingress block — allows HTTP
    description = "Port 80"
    from_port   = 80
    to_port     = 80
    protocol    = "tcp"
    cidr_blocks = ["0.0.0.0/0"]
  }
}
```

**Code Walkthrough:**

- Both `ingress` blocks are structurally identical except for the port and description values. This repetition is the problem dynamic blocks solve.
- Adding a third port (e.g., 8080) requires copying the entire block again.

```bash
terraform apply
```

## Task 2: Inspect State — Static Blocks

```bash
terraform state list
# aws_security_group.main

terraform state show aws_security_group.main
```

The state shows both ingress rules stored as elements of the `ingress` list:

```text
ingress = [
    { description = "Port 443", from_port = 443, to_port = 443, protocol = "tcp", ... },
    { description = "Port 80",  from_port = 80,  to_port = 80,  protocol = "tcp", ... },
]
```

**Key observation:** Terraform stores ingress rules as a list in state regardless of whether they were defined with static blocks or a dynamic block — the state representation is identical.

## Task 3: Refactor to a Dynamic Block (locals-driven)

```hcl
locals {
  ingress_rules = [
    {
      port        = 443
      description = "Port 443"
    },
    {
      port        = 80
      description = "Port 80"
    }
  ]
}

resource "aws_security_group" "main" {
  name   = "core-sg"
  vpc_id = aws_vpc.vpc.id

  dynamic "ingress" {
    for_each = local.ingress_rules

    content {
      description = ingress.value.description
      from_port   = ingress.value.port
      to_port     = ingress.value.port
      protocol    = "tcp"
      cidr_blocks = ["0.0.0.0/0"]
    }
  }
}
```

```hcl
# Line-by-line Comments
locals {
  ingress_rules = [          # a list of objects; each object defines one ingress rule
    { port = 443, description = "Port 443" },
    { port = 80,  description = "Port 80"  }
  ]
}

resource "aws_security_group" "main" {
  name   = "core-sg"
  vpc_id = aws_vpc.vpc.id

  dynamic "ingress" {        # generates one nested "ingress" block per element in for_each
    for_each = local.ingress_rules  # iterates over the list of objects

    content {                # defines the body of each generated ingress block
      description = ingress.value.description  # ingress = iterator name (matches the dynamic label)
      from_port   = ingress.value.port         # .value = the current list element (an object)
      to_port     = ingress.value.port
      protocol    = "tcp"
      cidr_blocks = ["0.0.0.0/0"]
    }
  }
}
```

**Code Walkthrough:**

- `dynamic "ingress"` — the label `ingress` must match the name of the nested block the resource supports.
- `for_each` — accepts a list or map. When iterating a list, `ingress.value` is the current element object; `ingress.key` is the zero-based index.
- `content { ... }` — the template for each generated block. Every attribute inside uses the iterator (`ingress.value.<attr>`) to pull per-element values.
- Removing the two static `ingress` blocks and replacing them with this single dynamic block produces the same infrastructure.

## Task 4: Verify State — Dynamic Block (locals)

```bash
terraform apply   # result: no changes (refactor only; infrastructure unchanged)
terraform state show aws_security_group.main
```

**Expected result:** The state output is identical to Task 2 — both ingress rules are present, unchanged. This confirms the dynamic block is functionally equivalent to the static blocks.

## Task 5: Dynamic Block Driven by a Typed Map Variable

Replace the `locals` list with a `map(object(...))` variable, which carries all per-rule attributes including `protocol` and `cidr_blocks` — making the security group fully configurable from the variable layer.

### Variable Declaration

```hcl
variable "web_ingress" {
  type = map(object({
    description = string
    port        = number
    protocol    = string
    cidr_blocks = list(string)
  }))
  default = {
    "80" = {
      description = "Port 80"
      port        = 80
      protocol    = "tcp"
      cidr_blocks = ["0.0.0.0/0"]
    }
    "443" = {
      description = "Port 443"
      port        = 443
      protocol    = "tcp"
      cidr_blocks = ["0.0.0.0/0"]
    }
  }
}
```

```hcl
# Line-by-line Comments
variable "web_ingress" {
  type = map(object({          # a map whose values are typed objects (enforces all four attributes)
    description = string       # human-readable rule description
    port        = number       # port number (used for both from_port and to_port)
    protocol    = string       # transport protocol (e.g., "tcp")
    cidr_blocks = list(string) # list of allowed source CIDR blocks
  }))
  default = {
    "80" = { ... }             # map key "80" — used as ingress.key inside the dynamic block
    "443" = { ... }            # map key "443"
  }
}
```

### Refactored Resource Block

```hcl
resource "aws_security_group" "main" {
  name   = "core-sg"
  vpc_id = aws_vpc.vpc.id

  dynamic "ingress" {
    for_each = var.web_ingress
    content {
      description = ingress.value.description
      from_port   = ingress.value.port
      to_port     = ingress.value.port
      protocol    = ingress.value.protocol
      cidr_blocks = ingress.value.cidr_blocks
    }
  }
}
```

```hcl
# Line-by-line Comments
dynamic "ingress" {
  for_each = var.web_ingress          # iterates over the map variable; one ingress block per map entry
  content {
    description = ingress.value.description  # pulls description from the object at the current map key
    from_port   = ingress.value.port
    to_port     = ingress.value.port
    protocol    = ingress.value.protocol     # now driven by variable (was hardcoded "tcp")
    cidr_blocks = ingress.value.cidr_blocks  # now driven by variable (was hardcoded ["0.0.0.0/0"])
  }
}
```

**Code Walkthrough:**

- `map(object({...}))` is a strongly-typed variable: Terraform validates that every supplied value contains exactly the declared attributes with the declared types. This prevents misconfiguration at plan time.
- When iterating a map, `ingress.key` is the map key string (`"80"` or `"443"`); `ingress.value` is the object at that key.
- The `locals` block from Task 3 can be removed once the variable is in place.
- To add a new ingress rule (e.g., port 8080), only the variable's `default` map needs a new entry — no changes to the resource block itself.

```bash
terraform validate   # catches syntax errors (e.g., typos in attribute names)
terraform apply      # result: no changes (refactor only)
```

## Key Terms & Definitions

| Term                              | Definition                                                                                                                               |
| --------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------- |
| **Dynamic Block**                 | A special block type that generates repeatable nested blocks by iterating over a collection                                              |
| **`dynamic "<label>"`**           | Declares a dynamic block; the label must match the nested block name the parent resource supports                                        |
| **`for_each`** (in dynamic block) | The collection (list or map) to iterate; one nested block is generated per element                                                       |
| **`content { }`**                 | The body template inside a dynamic block; uses the iterator to access per-element values                                                 |
| **Iterator**                      | The object available inside a dynamic block's `content` block; defaults to the dynamic label name (e.g., `ingress.value`, `ingress.key`) |
| **`ingress.value`**               | The current iteration's element value (an object if iterating a map of objects)                                                          |
| **`ingress.key`**                 | The current iteration's key (index if list, string key if map)                                                                           |
| **`map(object({...}))`**          | A variable type that enforces a typed schema on each map value                                                                           |

## Pitfalls & Best Practices

- **Only use dynamic blocks when the block count is variable or data-driven.** Two static `ingress` blocks are perfectly readable; a dynamic block for two rules adds complexity without benefit. The guideline from HashiCorp is to use dynamic blocks primarily in reusable modules where the caller controls the block count.
- **Always write nested blocks literally where possible.** Static blocks are easier to read, review, and debug than dynamic blocks.
- **Dynamic blocks are supported in `resource`, `data`, `provider`, and `provisioner` blocks only.** They cannot be used at the top level of a configuration.
- **The `content` block is required.** Omitting it causes a parse error.
- **Validate before applying after refactors.** Typos in attribute names inside `content` (e.g., `protocl` instead of `protocol`) cause plan errors. Run `terraform validate` to catch them before `apply`.
- **State is not affected by dynamic block refactoring.** Converting static nested blocks to a dynamic block (or vice versa) without changing the resulting infrastructure produces a no-change plan.
