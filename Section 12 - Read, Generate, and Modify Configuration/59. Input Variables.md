# Input Variables — Setting Values & Order of Precedence

## Overview

This lab extends the foundational Variables Block lab by demonstrating the multiple mechanisms Terraform provides for supplying variable values at runtime. Rather than hardcoding values in `main.tf`, operators can override defaults through environment variables, `.tfvars` files, or CLI flags — each with a defined order of precedence.

---

## Concepts

### Variable Value Resolution Order (Lowest → Highest Priority)

Terraform evaluates variable values in a strict order. A value set by a higher-priority mechanism **always overrides** values set by lower-priority mechanisms.

| Priority    | Mechanism                                  | Example                                                  |
| ----------- | ------------------------------------------ | -------------------------------------------------------- |
| 1 (lowest)  | Default value in `variable` block          | `default = "10.0.202.0/24"`                              |
| 2           | Environment variable (`TF_VAR_`)           | `export TF_VAR_variables_sub_cidr="10.0.203.0/24"`       |
| 3           | `terraform.tfvars` or `*.auto.tfvars` file | `variables_sub_cidr = "10.0.204.0/24"`                   |
| 4 (highest) | CLI `-var` or `-var-file` flag             | `terraform plan -var variables_sub_cidr="10.0.205.0/24"` |

> **Key rule:** Terraform uses the _last_ value it finds during evaluation. Moving down the table means overriding everything above it.

---

## Terraform Workflow

The lab progresses through four cumulative override steps, each replacing an AWS subnet CIDR block and availability zone:

```
Default (202) → ENV VAR (203) → tfvars (204) → CLI flag (205)
```

### Step-by-Step Task Flow

1. Inspect current state: `terraform state list` / `terraform state show <resource>`
2. **Task 1** — Set value via environment variable, then `terraform plan` + `terraform apply`
3. **Task 2** — Set value via `terraform.tfvars`, then `terraform plan` + `terraform apply`
4. **Task 3** — Set value via `-var` CLI flag, then `terraform plan` + `terraform apply`

## Task 1: Environment Variable

To set a Terraform variable via an environment variable, prefix its name with `TF_VAR_`.

```bash
export TF_VAR_variables_sub_cidr="10.0.203.0/24"
```

```bash
# Line-by-line Comments
export TF_VAR_variables_sub_cidr="10.0.203.0/24"
# export         — sets a shell environment variable for the current session and subprocesses
# TF_VAR_        — required prefix; Terraform scans for this prefix to identify variable inputs
# variables_sub_cidr — exact name of the declared Terraform variable
# "10.0.203.0/24"   — the new CIDR block value, overriding the default 10.0.202.0/24
```

**Code Walkthrough:**

- Terraform detects any environment variable prefixed with `TF_VAR_` at plan/apply time.
- The suffix must match the variable name exactly (case-sensitive).
- The environment variable is session-scoped; it persists only for the duration of the shell session unless exported to a persistent profile (e.g., `.bashrc`).
- This approach is common in CI/CD pipelines where secrets or environment-specific values are injected without modifying source files.

**Result:** Terraform replaces the subnet because the CIDR changed from `10.0.202.0/24` → `10.0.203.0/24`.

```bash
terraform plan   # observe replacement
terraform apply  # confirm with 'yes'
```

## Task 2: `.tfvars` File

A `terraform.tfvars` file allows multiple variable values to be declared in a single file without modifying `variables.tf` or setting environment variables.

```hcl
# Public Subnet Values
variables_sub_auto_ip = true
variables_sub_az      = "us-east-1d"
variables_sub_cidr    = "10.0.204.0/24"
```

```hcl
# Line-by-line Comments
# Public Subnet Values              — comment grouping related variables (best practice)
variables_sub_auto_ip = true        # enables auto-assign public IP on the subnet
variables_sub_az      = "us-east-1d" # overrides the default availability zone
variables_sub_cidr    = "10.0.204.0/24" # overrides both the default AND the env var value
```

**Code Walkthrough:**

- Terraform automatically loads `terraform.tfvars` if it exists in the working directory.
- Files named `*.auto.tfvars` are also automatically loaded.
- The `.tfvars` file takes precedence over both the `variable` block default and any `TF_VAR_` environment variables.
- The author recommends grouping variables with comments (e.g., `# Public Subnet Values`, `# Application Values`) to improve maintainability.

**Result:** Terraform replaces the subnet: CIDR changes from `10.0.203.0/24` → `10.0.204.0/24`, AZ changes from `us-east-1a` → `us-east-1d`. Tags update accordingly.

```bash
terraform plan   # observe replacement
terraform apply  # confirm with 'yes'
```

## Task 3: CLI `-var` Flag

The `-var` flag passes individual variable values directly on the command line. This is the highest-priority mechanism and overrides all other value sources.

```bash
terraform plan -var variables_sub_az="us-east-1e" -var variables_sub_cidr="10.0.205.0/24"
```

```bash
# Line-by-line Comments
terraform plan                          # initiates a plan (dry run)
  -var variables_sub_az="us-east-1e"   # overrides variables_sub_az for this execution only
  -var variables_sub_cidr="10.0.205.0/24" # overrides variables_sub_cidr for this execution only
```

**Code Walkthrough:**

- `-var` accepts one variable per flag; multiple `-var` flags can be chained.
- Values set with `-var` are **not persisted** — they apply only to that single `plan` or `apply` invocation.
- To reuse the same values in `apply`, either re-supply the `-var` flags or save the plan to a file and apply it:

```bash
# Save plan with variable overrides
terraform plan -var variables_sub_az="us-east-1e" -var variables_sub_cidr="10.0.205.0/24" -out=myplan

# Apply the saved plan (variable values are baked in)
terraform apply myplan
```

- The `-var-file` flag (alternative to `-var`) accepts a file containing multiple variable assignments and also carries highest priority.
- If `terraform apply` is run **without** re-specifying the `-var` flags and no saved plan is used, Terraform falls back to the next highest-priority source (`terraform.tfvars`), reverting to `10.0.204.0/24`.

**Result:** Terraform replaces the subnet: CIDR changes from `10.0.204.0/24` → `10.0.205.0/24`, AZ changes from `us-east-1d` → `us-east-1e`.

```bash
terraform apply -var variables_sub_az="us-east-1e" -var variables_sub_cidr="10.0.205.0/24"
# or
terraform apply myplan  # if plan was saved with -out=myplan
```

## Key Terms & Definitions

| Term                    | Definition                                                                                         |
| ----------------------- | -------------------------------------------------------------------------------------------------- |
| **Input Variable**      | A declared parameter in a `variable` block that allows dynamic value injection at runtime          |
| **`TF_VAR_`**           | Shell environment variable prefix Terraform scans to populate input variable values                |
| **`terraform.tfvars`**  | Auto-loaded file containing `key = value` pairs that set input variable values                     |
| **`*.auto.tfvars`**     | Any file ending in `.auto.tfvars`; also auto-loaded by Terraform                                   |
| **`-var` flag**         | CLI flag for setting a single variable value inline during `plan` or `apply`                       |
| **`-var-file` flag**    | CLI flag pointing to a file containing variable assignments; same highest priority as `-var`       |
| **`-out` flag**         | Saves a `terraform plan` result to a binary plan file for deterministic `apply`                    |
| **Order of Precedence** | The hierarchy determining which variable value "wins" when multiple sources conflict               |
| **HCL**                 | HashiCorp Configuration Language — the declarative language used to write Terraform configurations |

## Common Exam Traps

- **`.tfvars` does NOT override `-var` CLI flags.** The CLI is always the highest priority. Exam questions may test this by presenting a scenario where both are set.
- **Environment variables are session-scoped.** If a new shell session is opened, `TF_VAR_` values are lost unless set in a profile. Running `terraform apply` without re-exporting may revert to defaults.
- **Saving a plan captures variable values.** A plan saved with `-out=<file>` bakes in all variable values at plan time. Running `terraform apply <planfile>` uses those baked-in values regardless of current environment state.
- **`terraform apply` without a plan file re-evaluates variables.** Not providing `-var` flags on `apply` (when they were used on `plan`) means Terraform re-reads configuration files — it does **not** remember flags from a prior `plan` invocation.
- **`terraform.tfvars` is auto-loaded; custom `.tfvars` files are not.** A file named `production.tfvars` requires `-var-file=production.tfvars` to be loaded. Only `terraform.tfvars` and `*.auto.tfvars` are loaded automatically.
- **Variable name matching is case-sensitive.** `TF_VAR_Variables_Sub_CIDR` will NOT match a variable named `variables_sub_cidr`.
- **Multiple `-var` flags for the same variable:** Terraform uses the last one specified on the command line.
