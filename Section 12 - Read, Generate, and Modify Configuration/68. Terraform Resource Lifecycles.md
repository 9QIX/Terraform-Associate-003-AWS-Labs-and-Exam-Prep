# Terraform Resource Lifecycles

## Overview

Terraform's resource graph determines the order in which resources are created and destroyed. While the default order is appropriate in most cases, there are situations where the default behavior causes failures — most commonly when a resource must be replaced but cannot be destroyed while another resource depends on it. The `lifecycle` meta-argument block provides directives that override the default create/destroy order and add safeguards against accidental destruction.

---

## Concepts

### Default Terraform Replacement Behavior

When a resource change requires **replacement** (e.g., a security group's name changes), Terraform's default sequence is:

```
1. Destroy the existing resource
2. Create the replacement resource
```

This works for independent resources, but **fails** when the resource being destroyed is still in use by a dependent resource. In the lab example, renaming a security group from `core-sg` to `core-sg-global` forces a replacement. Terraform attempts to destroy the old security group first, but the destroy fails because the EC2 instance is still associated with it.

### Lifecycle Directives

The `lifecycle` block is a **meta-argument** available inside any `resource` block. It contains directives that modify Terraform's default create/destroy behavior.

| Directive                      | Effect                                                                                                                              |
| ------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------- |
| `create_before_destroy = true` | Creates the replacement resource first; both old and new exist simultaneously; old is destroyed only after new is confirmed created |
| `prevent_destroy = true`       | Causes `terraform plan` to fail with an error if any configuration change would result in this resource being destroyed             |

---

## Terraform Workflow

1. Create an AWS security group and associate it with an EC2 instance.
2. Make a change to the security group that forces replacement (rename).
3. Observe the failure under default lifecycle behavior (destroy-first).
4. Add `create_before_destroy = true` to the security group's `lifecycle` block.
5. Re-run `terraform apply` to confirm the replacement succeeds with the new order.

## Task 1: `create_before_destroy`

### Problem — Default Destroy-First Behavior

When a resource argument like `name` is marked as requiring replacement (ForceNew), Terraform's default plan is:

```
aws_security_group.main: Destroying... (destroy-first)
aws_security_group.main: Destruction complete
aws_security_group.main: Creating... (new)
```

If the security group is attached to a running EC2 instance, AWS will reject the destroy operation with a dependency violation — the security group cannot be deleted while it is in use.

### Solution — `create_before_destroy`

```hcl
resource "aws_security_group" "main" {
  name   = "core-sg-global"
  vpc_id = aws_vpc.vpc.id

  lifecycle {
    create_before_destroy = true
  }
}
```

```hcl
# Line-by-line Comments
resource "aws_security_group" "main" {
  name   = "core-sg-global"         # changed from "core-sg"; triggers forced replacement
  vpc_id = aws_vpc.vpc.id

  lifecycle {                        # meta-argument block; modifies Terraform's default behavior
    create_before_destroy = true     # reverses the destroy order:
                                     # 1. create new security group
                                     # 2. update EC2 instance to use new SG
                                     # 3. destroy old security group
  }
}
```

**Code Walkthrough:**

- `lifecycle` is a reserved meta-argument block available on all `resource` blocks.
- `create_before_destroy = true` instructs Terraform to provision the replacement resource before the old one is destroyed.
- During the apply, both the old and new resource exist simultaneously. After the new resource is confirmed created, the old one is destroyed.
- This resolves the dependency conflict: the EC2 instance is moved to the new security group before the old one is deleted.

### Revised Apply Sequence (with `create_before_destroy`)

```
1. aws_security_group.main (new): Creating...
2. aws_security_group.main (new): Creation complete
3. aws_instance.web_server: Updating... (security_groups updated to new SG)
4. aws_security_group.main (old): Destroying...
5. aws_security_group.main (old): Destruction complete
```

## Task 2: `prevent_destroy`

The `prevent_destroy` directive adds a safeguard against accidental destruction of critical resources.

```hcl
resource "aws_instance" "web_server" {
  # ... resource arguments ...

  lifecycle {
    prevent_destroy = true
  }
}
```

```hcl
# Line-by-line Comments
lifecycle {
  prevent_destroy = true   # causes terraform plan to ERROR if this resource would be destroyed
                           # protects against accidental terraform destroy or replacement
}
```

**Code Walkthrough:**

- When `prevent_destroy = true` is set, any plan that would result in the resource being destroyed (including replacement) causes a plan-time error — Terraform refuses to proceed.
- This applies to both explicit `terraform destroy` and implicit destroys caused by configuration changes that require replacement.
- To intentionally destroy the resource, the `prevent_destroy` directive must first be removed from the configuration.
- Common use cases: production databases, DNS zones, S3 buckets containing critical data.

### Plan Error Example

```text
Error: Instance cannot be destroyed

  on main.tf line 10:
  10: resource "aws_instance" "web_server" {

Resource aws_instance.web_server has lifecycle.prevent_destroy set,
but the plan calls for this resource to be destroyed. To avoid this error
and continue with the plan, either disable lifecycle.prevent_destroy or
reduce the scope of the plan using the -target flag.
```

## Key Terms & Definitions

| Term                        | Definition                                                                                                                                      |
| --------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------- |
| **`lifecycle` block**       | A meta-argument block inside a `resource` block that modifies Terraform's default create/update/destroy behavior                                |
| **`create_before_destroy`** | Lifecycle directive that reverses the default destroy-first replacement order; new resource is created before old is destroyed                  |
| **`prevent_destroy`**       | Lifecycle directive that causes `terraform plan` to fail if the resource would be destroyed                                                     |
| **ForceNew**                | A provider-level attribute flag indicating that a change to that attribute requires the resource to be destroyed and recreated                  |
| **Replacement**             | When a resource's ForceNew attribute changes, Terraform must destroy the existing resource and create a new one to apply the change             |
| **Meta-argument**           | A Terraform-level argument available on all resource blocks regardless of provider (`depends_on`, `count`, `for_each`, `provider`, `lifecycle`) |

---

## Common Exam Traps

- **`create_before_destroy` does not eliminate the destroy step.** It reverses the order — new is created first, old is destroyed after. Both resources exist simultaneously during the apply window.
- **`prevent_destroy` is enforced at plan time, not apply time.** The error appears when running `terraform plan`, not `terraform apply`.
- **Removing `prevent_destroy` from config does not immediately destroy the resource.** The resource is only destroyed when explicitly targeted by `terraform destroy` or a replacement is triggered.
- **`create_before_destroy` can fail if the provider does not allow two instances of the resource with the same name simultaneously.** In such cases, a unique name must be generated for the new resource (e.g., using `random_id` or a suffix) before the old one is destroyed.
- **`lifecycle` is a meta-argument, not a provider argument.** It is valid for all resource types across all providers — it is a Terraform core feature, not specific to AWS or any other provider.
- **`prevent_destroy = true` and `terraform destroy` using `-target`:** The `-target` flag does not bypass `prevent_destroy` — the error still occurs.
