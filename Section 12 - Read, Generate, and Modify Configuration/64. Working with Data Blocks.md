# Working with Data Blocks

## Overview

Cloud infrastructure emits data that Terraform can query without managing the resource itself. **Data sources** allow Terraform to fetch read-only information from a provider API — such as an S3 bucket ARN — and use that information elsewhere in the configuration. This lab demonstrates querying an externally created AWS S3 bucket, consuming its exported attributes inside a resource block, and surfacing additional attributes through outputs.

---

## Concepts

- A **data block** instructs Terraform to perform a read-only query against a provider API. It does not create, modify, or destroy the queried resource.
- Data sources are distinct from resources: resources are managed by Terraform; data sources are only read by Terraform.
- Any attribute exported by a data source can be referenced using the syntax `data.<type>.<name>.<attribute>`.
- If a resource is **created by Terraform**, its attributes are available directly via `<resource_type>.<name>.<attribute>` — no data block is needed for resources already in the same configuration.
- Data blocks are evaluated during `terraform plan` and `terraform apply` by calling the provider API in real time.

### Data Block vs. Resource Block

| Aspect              | `resource` block                   | `data` block                                           |
| ------------------- | ---------------------------------- | ------------------------------------------------------ |
| Purpose             | Creates / manages infrastructure   | Reads existing infrastructure                          |
| Terraform lifecycle | `create`, `update`, `destroy`      | Read-only                                              |
| State tracking      | Yes — Terraform manages the object | No — Terraform only caches the result                  |
| Reference syntax    | `<type>.<name>.<attr>`             | `data.<type>.<name>.<attr>`                            |
| Use case            | Deploying new resources            | Consuming pre-existing or externally managed resources |

---

## Terraform Workflow

1. Create or identify an existing resource outside Terraform (in this lab, an S3 bucket created manually in the AWS console).
2. Add a `data` block referencing that resource by its identifier.
3. Use `data.<type>.<name>.<attribute>` to consume exported attributes inside resource blocks or outputs.
4. Run `terraform plan` to verify attribute resolution; run `terraform apply` to deploy.

## Task 1: Query an Existing Resource with a Data Block

### Prerequisite

Create an S3 bucket manually in the AWS console (all defaults). S3 bucket names must be globally unique — append initials or a unique suffix.

### Data Block

```hcl
data "aws_s3_bucket" "data_bucket" {
  bucket = "my-data-lookup-bucket-btk"
}
```

```hcl
# Line-by-line Comments
data "aws_s3_bucket" "data_bucket" {      # data block; type = aws_s3_bucket, local name = data_bucket
  bucket = "my-data-lookup-bucket-btk"   # the S3 bucket name to query; must already exist in AWS
}
# result: data.aws_s3_bucket.data_bucket — a map of exported attributes (arn, id, region, etc.)
```

**Code Walkthrough:**

- `"aws_s3_bucket"` is the data source type defined by the AWS provider.
- `"data_bucket"` is the local name used to reference this lookup elsewhere in the configuration.
- `bucket` is the required argument — the exact name of the existing S3 bucket.
- Terraform calls the AWS API at plan time to retrieve the bucket's metadata; no infrastructure is created or modified.

### Using the Data Lookup in a Resource

```hcl
resource "aws_iam_policy" "policy" {
  name        = "data_bucket_policy"
  description = "Deny access to my bucket"
  policy = jsonencode({
    "Version" : "2012-10-17",
    "Statement" : [
      {
        "Effect" : "Allow",
        "Action" : [
          "s3:Get*",
          "s3:List*"
        ],
        "Resource" : "${data.aws_s3_bucket.data_bucket.arn}"
      }
    ]
  })
}
```

```hcl
# Line-by-line Comments
resource "aws_iam_policy" "policy" {
  name        = "data_bucket_policy"          # name of the IAM policy as it appears in AWS
  description = "Deny access to my bucket"    # human-readable description
  policy = jsonencode({                        # jsonencode() converts HCL map/object to a JSON string
    "Version" : "2012-10-17",                  # IAM policy version — always "2012-10-17" for current syntax
    "Statement" : [
      {
        "Effect" : "Allow",                    # allows the listed actions
        "Action" : [
          "s3:Get*",                           # all S3 Get actions
          "s3:List*"                           # all S3 List actions
        ],
        "Resource" : "${data.aws_s3_bucket.data_bucket.arn}"
        # data.aws_s3_bucket.data_bucket.arn — resolves to the ARN of the queried bucket
        # interpolation syntax required here because the value is inside a JSON string
      }
    ]
  })
}
```

**Code Walkthrough:**

- `jsonencode()` converts an HCL object literal to a JSON string, which is what the `aws_iam_policy` resource requires for its `policy` argument.
- `data.aws_s3_bucket.data_bucket.arn` references the `arn` attribute exported by the data source. Terraform substitutes the actual ARN at plan time.
- The `${}` interpolation syntax is used here because the reference appears inside a JSON string within `jsonencode()`.
- The policy description says "Deny" but the Effect is "Allow" — this is a documentation error in the source material; the policy as written grants `Allow`.

```bash
terraform plan           # verify the IAM policy references the correct bucket ARN
terraform apply -auto-approve
```

## Task 2: Export Additional Attributes from a Data Lookup

The `aws_s3_bucket` data source exports multiple attributes, including: `id` (bucket name), `arn`, `bucket_domain_name`, `bucket_regional_domain_name`, `hosted_zone_id`, `region`, `website_endpoint`, `website_domain`.

### Output Blocks

```hcl
output "data-bucket-arn" {
  value = data.aws_s3_bucket.data_bucket.arn
}

output "data-bucket-domain-name" {
  value = data.aws_s3_bucket.data_bucket.bucket_domain_name
}

output "data-bucket-region" {
  value = "The ${data.aws_s3_bucket.data_bucket.id} bucket is located in ${data.aws_s3_bucket.data_bucket.region}"
}
```

```hcl
# Line-by-line Comments
output "data-bucket-arn" {
  value = data.aws_s3_bucket.data_bucket.arn               # the bucket's ARN (includes account number)
}

output "data-bucket-domain-name" {
  value = data.aws_s3_bucket.data_bucket.bucket_domain_name # global S3 domain name for the bucket
}

output "data-bucket-region" {
  value = "The ${data.aws_s3_bucket.data_bucket.id} bucket is located in ${data.aws_s3_bucket.data_bucket.region}"
  # .id     — the bucket name (equivalent to the bucket argument passed to the data block)
  # .region — the AWS region where the bucket was created
  # string interpolation produces a human-readable sentence combining both attributes
}
```

**Code Walkthrough:**

- Each output references a different exported attribute of the same data source (`data.aws_s3_bucket.data_bucket`).
- String interpolation (`"${...}"`) can mix literal text and data source attributes in a single string value.
- Running `terraform apply -auto-approve` (with no infrastructure changes) only updates the outputs in state.

```bash
terraform apply -auto-approve
```

Sample output:

```text
data-bucket-arn         = "arn:aws:s3:::my-data-lookup-bucket-btk"
data-bucket-domain-name = "my-data-lookup-bucket-btk.s3.amazonaws.com"
data-bucket-region      = "The my-data-lookup-bucket-btk bucket is located in us-east-1"
```

## Key Terms & Definitions

| Term                            | Definition                                                                                                              |
| ------------------------------- | ----------------------------------------------------------------------------------------------------------------------- |
| **Data Source**                 | A provider-defined read-only query that retrieves information about existing infrastructure                             |
| **`data` block**                | HCL — HashiCorp Configuration Language block that declares a data source query                                          |
| **`data.<type>.<name>.<attr>`** | Reference syntax for consuming an exported attribute from a data source                                                 |
| **Exported attributes**         | The set of attributes a data source makes available after a successful query; documented in the provider registry       |
| **`jsonencode()`**              | HCL built-in function that converts an HCL map or object to a JSON-formatted string                                     |
| **IAM Policy**                  | AWS Identity and Access Management document (JSON) that defines allowed or denied actions on resources                  |
| **ARN**                         | Amazon Resource Name — a globally unique identifier for an AWS resource; embeds account number, region, and resource ID |
| **`terraform console`**         | Interactive REPL that evaluates Terraform expressions, useful for inspecting data source attributes                     |

---

## Common Exam Traps

- **Data blocks do not create resources.** A `data` block only reads; it never modifies or destroys. Confusing `data` blocks with `resource` blocks is a common mistake.
- **Resources created by Terraform do not need a `data` block.** If a resource already exists in the same Terraform configuration, reference it directly via `<type>.<name>.<attribute>`. A `data` block is only needed for resources created outside Terraform or in a separate configuration.
- **Data source reference syntax requires the `data.` prefix.** `data.aws_s3_bucket.data_bucket.arn` is correct; `aws_s3_bucket.data_bucket.arn` (without `data.`) would be interpreted as a resource reference and cause an error.
- **Data sources are re-evaluated on every plan and apply.** If the queried resource changes externally between runs, Terraform will pick up the new values. This is intentional behavior, not a bug.
- **`jsonencode()` is required when a resource argument expects a JSON string.** Passing an HCL object directly to a JSON-string argument causes a type error.
- **Exported attributes vary by data source type.** Not all attributes shown in the resource documentation are available in the data source. Always check the Data Sources section of the provider documentation (not the Resources section) for the correct exported attribute list.
