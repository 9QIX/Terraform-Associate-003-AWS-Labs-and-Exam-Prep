# Terraform Graph

## Overview

Terraform builds an internal **resource graph** that models every resource and its dependencies before executing any plan or apply. This graph drives dependency ordering (sequential vs. parallel creation), optimizes deployment speed, and is the mechanism behind Terraform's interpolation syntax. The `terraform graph` command exports this graph in DOT format, which can be rendered visually with tools like GraphViz.

---

## Concepts

- Every reference between resources (e.g., `aws_subnet` using `aws_vpc.vpc.id`) creates an implicit **dependency edge** in the graph.
- Resources with no dependencies on other resources can be created **in parallel**.
- Resources that depend on the output of another resource must be created **sequentially** — after the dependency exists.
- Terraform walks the graph multiple times: once to collect provider input, once to validate, once to plan, and once to apply.
- The graph starts at a **root node** and fans out through providers to individual resources.

### Dependency Types

| Dependency Type     | How It Is Created                                          | Example                      |
| ------------------- | ---------------------------------------------------------- | ---------------------------- |
| **Implicit**        | Referencing another resource's attribute via interpolation | `vpc_id = aws_vpc.vpc.id`    |
| **Explicit**        | Using the `depends_on` meta-argument                       | `depends_on = [aws_vpc.vpc]` |
| **None (parallel)** | No reference to any other resource                         | `tls_private_key.generated`  |

---

## Terraform Workflow

1. **Task 1** — Examine resource blocks in `main.tf` to identify which resources have dependencies and which are independent.
2. **Task 2** — Run `terraform graph` to generate DOT-format output; paste into a GraphViz-compatible visualizer to render the dependency graph.

## Task 1: Resource Graph and Dependencies

### Example Configuration

```hcl
resource "aws_vpc" "vpc" {
  cidr_block = var.vpc_cidr

  tags = {
    Name        = var.vpc_name
    Environment = "demo_environment"
    Terraform   = "true"
  }

  enable_dns_hostnames = true
}

resource "aws_subnet" "private_subnets" {
  for_each          = var.private_subnets
  vpc_id            = aws_vpc.vpc.id
  cidr_block        = cidrsubnet(var.vpc_cidr, 8, each.value)
  availability_zone = tolist(data.aws_availability_zones.available.names)[each.value]

  tags = {
    Name      = each.key
    Terraform = "true"
  }
}

resource "aws_internet_gateway" "internet_gateway" {
  vpc_id = aws_vpc.vpc.id
  tags = {
    Name = "demo_igw"
  }
}

resource "tls_private_key" "generated" {
  algorithm = "RSA"
}
```

```hcl
# Line-by-line Comments (dependency-relevant lines only)

# aws_vpc.vpc — no references to other managed resources; no dependency
cidr_block = var.vpc_cidr   # input variable reference, not a resource dependency

# aws_subnet.private_subnets — DEPENDS ON aws_vpc.vpc
vpc_id = aws_vpc.vpc.id     # interpolation creates implicit dependency: subnet waits for VPC

# aws_internet_gateway.internet_gateway — DEPENDS ON aws_vpc.vpc
vpc_id = aws_vpc.vpc.id     # same pattern: IGW waits for VPC

# tls_private_key.generated — NO DEPENDENCY
algorithm = "RSA"            # no resource references; can be created in parallel with the VPC
```

**Code Walkthrough:**

- `aws_vpc.vpc` — independent; no references to other managed resources. It is one of the first resources created.
- `aws_subnet.private_subnets` — references `aws_vpc.vpc.id`, creating an implicit dependency. Terraform will not attempt to create subnets until the VPC exists and its `id` is known.
- `aws_internet_gateway.internet_gateway` — references `aws_vpc.vpc.id` in the same way; also dependent on the VPC.
- `tls_private_key.generated` — no resource references whatsoever. Terraform can create it **in parallel** with the VPC during the same apply operation.

### Execution Order (derived from the graph)

```
Root
├── [parallel] aws_vpc.vpc
└── [parallel] tls_private_key.generated

After aws_vpc.vpc is created:
├── aws_subnet.private_subnets (depends on VPC)
└── aws_internet_gateway.internet_gateway (depends on VPC)
```

## Task 2: Generate the Graph with `terraform graph`

### Commands

```bash
terraform init
terraform apply
terraform graph
```

```bash
# Line-by-line Comments
terraform init    # initializes providers and modules (required before graph)
terraform apply   # deploys the infrastructure (graph can also be run against an undeployed config)
terraform graph   # outputs the resource graph in DOT format to stdout
```

### Sample DOT Output (abbreviated)

```text
digraph {
    compound = "true"
    newrank  = "true"
    subgraph "root" {
        # ...resource nodes and edges...
    }
}
```

**Code Walkthrough:**

- `terraform graph` does not require a deployed environment — it generates the graph from the current configuration files.
- The output format is **DOT** (a graph description language used by GraphViz).
- The `digraph` keyword declares a **directed graph** — edges have direction (dependency flows from dependent → dependency).
- `subgraph "root"` is the root node from which Terraform begins its graph walk.

### Visualize the Output

Copy the full DOT output and paste it into a GraphViz-compatible web tool (e.g., [webgraphviz.com](http://www.webgraphviz.com)) to render a visual dependency diagram.

The rendered graph will show:

- All resource nodes connected by directed edges.
- Variables and data sources as upstream nodes.
- The VPC node with multiple downstream dependencies (subnets, internet gateway).
- The TLS private key as an isolated node with no dependency edges to the VPC.

## Key Terms & Definitions

| Term                     | Definition                                                                                                                |
| ------------------------ | ------------------------------------------------------------------------------------------------------------------------- |
| **Resource Graph**       | Terraform's internal directed acyclic graph (DAG) representing all resources and their dependency relationships           |
| **Root Node**            | The starting point of the graph walk; Terraform begins evaluation here and fans out through providers                     |
| **Implicit Dependency**  | A dependency created automatically when one resource references another resource's attribute via interpolation            |
| **Parallel Execution**   | Resources with no dependency relationship are created concurrently during `apply` to minimize total deployment time       |
| **Sequential Execution** | Resources that depend on another resource are created only after the dependency is fully provisioned                      |
| **`terraform graph`**    | CLI command that outputs the current resource graph in DOT format                                                         |
| **DOT Format**           | A plain-text graph description language used by GraphViz; output of `terraform graph`                                     |
| **GraphViz**             | An open-source graph visualization tool that renders DOT-format output as diagrams                                        |
| **DAG**                  | Directed Acyclic Graph — the data structure underlying Terraform's resource graph; ensures no circular dependencies exist |

---

## Common Exam Traps

- **`terraform graph` outputs DOT format, not JSON or HCL.** The output must be processed by a GraphViz-compatible tool to produce a visual diagram.
- **Implicit dependencies are created by interpolation references.** Simply declaring resources in the same file does not create a dependency — only referencing one resource's attribute inside another resource does.
- **Terraform creates independent resources in parallel.** The exam may ask about how Terraform optimizes apply time — the answer is parallel execution of unrelated resources, enabled by the resource graph.
- **`terraform graph` can be run before `terraform apply`.** It reads the configuration, not the state, so it works on any valid configuration even before infrastructure is deployed.
- **Circular dependencies are not permitted.** If resource A references resource B and resource B references resource A, Terraform will fail with a cycle error at plan time.
- **`depends_on` forces an explicit dependency.** Use it when a dependency exists that cannot be expressed through attribute references (e.g., a resource that implicitly relies on a permission being in place).

### Updated Information (as of 2026-06-30)

- No deprecated syntax or commands were identified in the source material. The `terraform graph` command and DOT output format remain current and valid in Terraform 1.x.
- Note: `terraform graph` output has become significantly more verbose in recent Terraform versions (1.x) due to provider schema nodes and meta-resources being included. The rendered graph for a real configuration will be considerably larger than the simplified conceptual diagram shown in the lab. This does not affect functionality — the dependency relationships remain correct.
