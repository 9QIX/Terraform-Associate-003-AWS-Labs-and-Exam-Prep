# Variable Validation and Suppression

## Overview

Terraform provides two complementary mechanisms for hardening variable usage: **validation blocks** to enforce constraints on variable values at plan time, and the **`sensitive` argument** to suppress confidential values from CLI output. This lab covers both, demonstrates multiple validation patterns, and shows how sensitive values are still stored in plaintext in the Terraform state file.

---

## Concepts

- A `validation` block inside a `variable` block defines a `condition` expression and an `error_message`. If the condition evaluates to `false`, Terraform fails the plan with the specified message.
- Multiple `validation` blocks can exist within a single `variable` block — all conditions must pass.
- `sensitive = true` on a variable suppresses its value from CLI output but **does not** prevent it from being stored in the state file.
- The `nonsensitive()` function explicitly "unwraps" a sensitive value, allowing it to be output without the sensitive mask.
- If an output references a sensitive variable or local, Terraform **requires** the output to also declare `sensitive = true`.

---

## Terraform Workflow

1. Create `variables.tf` with `validation` blocks.
2. Run `terraform plan -var <name>=<value>` with both valid and invalid inputs to observe validation behavior.
3. Add `sensitive = true` to variables containing confidential data.
4. Add outputs; observe that Terraform enforces `sensitive = true` on any output referencing sensitive values.
5. Run `terraform apply` and inspect the state file to confirm sensitive values are stored in plaintext.

## Task 1: Basic Variable Validation

### Configuration

```hcl
variable "cloud" {
  type = string

  validation {
    condition     = contains(["aws", "azure", "gcp", "vmware"], lower(var.cloud))
    error_message = "You must use an approved cloud."
  }

  validation {
    condition     = lower(var.cloud) == var.cloud
    error_message = "The cloud name must not have capital letters."
  }
}
```

```hcl
# Line-by-line Comments
variable "cloud" {                                                              # declares an input variable named "cloud"
  type = string                                                                 # restricts the variable to string type

  validation {                                                                  # first validation block
    condition     = contains(["aws", "azure", "gcp", "vmware"], lower(var.cloud)) # checks that the lowercased value is in the approved list
    error_message = "You must use an approved cloud."                           # displayed if condition is false
  }

  validation {                                                                  # second validation block
    condition     = lower(var.cloud) == var.cloud                               # checks that no uppercase letters are present
    error_message = "The cloud name must not have capital letters."             # displayed if condition is false
  }
}
```

**Code Walkthrough:**

- `contains(list, element)` returns `true` if the element exists in the list.
- `lower(var.cloud)` normalizes the input to lowercase before the list check, so "AWS" passes the first condition but fails the second (uppercase check).
- Two separate `validation` blocks are evaluated independently. Both must pass.
- `error_message` must be a static string — it cannot reference `var.*` or other computed values.

### Testing Validation

```bash
terraform plan -var cloud=aws      # passes both validations
terraform plan -var cloud=alibabba # fails: "You must use an approved cloud."
```

```bash
# Line-by-line Comments
terraform plan -var cloud=aws       # valid: "aws" is in the approved list and is lowercase
terraform plan -var cloud=alibabba  # invalid: "alibabba" is not in the approved list
```

## Task 2: Additional Validation Patterns

### Configuration

```hcl
variable "no_caps" {
  type = string

  validation {
    condition     = lower(var.no_caps) == var.no_caps
    error_message = "Value must be in all lower case."
  }
}

variable "character_limit" {
  type = string

  validation {
    condition     = length(var.character_limit) == 3
    error_message = "This variable must contain only 3 characters."
  }
}

variable "ip_address" {
  type = string

  validation {
    condition     = can(regex("^(?:[0-9]{1,3}\\.){3}[0-9]{1,3}$", var.ip_address))
    error_message = "Must be an IP address of the form X.X.X.X."
  }
}
```

```hcl
# Line-by-line Comments

# --- no_caps ---
variable "no_caps" {
  type = string
  validation {
    condition     = lower(var.no_caps) == var.no_caps  # passes only if input is already all lowercase
    error_message = "Value must be in all lower case."
  }
}

# --- character_limit ---
variable "character_limit" {
  type = string
  validation {
    condition     = length(var.character_limit) == 3   # passes only if the string is exactly 3 characters
    error_message = "This variable must contain only 3 characters."
  }
}

# --- ip_address ---
variable "ip_address" {
  type = string
  validation {
    condition     = can(regex("^(?:[0-9]{1,3}\\.){3}[0-9]{1,3}$", var.ip_address))
    # can()   — returns true if the inner expression does not produce an error
    # regex() — applies a regular expression; errors (returns null) if no match, which can() converts to false
    # pattern — matches the form X.X.X.X where each X is 1–3 digits
    error_message = "Must be an IP address of the form X.X.X.X."
  }
}
```

**Code Walkthrough:**

- `length(string)` returns the number of characters — useful for enforcing fixed-length codes.
- `can(expr)` returns `true` if `expr` evaluates without error, and `false` if it produces an error. This pairs well with `regex()`, which throws an error on no-match rather than returning a boolean.
- The IP regex `^(?:[0-9]{1,3}\.){3}[0-9]{1,3}$` validates the structural format `X.X.X.X` but does not validate the numeric range of each octet (e.g., `999.999.999.999` would pass this check).

### Testing Valid and Invalid Inputs

```bash
# All valid inputs — all validations pass
terraform plan \
  -var cloud=aws \
  -var no_caps=training \
  -var ip_address=1.1.1.1 \
  -var character_limit=rpt

# Invalid inputs — multiple validations fail
terraform plan \
  -var cloud=all \
  -var no_caps=Training \
  -var ip_address=1223.22.342.22 \
  -var character_limit=ga
```

## Task 3: Suppressing Sensitive Variable Values

### Configuration

```hcl
variable "phone_number" {
  type      = string
  sensitive = true
  default   = "867-5309"
}

locals {
  contact_info = {
    cloud        = var.cloud
    department   = var.no_caps
    cost_code    = var.character_limit
    phone_number = var.phone_number
  }

  my_number = nonsensitive(var.phone_number)
}

output "cloud" {
  value = local.contact_info.cloud
}

output "department" {
  value = local.contact_info.department
}

output "cost_code" {
  value = local.contact_info.cost_code
}

output "phone_number" {
  sensitive = true
  value     = local.contact_info.phone_number
}

output "my_number" {
  value = local.my_number
}
```

```hcl
# Line-by-line Comments
variable "phone_number" {
  type      = string
  sensitive = true          # marks the variable as sensitive; suppresses value in CLI output
  default   = "867-5309"   # default value used if not supplied at runtime
}

locals {
  contact_info = {
    cloud        = var.cloud           # standard variable reference
    department   = var.no_caps
    cost_code    = var.character_limit
    phone_number = var.phone_number    # sensitive variable propagated into a local map
  }

  my_number = nonsensitive(var.phone_number)
  # nonsensitive() — explicitly removes the sensitive classification, allowing the value to be output without masking
  # Use with caution: this intentionally exposes the value in CLI output
}

output "phone_number" {
  sensitive = true                         # REQUIRED when output references a sensitive value
  value     = local.contact_info.phone_number
}

output "my_number" {
  value = local.my_number                  # exposed via nonsensitive(); displayed in plaintext
}
```

**Code Walkthrough:**

- When a variable is marked `sensitive = true`, that sensitivity **propagates** through any locals or expressions referencing it. Any output consuming a sensitive value must itself declare `sensitive = true`, or Terraform will fail with an error.
- `nonsensitive(value)` is an explicit override that tells Terraform "I understand this value is sensitive, and I intentionally want it exposed." The author used this to demonstrate the mechanism; in production it should only be used when there is a deliberate reason to expose the value.
- The output `my_number` uses `nonsensitive()` and therefore displays `"867-5309"` in plaintext, while `phone_number` displays `<sensitive>`.

### Error When `sensitive = true` Is Missing on Output

```text
Error: Output refers to sensitive values

  on variables.tf line 73:
  73: output "phone_number" {

To reduce the risk of accidentally exporting sensitive data that was intended to be only internal, Terraform requires
that any root module output containing sensitive data be explicitly marked as sensitive to confirm your intent.

If you do intend to export this data, annotate the output value as sensitive by adding the following argument:
    sensitive = true
```

### Apply Command and Expected Output

```bash
terraform apply \
  -var cloud=aws \
  -var no_caps=training \
  -var ip_address=1.1.1.1 \
  -var character_limit=rpt
```

```text
Outputs:

cost_code    = "rpt"
department   = "training"
my_number    = "867-5309"
phone_number = <sensitive>
```

## Task 4: Sensitive Values in the State File

Despite the `sensitive = true` marking, Terraform stores all output values — including sensitive ones — in plaintext within `terraform.tfstate`.

```json
{
  "version": 4,
  "terraform_version": "1.0.4",
  "serial": 3,
  "lineage": "5cfbccdd-b915-ee22-ea3c-17db83258332",
  "outputs": {
    "cloud": {
      "value": "aws",
      "type": "string"
    },
    "cost_code": {
      "value": "rpt",
      "type": "string"
    },
    "department": {
      "value": "training",
      "type": "string"
    },
    "my_number": {
      "value": "867-5309",
      "type": "string"
    },
    "phone_number": {
      "value": "867-5309",
      "type": "string",
      "sensitive": true
    }
  },
  "resources": []
}
```

```json
// Line-by-line Comments
"phone_number": {
  "value": "867-5309",    // plaintext value — stored regardless of sensitive = true
  "type": "string",
  "sensitive": true       // metadata flag indicating the value was marked sensitive; does not encrypt the value
}
```

**Code Walkthrough:**

- The `sensitive: true` flag in the state file is metadata — it tells Terraform to suppress display, but the value itself (`"867-5309"`) is stored unencrypted.
- Access to the state file must be controlled through external mechanisms: remote backends with access controls (e.g., HCP Terraform — HashiCorp Cloud Platform Terraform, S3 with bucket policies), encryption at rest, and least-privilege IAM policies.

      name = "variable_validation"           # the workspace to use for state storage and runs

```hcl
cloud           = "aws"
no_caps         = "training"

```

**Code Walkthrough:**

- `terraform.auto.tfvars` is automatically loaded by Terraform without any `-var-file` flag.
- After adding `remote.tf`, run `terraform init` to migrate state to the HCP Terraform workspace, then `terraform apply` to observe how sensitive values are handled in the HCP Terraform UI.

> **Note:** The `backend "remote"` block is the legacy syntax for configuring HCP Terraform. Current recommended syntax uses `cloud` block instead (see Updated Information).

## Key Terms & Definitions

| Term                          | Definition                                                                                                                 |
| ----------------------------- | -------------------------------------------------------------------------------------------------------------------------- |
| **`validation` block**        | A sub-block within a `variable` block that defines a `condition` and `error_message` to enforce constraints at plan time   |
| **`condition`**               | A boolean expression inside a `validation` block; must evaluate to `true` for the variable value to be accepted            |
| **`error_message`**           | A static string displayed when a `validation` condition fails                                                              |
| **`contains(list, element)`** | HCL — HashiCorp Configuration Language built-in function; returns `true` if the list contains the element                  |
| **`lower(string)`**           | HCL built-in function; converts a string to lowercase                                                                      |
| **`length(value)`**           | HCL built-in function; returns the number of characters in a string or elements in a collection                            |
| **`can(expression)`**         | HCL built-in function; returns `true` if the expression evaluates without error, `false` otherwise                         |
| **`regex(pattern, string)`**  | HCL built-in function; returns a match or throws an error if no match — typically wrapped in `can()` for validation        |
| **`sensitive = true`**        | Variable or output argument that suppresses the value in CLI output; does not affect state storage                         |
| **`nonsensitive(value)`**     | HCL built-in function; explicitly removes the sensitive classification from a value, allowing it to be output in plaintext |
| **HCP Terraform**             | HashiCorp Cloud Platform Terraform — managed Terraform service providing remote state, runs, and workspace management      |

## Common Exam Traps

- **`sensitive = true` is not encryption.** The state file stores the value in plaintext. The flag only controls CLI display. Exam questions may test this distinction.
- **Outputs that reference sensitive variables require `sensitive = true`.** Terraform enforces this at plan time. Forgetting this causes a plan error, not just a warning.
- **`nonsensitive()` intentionally exposes a sensitive value.** Using it in output blocks will display the value in the CLI — use only when deliberate.
- **Multiple `validation` blocks are independent.** Each condition is evaluated separately; all must pass. A value may pass one validation and fail another.
- **`error_message` must be a static string.** It cannot use string interpolation to reference variable values or other expressions.
- **`can(regex(...))` vs. direct `regex(...)`.** Using `regex()` directly in a condition without `can()` will cause a Terraform error rather than a clean validation failure if the pattern does not match.
- **`terraform.auto.tfvars` is auto-loaded.** Files named exactly `terraform.tfvars` or with the `.auto.tfvars` suffix are automatically picked up. Custom filenames require `-var-file`.
- **Remote backend `backend "remote"` is legacy syntax.** The current recommended approach uses the `cloud` block (see Updated Information).

### Updated Information (as of 2026-06-30)

- **`backend "remote"` is deprecated in favor of the `cloud` block.** The `remote` backend syntax used in the TFC Integration section has been superseded. The current recommended configuration for HCP Terraform is:

  ```hcl
  terraform {
    cloud {
      organization = "<<ORGANIZATION NAME>>"

      workspaces {
        name = "variable_validation"
      }
    }
  }
  ```

  The `cloud` block offers additional features (e.g., workspace tags) and is the canonical approach as of Terraform 1.1+.

- All other commands and HCL syntax demonstrated in this lab (`validation`, `sensitive`, `nonsensitive()`, `can()`, `regex()`, `contains()`, `lower()`, `length()`) remain current and valid in Terraform 1.x.
