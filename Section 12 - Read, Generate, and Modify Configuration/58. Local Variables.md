# Local Values in Terraform

## Overview

Local values (locals) assign a name to an expression, allowing reuse across a configuration without repetition. Unlike input variables, locals are internal to the module — they cannot be passed in by the caller. They are best used sparingly: when a single value or expression is referenced in many places and is likely to change in the future.

> **Exam Objective:** Terraform Associate 004 — Objective 8: Read, Generate, and Modify Configuration.

---

## Concepts

- A `locals` block defines one or more named values scoped to the current module.
- Local values can reference **variables**, **resource attributes**, and **other local values**.
- Multiple `locals` blocks are allowed in a configuration; they are merged at runtime.
- Locals do **not** accept input from the CLI or `.tfvars` files — they are computed internally.

## Terraform Workflow

### Task 1 — Define a `locals` Block

```hcl
locals {
  service_name = "Automation"
  app_team     = "Cloud Team"
  createdby    = "terraform"
}
```

**Line-by-line Comments:**

```hcl
locals {                          # Opens the local values block
  service_name = "Automation"    # Defines a local named service_name with a string literal
  app_team     = "Cloud Team"    # Defines a local named app_team with a string literal
  createdby    = "terraform"     # Defines a local named createdby with a string literal
}
```

**Code Walkthrough:**
This block introduces three static string locals. They have no external dependencies and serve as centralized constants for tagging resources. Placing them in a dedicated `locals` block (rather than inline) makes future updates a single-file change.

---

### Task 2 — Interpolate Local Values into Resource Tags

```hcl
tags = {
  "Service"   = local.service_name
  "AppTeam"   = local.app_team
  "CreatedBy" = local.createdby
}
```

**Line-by-line Comments:**

```hcl
tags = {
  "Service"   = local.service_name  # Reads the local value service_name → "Automation"
  "AppTeam"   = local.app_team      # Reads the local value app_team → "Cloud Team"
  "CreatedBy" = local.createdby     # Reads the local value createdby → "terraform"
}
```

**Code Walkthrough:**
Tag keys are string literals (quoted or unquoted when no spaces are present). Each value references a local using the `local.<name>` syntax. Running `terraform plan` after this change shows tag additions on the `aws_instance` resource; `terraform apply` commits them.

---

### Task 3 — Reference Locals from Other Locals (Common Tags Pattern)

```hcl
locals {
  common_tags = {
    Name      = var.server_name
    Owner     = local.team
    App       = local.application
    Service   = local.service_name
    AppTeam   = local.app_team
    CreatedBy = local.createdby
  }
}
```

**Line-by-line Comments:**

```hcl
locals {
  common_tags = {
    Name      = var.server_name    # Pulls the server name from an input variable
    Owner     = local.team         # References another local value: team
    App       = local.application  # References another local value: application
    Service   = local.service_name # References the service_name local defined earlier
    AppTeam   = local.app_team     # References the app_team local defined earlier
    CreatedBy = local.createdby    # References the createdby local defined earlier
  }
}
```

**Code Walkthrough:**
`common_tags` is a map-typed local that consolidates all standard tags. It mixes input variable references (`var.server_name`) with other local references (`local.team`, `local.application`, etc.). This pattern centralizes tag management — updating a single local propagates to every resource that references `local.common_tags`.

---

### Task 4 — Apply `common_tags` to a Resource

Replace the inline tag map on `aws_instance` with the shared local:

```hcl
resource "aws_instance" "web_server" {
  ami           = data.aws_ami.ubuntu.id
  instance_type = "t3.micro"
  subnet_id     = aws_subnet.public_subnets["public_subnet_1"].id

  tags = local.common_tags
}
```

**Line-by-line Comments:**

```hcl
resource "aws_instance" "web_server" {
  ami           = data.aws_ami.ubuntu.id                          # AMI sourced from a data block
  instance_type = "t3.micro"                                     # Instance size
  subnet_id     = aws_subnet.public_subnets["public_subnet_1"].id # Subnet reference via expression

  tags = local.common_tags  # Assigns the entire common_tags map — no inline tag definitions needed
}
```

**Code Walkthrough:**
Replacing the individual tag assignments with `local.common_tags` produces **no infrastructure changes** if the underlying values are identical to what was previously deployed. `terraform plan` confirms `No changes.` — validating that the refactor is logically equivalent. Any resource that also sets `tags = local.common_tags` will automatically inherit future tag updates.

## Key Terms & Definitions

| Term                     | Definition                                                                                         |
| ------------------------ | -------------------------------------------------------------------------------------------------- |
| `locals` block           | HCL block that defines named, module-scoped expressions not exposed to callers                     |
| `local.<name>`           | Syntax to reference a local value within the same module                                           |
| Common Tags Pattern      | A map-typed local holding all standard tags, referenced by every resource                          |
| Input Variable (`var.*`) | A value supplied externally; can be used inside a `locals` expression                              |
| Interpolation            | Embedding a reference (`local.*`, `var.*`) inside a string or map value                            |
| HCL                      | HashiCorp Configuration Language — the declarative language used to write Terraform configurations |

## Pitfalls & Best Practices

- **Use locals in moderation.** Overuse hides actual values and makes configurations harder to audit.
- **Group related locals together.** Multiple `locals` blocks are valid; grouping by purpose (e.g., tagging, naming, networking) improves readability.
- **Locals are not variables.** They cannot be overridden from the CLI or `.tfvars` — they are always computed from the module's own expressions.
- **Cross-referencing locals is valid.** A local value can reference another local (`local.service_name = local.team` is legal).
- **Quote tag keys only when needed.** Keys with spaces require quotes; alphanumeric keys do not, though quotes are acceptable either way.
- **Validate after changes.** Run `terraform fmt` → `terraform validate` → `terraform plan` before applying to catch syntax errors early.

---

## Common Exam Traps

- **Locals vs. variables:** Locals are **not** settable by the caller; input variables are. Confusing the two is a common exam error.
- **`local` vs. `locals`:** The block is declared with `locals` (plural); it is referenced with `local.<name>` (singular). Using `locals.<name>` in a reference is a syntax error.
- **Circular references:** A local value cannot reference itself, directly or indirectly — Terraform will throw a cycle error.
- **No changes ≠ no modification:** Refactoring from inline tags to `local.common_tags` produces `No changes.` in the plan. This is expected and correct — it does not mean the configuration was unmodified.
- **Multiple `locals` blocks:** Terraform merges them; duplicate names across blocks cause an error.
