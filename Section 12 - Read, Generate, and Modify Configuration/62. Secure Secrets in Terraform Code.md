# Secure Secrets in Terraform Code

## Overview

When working with Terraform it is very likely that sensitive values — passwords, access tokens, private keys, phone numbers — will appear in configurations. This lab covers four strategies, ordered from least to most robust, for keeping those secrets out of version control and out of plaintext CLI output.

---

## Concepts

- **Never store secrets in `.tf` files committed to source control.** Any value hardcoded in a `.tf` file is accessible to everyone with repository access, every machine that clones the repository, and every process that runs on those machines.
- **`sensitive = true`** on a variable or output suppresses CLI display only — the value is still stored in plaintext in the Terraform state file.
- **`TF_VAR_<name>` environment variables** supply variable values at runtime without ever touching a source file.
- **Secrets management systems** (e.g., HashiCorp Vault) centralize secret storage with access controls, audit logs, and token revocation — none of which are available when secrets are committed to code.

---

## Terraform Workflow

1. **Task 1** — Understand why plain-text secrets in `.tf` files are dangerous.
2. **Task 2** — Mark variables as `sensitive` to suppress CLI output.
3. **Task 3** — Remove default values from sensitive variables; supply them at runtime via `TF_VAR_` environment variables.
4. **Task 4** — Store secrets in HashiCorp Vault and retrieve them in Terraform using the Vault provider's data source.

---

## Task 1: Do Not Store Secrets in Plain Text

Committing secrets to source control creates the following risks:

| Risk                              | Consequence                                                                     |
| --------------------------------- | ------------------------------------------------------------------------------- |
| Repository access = secret access | Every developer, CI system, and contractor with repo access can read the secret |
| Every clone is a copy             | Removing the secret later does not remove it from git history                   |
| Process visibility                | Every process on every machine with a clone can read the secret                 |
| No audit trail                    | There is no way to know who accessed the secret or when                         |
| No revocation                     | Invalidating the secret requires rotating it everywhere it was distributed      |

**Rule:** Never put passwords, tokens, certificates, or other secrets in `.tf` files or any file tracked by version control.

## Task 2: Mark Variables as Sensitive

The first defensive measure is `sensitive = true`, which suppresses the value in Terraform CLI output.

### Configuration

```hcl
variable "phone_number" {
  type      = string
  sensitive = true
  default   = "867-5309"
}

output "phone_number" {
  value     = var.phone_number
  sensitive = true
}
```

```hcl
# Line-by-line Comments
variable "phone_number" {
  type      = string
  sensitive = true          # suppresses value in all CLI output; does NOT remove it from state
  default   = "867-5309"   # CAUTION: default value is still stored in plaintext in the .tf file
}

output "phone_number" {
  value     = var.phone_number  # references the sensitive variable
  sensitive = true              # required when output references a sensitive variable
}
```

**Code Walkthrough:**

- `sensitive = true` on a variable causes Terraform to display `(sensitive value)` wherever that variable's value would appear in plan or apply output.
- Any output that references a sensitive variable **must** also declare `sensitive = true` — Terraform enforces this at plan time and will fail if it is missing.
- **Limitation:** Having a `default` value here means the secret is still in the `.tf` file in plaintext. This approach alone is insufficient — Task 3 addresses this.

```bash
terraform apply
```

Terraform will apply and display `phone_number = <sensitive>` in the output section.

## Task 3: Environment Variables

Remove the `default` value from the sensitive variable so no plaintext secret exists in any source file. Supply the value at runtime via a `TF_VAR_` environment variable.

### Updated Variable (no default)

```hcl
variable "phone_number" {
  type      = string
  sensitive = true
}
```

```hcl
# Line-by-line Comments
variable "phone_number" {
  type      = string
  sensitive = true   # marks as sensitive; value must be supplied at runtime
                     # no default — the secret no longer exists anywhere in the codebase
}
```

### Set the Environment Variable

```bash
export TF_VAR_phone_number="867-5309"
```

```bash
# Line-by-line Comments
export TF_VAR_phone_number="867-5309"
# export            — makes the variable available to child processes (including Terraform)
# TF_VAR_          — prefix Terraform scans to populate input variable values
# phone_number      — exact name of the declared Terraform variable
# "867-5309"        — the sensitive value supplied at runtime, never written to any file
```

**Code Walkthrough:**

- With no `default` and no value in any `.tf` or `.tfvars` file, the secret only exists in the shell environment for the duration of that session.
- Terraform automatically reads `TF_VAR_<name>` at plan/apply time.
- This approach is particularly well-suited to CI/CD pipelines, where secrets are injected as environment variables by the pipeline system (e.g., GitHub Actions secrets, GitLab CI variables).

```bash
terraform apply   # Terraform picks up TF_VAR_phone_number automatically; no prompt required
```

> **HCP Terraform note:** If using HCP Terraform — HashiCorp Cloud Platform Terraform — as the remote backend, the `TF_VAR_` environment variable must be set in the HCP Terraform workspace (under Variables), not in the local shell, because runs execute remotely.

## Task 4: Inject Secrets Using HashiCorp Vault

For production environments, store secrets in a dedicated secrets management system. This lab demonstrates HashiCorp Vault using a local dev server.

### Prerequisites

- Download and install Vault from [vaultproject.io](https://www.vaultproject.io/docs/install).
- Ensure the `vault` binary is on your `$PATH`.

```bash
vault version   # verify installation
```

### Start a Vault Dev Server

```bash
vault server -dev
```

```bash
# Line-by-line Comments
vault server -dev
# vault server   — starts the Vault server process
# -dev           — runs in development mode: in-memory, pre-unsealed, no TLS
#                  WARNING: never use -dev in production
```

**Dev server startup output (example):**

```text
Unseal Key: 1zqTTWCHyAvEhTqOLurR2nQPeeoR1Sk2FMp95fRNEaU=
Root Token: s.Oi1tQPY98uwWQ6HOf9T7Elkg

Development mode should NOT be used in production installations!
```

### Configure and Authenticate

In a second terminal:

```bash
export VAULT_ADDR="http://127.0.0.1:8200"
vault login <root_token>
```

```bash
# Line-by-line Comments
export VAULT_ADDR="http://127.0.0.1:8200"
# VAULT_ADDR   — environment variable the Vault CLI uses to locate the server
# http://      — dev server does not support TLS; must use http, not https

vault login <root_token>
# vault login  — authenticates the CLI session to Vault
# <root_token> — the Root Token printed by `vault server -dev`
#                WARNING: use root tokens only for setup/testing, never for day-to-day access
```

### Write the Secret to Vault

```bash
vault kv put /secret/app phone_number=867-5309
```

```bash
# Line-by-line Comments
vault kv put         — writes a key/value secret to Vault's KV secrets engine
/secret/app          — the path in Vault where the secret is stored (mount: secret, path: app)
phone_number=867-5309 — key=value pair to store
```

### Terraform Vault Provider Configuration

```hcl
provider "vault" {
  address = "http://127.0.0.1:8200"
  token   = "<root_token>"
}
```

```hcl
# Line-by-line Comments
provider "vault" {
  address = "http://127.0.0.1:8200"  # URL of the Vault server
  token   = "<root_token>"           # authentication token
                                     # WARNING: root tokens must NOT be used in production;
                                     # use AppRole or another auth method instead
}
```

### Retrieve Secrets via Data Source

```hcl
data "vault_generic_secret" "phone_number" {
  path = "secret/app"
}
```

```hcl
# Line-by-line Comments
data "vault_generic_secret" "phone_number" {  # data source provided by the Vault provider
  path = "secret/app"                          # the Vault path where the secret was written
}
# result: data.vault_generic_secret.phone_number.data — a map of all key/value pairs at that path
```

### Output Block — Full Map

```hcl
output "phone_number" {
  value     = data.vault_generic_secret.phone_number
  sensitive = true
}
```

```hcl
# Line-by-line Comments
output "phone_number" {
  value     = data.vault_generic_secret.phone_number  # returns the entire data object (JSON map)
  sensitive = true   # required: Terraform automatically marks Vault-sourced data as sensitive
}
```

**Code Walkthrough:**

- Terraform recognizes that data sourced from Vault is likely sensitive and enforces `sensitive = true` on any output referencing it. Omitting this causes a plan error.
- The `value` above returns the entire JSON object, including metadata fields from Vault.

### Output Block — Specific Value Only

To retrieve only the `phone_number` string (not the full JSON object):

```hcl
output "phone_number" {
  value     = data.vault_generic_secret.phone_number.data["phone_number"]
  sensitive = true
}
```

```hcl
# Line-by-line Comments
output "phone_number" {
  value = data.vault_generic_secret.phone_number.data["phone_number"]
  # .data            — the map of key/value pairs returned by the vault_generic_secret data source
  # ["phone_number"] — selects the specific key from the map, returning only the string value
  sensitive = true
}
```

### Initialize and Apply

```bash
terraform init     # downloads the Vault provider
terraform apply    # retrieves secret from Vault; output displayed as <sensitive>
```

### Retrieve the Sensitive Output Explicitly

```bash
terraform output phone_number
```

Terraform displays the actual value when queried by name, even though it is marked sensitive.

## Comparison: Secret Management Strategies

| Strategy                          | Prevents plaintext in `.tf` files | Prevents plaintext in state | Audit trail | Access revocation |
| --------------------------------- | --------------------------------- | --------------------------- | ----------- | ----------------- |
| `sensitive = true` with `default` | No                                | No                          | No          | No                |
| `TF_VAR_` environment variable    | Yes                               | No                          | No          | No                |
| HashiCorp Vault                   | Yes                               | No (still in state)         | Yes         | Yes               |

> **Important:** No Terraform-native mechanism prevents sensitive values from being written to the state file. Protect the state file through remote backend access controls, encryption at rest, and least-privilege permissions regardless of which strategy is used.

## Key Terms & Definitions

| Term                       | Definition                                                                                                                                              |
| -------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **`sensitive = true`**     | Variable or output argument that suppresses value display in CLI output; does not affect state storage                                                  |
| **`TF_VAR_<name>`**        | Shell environment variable prefix Terraform reads to populate an input variable named `<name>`                                                          |
| **HashiCorp Vault**        | A secrets management tool for storing, accessing, and auditing access to sensitive values                                                               |
| **`vault server -dev`**    | Starts Vault in development mode — in-memory, pre-unsealed, no TLS; not for production use                                                              |
| **`vault_generic_secret`** | Terraform data source provided by the Vault provider for reading KV secrets from Vault                                                                  |
| **KV secrets engine**      | Vault's key/value store, mounted at `/secret` by default in dev mode                                                                                    |
| **AppRole**                | A Vault authentication method designed for machine-to-machine access; the recommended method for Terraform-to-Vault authentication                      |
| **Root Token**             | Vault's initial superuser credential; should only be used for initial setup, never for ongoing access                                                   |
| **HCP Terraform**          | HashiCorp Cloud Platform Terraform — managed service; workspace-level environment variables replace local `TF_VAR_` exports when using remote execution |

## Common Exam Traps

- **`sensitive = true` does not protect the state file.** Sensitive values are stored in plaintext in `terraform.tfstate`. This is a critical distinction the exam tests directly.
- **`sensitive = true` is required on outputs that reference sensitive variables.** Omitting it causes a plan error — Terraform does not silently permit it.
- **Environment variables are session-scoped.** If the shell session ends, the `TF_VAR_` variable is gone. In CI/CD environments, they must be injected by the pipeline system on every run.
- **In HCP Terraform, `TF_VAR_` must be set in the workspace.** Local shell exports have no effect when execution is remote.
- **Never use Vault root tokens in production.** The lab uses a root token for simplicity. The exam may present scenarios where the correct answer is to use AppRole or another appropriate auth method.
- **`vault server -dev` is not production-safe.** It stores everything in memory and loses all data on restart. The exam distinguishes between dev and production Vault deployment.
- **`data.vault_generic_secret.<name>.data` returns a map.** To extract a single value, index the map: `.data["key_name"]`. Returning the entire object includes Vault metadata fields.

### Updated Information (as of 2026-06-30)

- **`vault_generic_secret` data source is deprecated** in the HashiCorp Vault provider (hashicorp/vault). The current recommended replacement is `vault_kv_secret_v2` for KV v2 secrets engines or `vault_kv_secret` for KV v1. The path syntax also changes: KV v2 uses `secret/data/app` rather than `secret/app`. For the Terraform Associate exam, the conceptual pattern (use a data source to retrieve secrets from Vault) remains the same regardless of the specific data source name.
- All other commands and HCL constructs (`sensitive = true`, `TF_VAR_` prefix, `terraform init`, `terraform apply`, `terraform output`) remain current and valid in Terraform 1.x.
