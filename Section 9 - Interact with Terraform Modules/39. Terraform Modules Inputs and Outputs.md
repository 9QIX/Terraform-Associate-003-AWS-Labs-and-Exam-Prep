# Terraform Modules Inputs and Outputs

## Overview

Terraform modules become configurable and reusable through input variables and output values. Input variables define parameters that can be passed into modules, while output blocks define values that modules return to calling configurations. Proper organization of module files and clear definition of inputs and outputs are essential for creating maintainable, shareable modules.

## Concepts

### Module Interface Components

- **Input Variables**: Parameters passed into modules for configuration
- **Output Values**: Data returned from modules to calling configurations
- **Required Inputs**: Variables without default values that must be provided
- **Optional Inputs**: Variables with default values that can be overridden
- **Module Organization**: Standard file structure for maintainability

### Key Benefits

- Configurable and reusable module design
- Clear module interface definition
- Dependency inference between modules
- Standardized code organization
- Enhanced module documentation

## Terraform Workflow

### Module File Organization

**Standard Module Structure:**

```bash
modules/
└── server/
    ├── main.tf        # Core resource definitions
    ├── variables.tf   # Input variable declarations
    └── outputs.tf     # Output value definitions
```

**Code Walkthrough:**
The standard module structure separates concerns into three files: `main.tf` contains resource definitions, `variables.tf` declares all input parameters, and `outputs.tf` defines return values. This organization improves readability and maintainability.

### Module Core Configuration (main.tf)

```hcl
resource "aws_instance" "web" {
  ami                    = var.ami
  instance_type          = var.size
  subnet_id              = var.subnet_id
  vpc_security_group_ids = var.security_groups

  tags = {
    "Name"        = "Server from Module"
    "Environment" = "Training"
  }
}
```

**Line-by-line Comments:**

```hcl
# EC2 instance resource definition
# Use input variable for AMI
# Use input variable for instance type
# Use input variable for subnet placement
# Use input variable for security groups
# Static resource tags
```

**Code Walkthrough:**
The main configuration file contains only resource definitions. All configurable values reference input variables using `var.` syntax, making the module flexible and reusable across different contexts.

## Modules & Variables

### Input Variable Definitions (variables.tf)

```hcl
variable "ami" {}
variable "size" {
  default = "t3.micro"
}
variable "subnet_id" {}
variable "security_groups" {
  type = list(any)
}
```

**Line-by-line Comments:**

```hcl
# Required AMI variable (no default)
# Optional size variable with default value
# Required subnet ID variable
# Required security groups list variable
```

**Code Walkthrough:**
Variables without default values are required and must be provided when calling the module. Variables with default values are optional and can be overridden. Type constraints ensure proper data structure validation.

### Required vs Optional Inputs

**Making a Variable Required:**

```hcl
variable "size" {
  # default = "t3.micro"  # Commenting out makes it required
}
```

**Module Call with Required Inputs:**

```hcl
module "server" {
  source          = "./modules/server"
  ami             = data.aws_ami.ubuntu.id
  size            = "t3.micro"
  subnet_id       = aws_subnet.public_subnets["public_subnet_3"].id
  security_groups = [
    aws_security_group.vpc-ping.id,
    aws_security_group.ingress-ssh.id,
    aws_security_group.vpc-web.id
  ]
}
```

**Line-by-line Comments:**

```hcl
# Variable without default is required
# Module block calling server module
# Local path to module source
# Required AMI input
# Required size input (now required)
# Required subnet input
# Required security groups input
```

**Code Walkthrough:**
Removing or commenting out the default value converts an optional variable to required. The calling module must then provide this argument, or Terraform will produce a validation error.

### Module Outputs (outputs.tf)

```hcl
output "public_ip" {
  description = "IP Address of server built with Server Module"
  value       = aws_instance.web.public_ip
}

output "public_dns" {
  description = "DNS Address of server built with Server Module"
  value       = aws_instance.web.public_dns
}

output "size" {
  description = "Size of server built with Server Module"
  value       = aws_instance.web.instance_type
}
```

**Line-by-line Comments:**

```hcl
# Output block for public IP
# Descriptive documentation
# Reference resource attribute
# Output block for public DNS
# Descriptive documentation
# Reference resource attribute
# Output block for instance size
# Descriptive documentation
# Reference instance_type attribute
```

**Code Walkthrough:**
Output blocks define values that modules return to calling configurations. The output name (e.g., "size") can differ from the referenced attribute (e.g., "instance_type"). Descriptions document the purpose of each output.

### Referencing Module Outputs

**Root Module Output (main.tf):**

```hcl
output "public_ip" {
  value = module.server.public_ip
}

output "size" {
  value = module.server.size
}
```

**Line-by-line Comments:**

```hcl
# Root module output definition
# Reference module's public_ip output
# Root module output for size
# Reference module's size output
```

**Code Walkthrough:**
Module outputs are accessed using `module.<MODULE_NAME>.<OUTPUT_NAME>` syntax. The root module can expose module outputs directly or use them in expressions and resource configurations.

### Input and Output Comparison

| Component        | Location       | Purpose           | Syntax                         |
| ---------------- | -------------- | ----------------- | ------------------------------ |
| Input Variable   | `variables.tf` | Accept parameters | `var.ami`                      |
| Output Value     | `outputs.tf`   | Return values     | `aws_instance.web.public_ip`   |
| Module Call      | Root `main.tf` | Pass inputs       | `ami = data.aws_ami.ubuntu.id` |
| Output Reference | Root `main.tf` | Access outputs    | `module.server.public_ip`      |

## State Management

### Module Validation Workflow

```bash
terraform init
terraform validate
terraform plan
terraform apply
```

**Line-by-line Comments:**

```bash
# Initialize modules and providers
# Validate configuration syntax and requirements
# Preview infrastructure changes
# Apply configuration changes
```

**Code Walkthrough:**
After refactoring modules or changing variable requirements, run `terraform init` to reinitialize, then `terraform validate` to check for missing required arguments or syntax errors before planning and applying.

## Pitfalls & Best Practices

### Critical Considerations

- **File Organization**: Use standard structure (main.tf, variables.tf, outputs.tf)
- **Required vs Optional**: Clearly distinguish through default values
- **Output Descriptions**: Document all outputs for module consumers
- **Dependency Inference**: Outputs enable Terraform to determine resource dependencies

### Common Mistakes

- Not providing required module inputs
- Forgetting to run `terraform init` after module changes
- Missing output descriptions for module documentation
- Inconsistent naming between output names and referenced attributes
- Not exposing useful values as module outputs

### Best Practices

- Use descriptive variable and output names
- Provide meaningful descriptions for all variables and outputs
- Expose all potentially useful values as outputs
- Use type constraints for input variables
- Document module requirements and usage
- Keep module interface minimal but complete
- Test modules in isolation before integration

## Key Terms & Definitions

- **Input Variable**: Parameter that accepts values from calling configuration
- **Output Value**: Data returned by module to calling configuration
- **Required Input**: Variable without default value that must be provided
- **Optional Input**: Variable with default value that can be overridden
- **Module Interface**: Combination of input variables and output values
- **Module Output Reference**: Syntax `module.<name>.<output>` to access module outputs

## Common Exam Traps

- **Default Values**: Variables without defaults are required, with defaults are optional
- **Output Syntax**: Module outputs accessed via `module.<name>.<output>`
- **Variable Scope**: Module variables are separate from root module variables
- **Output Names**: Can differ from the attribute names they reference
- **Validation Errors**: Missing required inputs cause validation failures
- **Dependency Inference**: Outputs are necessary for proper module ordering
