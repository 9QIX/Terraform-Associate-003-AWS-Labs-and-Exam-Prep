# Terraform Modules

## Overview

Terraform modules are the primary method for packaging and reusing resource configurations. A module is simply any set of Terraform configuration files in a folder. Modules enable code organization, reusability across organizations, and consistency in infrastructure deployments. They are essential for complex configurations, team projects, and multi-repository codebases.

## Concepts

### Module Fundamentals

- **Definition**: Any set of Terraform configuration files in a folder
- **Root Module**: The working directory where Terraform commands are executed
- **Child Modules**: Modules called by the root module from other directories
- **Local Modules**: Modules stored in local directories or subdirectories
- **Remote Modules**: Modules stored in version control systems or registries

### Key Benefits

- Code organization and maintainability
- Reusability across teams and projects
- Consistency and best practice enforcement
- Simplified complex infrastructure management
- Encapsulation of related resources

## Terraform Workflow

### Creating a Local Module

**Directory Structure:**

```bash
/workspace/terraform/
├── main.tf
└── server/
    └── server.tf
```

**Module Configuration (server/server.tf):**

```hcl
variable "ami" {}
variable "size" {
  default = "t3.micro"
}
variable "subnet_id" {}
variable "security_groups" {
  type = list(any)
}

resource "aws_instance" "web" {
  ami                    = var.ami
  instance_type          = var.size
  subnet_id              = var.subnet_id
  vpc_security_group_ids = var.security_groups

  tags = {
    "Name"        = "Server from Module"
    "Environment" = "Training"
  }
}

output "public_ip" {
  value = aws_instance.web.public_ip
}

output "public_dns" {
  value = aws_instance.web.public_dns
}
```

**Line-by-line Comments:**

```hcl
# Required AMI variable with no default
# Instance size with default value
# Required subnet ID variable
# Security groups as list type

# EC2 instance resource definition
# Use variable for AMI selection
# Use variable for instance type
# Use variable for subnet placement
# Use variable for security group assignment

# Static tags for identification
# Environment classification tag

# Output public IP address
# Output public DNS name
```

**Code Walkthrough:**
The module defines input variables for customization, creates an EC2 instance using those variables, and exposes outputs for consumption by the calling module. Variables enable flexibility while maintaining consistent resource configuration.

### Calling a Module

**Root Module Configuration (main.tf):**

```hcl
module "server" {
  source          = "./server"
  ami             = data.aws_ami.ubuntu.id
  subnet_id       = aws_subnet.public_subnets["public_subnet_3"].id
  security_groups = [
    aws_security_group.vpc-ping.id,
    aws_security_group.ingress-ssh.id,
    aws_security_group.vpc-web.id
  ]
}

output "public_ip" {
  value = module.server.public_ip
}

output "public_dns" {
  value = module.server.public_dns
}
```

**Line-by-line Comments:**

```hcl
# Module block with unique name
# Local path to module source
# Pass AMI data source value
# Pass subnet resource reference
# Pass security group IDs as list

# Output module's public IP
# Reference module output value
# Output module's public DNS
# Reference module output value
```

**Code Walkthrough:**
The module block references the local module source and passes required variables. Module outputs are accessed using `module.<name>.<output>` syntax. The source path is relative to the root module directory.

### Module Installation and Usage

```bash
terraform init
terraform providers
terraform apply
```

**Line-by-line Comments:**

```bash
# Install modules and providers
# Show provider dependencies including modules
# Apply configuration with modules
```

**Code Walkthrough:**
`terraform init` downloads and installs modules, making them available for use. The `providers` command shows module dependencies. Any module changes require re-running `init`.

## Modules & Variables

### Module Reusability

```hcl
module "server_subnet_1" {
  source          = "./server"
  ami             = data.aws_ami.ubuntu.id
  subnet_id       = aws_subnet.public_subnets["public_subnet_1"].id
  security_groups = [
    aws_security_group.vpc-ping.id,
    aws_security_group.ingress-ssh.id,
    aws_security_group.vpc-web.id
  ]
}

output "public_ip_server_subnet_1" {
  value = module.server_subnet_1.public_ip
}
```

**Line-by-line Comments:**

```hcl
# Second module instance with different name
# Same source as first module
# Same AMI for consistency
# Different subnet for placement
# Same security groups

# Unique output name for second instance
# Reference second module's output
```

**Code Walkthrough:**
The same module source can be instantiated multiple times with different names and variable values. Each instance maintains separate state and resources while sharing the same configuration logic.

### Variable Types and Defaults

| Variable Type | Example                                           | Purpose                    |
| ------------- | ------------------------------------------------- | -------------------------- |
| Required      | `variable "ami" {}`                               | Must be provided by caller |
| Optional      | `variable "size" { default = "t3.micro" }`        | Has fallback value         |
| Typed         | `variable "security_groups" { type = list(any) }` | Enforces data structure    |

## Pitfalls & Best Practices

### Critical Considerations

- **Module Installation**: Always run `terraform init` after adding or updating modules
- **Unique Names**: Each module instance must have a unique name
- **Source Paths**: Use relative paths for local modules
- **Variable Validation**: Define appropriate variable types and constraints

### Common Mistakes

- Forgetting to run `terraform init` after module changes
- Using duplicate module names in the same configuration
- Not defining required variables in modules
- Hardcoding values that should be variables

### Best Practices

- Use descriptive module and variable names
- Provide default values for optional variables
- Document module inputs and outputs
- Keep modules focused on specific functionality
- Version control modules separately when shared
- Use consistent tagging strategies across modules

## Key Terms & Definitions

- **Root Module**: The working directory where Terraform commands are executed
- **Child Module**: A module called by another module
- **Module Source**: The location where module configuration files are stored
- **Module Block**: HCL block that calls and configures a module
- **Module Output**: Values exposed by a module for external consumption
- **Local Module**: Module stored in local filesystem relative to root module

## Common Exam Traps

- **Module Installation**: Modules require `terraform init` to be available
- **State References**: Module resources use `module.<name>.<resource>` format
- **Source Paths**: Local modules use relative paths starting with `./`
- **Variable Requirements**: Modules must declare all variables they use
- **Output Access**: Module outputs accessed via `module.<name>.<output>`
- **Working Directory**: Terraform only reads files in current directory without modules
