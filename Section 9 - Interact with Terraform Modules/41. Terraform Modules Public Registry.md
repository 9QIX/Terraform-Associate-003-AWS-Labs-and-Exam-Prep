# Terraform Modules - Public Registry

## Overview

HashiCorp maintains a public registry that enables consumption of Terraform modules created by the community. The Terraform Public Registry provides an index of publicly shared modules with support for versioning, searchable and filterable listings, and standardized documentation. Modules can be sourced using the registry address format `<NAMESPACE>/<NAME>/<PROVIDER>`.

## Concepts

### Public Registry Features

- **Community Contributions**: Modules shared by the Terraform community
- **Version Management**: Semantic versioning support for module releases
- **Search and Filter**: Easy discovery of modules by provider and use case
- **Standardized Documentation**: Automatic generation from module structure
- **Quality Standards**: Requirements ensure consistent module quality

### Key Benefits

- Rapid deployment of common infrastructure patterns
- Community-maintained and tested configurations
- Reduced development time through code reuse
- Standardized module interfaces and documentation
- Version control for stable deployments

## Terraform Workflow

### Consuming Registry Modules

**S3 Bucket Module:**

```hcl
module "s3-bucket" {
  source  = "terraform-aws-modules/s3-bucket/aws"
  version = "2.11.1"
}

output "s3_bucket_name" {
  value = module.s3-bucket.s3_bucket_bucket_domain_name
}
```

**Line-by-line Comments:**

```hcl
# Module block with registry source
# Registry format: namespace/name/provider
# Specific version constraint
# Output from module
# Reference module output attribute
```

**Code Walkthrough:**
Registry modules use the three-part naming convention where `terraform-aws-modules` is the namespace, `s3-bucket` is the module name, and `aws` is the provider. Version constraints ensure reproducible deployments by pinning to specific releases.

### VPC Module Implementation

```hcl
module "vpc" {
  source = "terraform-aws-modules/vpc/aws"

  name = "my-vpc-terraform"
  cidr = "10.0.0.0/16"

  azs             = ["us-east-1a", "us-east-1b", "us-east-1c"]
  private_subnets = ["10.0.1.0/24", "10.0.2.0/24", "10.0.3.0/24"]
  public_subnets  = ["10.0.101.0/24", "10.0.102.0/24", "10.0.103.0/24"]

  enable_nat_gateway = true
  enable_vpn_gateway = true

  tags = {
    Name        = "VPC from Module"
    Terraform   = "true"
    Environment = "dev"
  }
}
```

**Line-by-line Comments:**

```hcl
# VPC module from registry
# VPC name identifier
# CIDR block for VPC
# Availability zones for subnets
# Private subnet CIDR blocks
# Public subnet CIDR blocks
# Enable NAT gateway for private subnets
# Enable VPN gateway
# Resource tagging
```

**Code Walkthrough:**
The VPC module abstracts the complexity of creating a complete VPC infrastructure including subnets, route tables, gateways, and networking components. It replaces dozens of individual resource definitions with a single, configurable module block.

## Modules & Variables

### Registry Module Structure

**Required Components:**

- **main.tf**: Core resource definitions
- **variables.tf**: Input variable declarations
- **outputs.tf**: Output value definitions
- **README.md**: Module documentation
- **examples/**: Usage examples

### Module Publishing Requirements

| Requirement             | Description                         | Example                             |
| ----------------------- | ----------------------------------- | ----------------------------------- |
| **GitHub Repository**   | Must be public GitHub repo          | `github.com/user/terraform-aws-vpc` |
| **Naming Convention**   | `terraform-<PROVIDER>-<NAME>`       | `terraform-aws-ec2-instance`        |
| **Description**         | Repository description for registry | "Creates AWS VPC with subnets"      |
| **Standard Structure**  | main.tf, variables.tf, outputs.tf   | Standard module file layout         |
| **Semantic Versioning** | Release tags (x.y.z format)         | `v1.0.4`, `0.9.2`                   |

## Pitfalls & Best Practices

### Critical Considerations

- **Version Pinning**: Always specify version constraints for production
- **Module Evaluation**: Review module source code before use
- **Update Management**: Plan module version updates carefully
- **Documentation Review**: Understand module inputs and outputs

### Common Mistakes

- Using modules without version constraints
- Not reviewing module source code and requirements
- Assuming all registry modules follow best practices
- Not testing module updates in non-production environments
- Ignoring module dependencies and provider requirements

### Best Practices

- Pin module versions in production environments
- Review module documentation and examples
- Test modules in development before production use
- Contribute back to community modules when possible
- Follow publishing requirements for your own modules
- Use established, well-maintained modules when available

## Key Terms & Definitions

- **Public Registry**: HashiCorp's hosted registry of community Terraform modules
- **Registry Source**: Module source format `<NAMESPACE>/<NAME>/<PROVIDER>`
- **Semantic Versioning**: Version numbering scheme (major.minor.patch)
- **Module Namespace**: Organization or user identifier in registry
- **Release Tag**: Git tag marking a specific module version
- **Standard Structure**: Required file layout for registry modules

## Common Exam Traps

- **Source Format**: Registry modules use three-part naming `namespace/name/provider`
- **Version Requirements**: Registry modules support version constraints
- **Publishing Requirements**: Specific GitHub and naming requirements for publishing
- **Standard Structure**: Registry modules must follow main.tf/variables.tf/outputs.tf pattern
- **Public Repository**: Registry modules must be in public GitHub repositories
- **Semantic Versioning**: Release tags must follow semantic versioning format
