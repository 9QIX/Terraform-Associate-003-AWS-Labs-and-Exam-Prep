# Terraform Module Sources

## Overview

Terraform modules can be sourced from various locations including local directories, the Terraform Public Registry, version control systems like GitHub, HTTP URLs, and S3 buckets. This flexibility allows organizations to organize, share, and reuse Terraform configurations across different teams and projects while maintaining proper code organization and version control.

## Concepts

### Module Source Types
- **Local Sources**: Folders and subfolders within the filesystem
- **Remote Sources**: Terraform Registry, GitHub, HTTP URLs, S3 buckets
- **Version Control**: Git repositories with specific branch/tag references
- **Registry Sources**: Public and private module registries

### Key Benefits
- Code reusability across different environments
- Centralized module management and versioning
- Team collaboration through shared repositories
- Standardized infrastructure patterns
- Simplified maintenance and updates

## Terraform Workflow

### Local Module Organization

**Directory Structure:**
```bash
/workspace/terraform/
├── main.tf
└── modules/
    ├── server/
    │   └── server.tf
    └── web_server/
        └── server.tf
```

**Module Source Configuration:**
```hcl
module "server" {
  source          = "./modules/server"
  ami             = data.aws_ami.ubuntu.id
  subnet_id       = aws_subnet.public_subnets["public_subnet_3"].id
  security_groups = [
    aws_security_group.vpc-ping.id,
    aws_security_group.ingress-ssh.id,
    aws_security_group.vpc-web.id
  ]
}

module "server_subnet_1" {
  source          = "./modules/web_server"
  ami             = data.aws_ami.ubuntu.id
  key_name        = aws_key_pair.generated.key_name
  user            = "ubuntu"
  private_key     = tls_private_key.generated.private_key_pem
  subnet_id       = aws_subnet.public_subnets["public_subnet_1"].id
  security_groups = [
    aws_security_group.vpc-ping.id,
    aws_security_group.ingress-ssh.id,
    aws_security_group.vpc-web.id
  ]
}
```

**Line-by-line Comments:**
```hcl
# Basic server module with local source
# Relative path to module directory
# Pass AMI data source
# Pass subnet reference
# Pass security group list

# Enhanced web server module
# Different local module source
# Same AMI for consistency
# SSH key for provisioning
# Username for remote connection
# Private key for authentication
# Different subnet placement
# Same security groups
```

**Code Walkthrough:**
Local modules use relative paths starting with `./` to reference subdirectories. The `modules/` directory is a common convention for organizing local modules. Each module can have different variable requirements, as shown by the web_server module requiring additional authentication parameters.

### Public Registry Module

```hcl
module "autoscaling" {
  source  = "terraform-aws-modules/autoscaling/aws"
  version = "8.0.1"
 
  # Autoscaling group
  name = "myasg"
 
  vpc_zone_identifier = [
    aws_subnet.private_subnets["private_subnet_1"].id,
    aws_subnet.private_subnets["private_subnet_2"].id,
    aws_subnet.private_subnets["private_subnet_3"].id
  ]
  min_size         = 0
  max_size         = 1
  desired_capacity = 1
 
  # Launch template
  image_id      = data.aws_ami.ubuntu.id
  instance_type = "t3.micro"
  instance_name = "asg-instance"
 
  tags = {
    Name = "Web EC2 Server 2"
  }
}
```

**Line-by-line Comments:**
```hcl
# Module from public registry
# Registry source format: namespace/name/provider
# Specific version constraint

# Autoscaling group name
# Subnets for instance placement
# Minimum instances
# Maximum instances
# Desired instance count

# AMI for launch template
# Instance type specification
# Instance naming pattern
# Resource tags
```

**Code Walkthrough:**
Public registry modules use the format `<NAMESPACE>/<NAME>/<PROVIDER>`. Version constraints ensure reproducible deployments. The module abstracts complex autoscaling group and launch template configuration into simple parameters.

### GitHub Module Source

```hcl
module "autoscaling" {
  source = "github.com/terraform-aws-modules/terraform-aws-autoscaling?ref=v4.9.0"

  # Autoscaling group
  name = "myasg"

  vpc_zone_identifier = [
    aws_subnet.private_subnets["private_subnet_1"].id,
    aws_subnet.private_subnets["private_subnet_2"].id,
    aws_subnet.private_subnets["private_subnet_3"].id
  ]
  min_size         = 0
  max_size         = 1
  desired_capacity = 1

  # Launch template
  use_lt    = true
  create_lt = true

  image_id      = data.aws_ami.ubuntu.id
  instance_type = "t3.micro"

  tags_as_map = {
    Name = "Web EC2 Server 2"
  }
}
```

**Line-by-line Comments:**
```hcl
# GitHub source with version reference
# Repository URL with ref parameter

# Same configuration parameters
# Subnet placement specification
# Scaling parameters

# Launch template configuration
# Enable launch template usage
# Create new launch template
# Instance configuration
# Tag specification format
```

**Code Walkthrough:**
GitHub sources use the repository URL with an optional `?ref=` parameter for version control. The `ref` can specify branches, tags, or commit hashes. Configuration parameters may vary between registry and GitHub versions of the same module.

## Modules & Variables

### Enhanced Web Server Module

```hcl
variable "ami" {}
variable "size" {
  default = "t3.micro"
}
variable "subnet_id" {}
variable "user" {}
variable "security_groups" {
  type = list(any)
}
variable "key_name" {}
variable "private_key" {}

resource "aws_instance" "web" {
  ami                         = var.ami
  instance_type               = var.size
  subnet_id                   = var.subnet_id
  vpc_security_group_ids      = var.security_groups
  associate_public_ip_address = true
  key_name                    = var.key_name
  
  connection {
    user        = var.user
    private_key = var.private_key
    host        = self.public_ip
  }

  provisioner "remote-exec" {
    inline = [
      "sudo rm -rf /tmp",
      "sudo git clone https://github.com/hashicorp/demo-terraform-101 /tmp",
      "sudo sh /tmp/assets/setup-web.sh",
    ]
  }

  tags = {
    "Name"        = "Web Server from Module"
    "Environment" = "Training"
  }
}

output "public_ip" {
  value = aws_instance.web.public_ip
}

output "public_dns" {
  value = aws_instance.web.public_dns
}
```

**Line-by-line Comments:**
```hcl
# Required variables for module
# Optional variable with default
# Connection parameters for provisioning
# Security group list type

# EC2 instance with provisioning
# Enable public IP assignment
# SSH key for access
# Connection configuration
# Remote provisioning commands
# Web application installation
# Resource tagging
# Module outputs
```

**Code Walkthrough:**
The enhanced module includes provisioning capabilities through connection blocks and remote-exec provisioners. Additional variables enable SSH connectivity and application deployment, demonstrating module evolution and enhancement.

### Module Source Comparison

| Source Type | Format | Version Control | Use Case |
|-------------|--------|-----------------|----------|
| Local | `./modules/server` | File system | Development, testing |
| Registry | `terraform-aws-modules/autoscaling/aws` | Version tags | Production, shared modules |
| GitHub | `github.com/user/repo?ref=v1.0.0` | Git refs | Custom modules, forks |
| HTTP | `https://example.com/module.zip` | Manual | Legacy systems |
| S3 | `s3::https://bucket/module.zip` | Manual | Private storage |

## Pitfalls & Best Practices

### Critical Considerations
- **Initialization Required**: Always run `terraform init` after source changes
- **Version Pinning**: Use specific versions for production deployments
- **Source Validation**: Verify module sources before use
- **Credential Management**: Configure appropriate access for private sources

### Common Mistakes
- Forgetting to reinitialize after source changes
- Using unpinned versions in production
- Not validating third-party modules before use
- Mixing local and remote module patterns inconsistently

### Best Practices
- Use semantic versioning for module releases
- Organize local modules in dedicated directories
- Pin module versions in production environments
- Document module requirements and outputs
- Test modules in isolation before integration
- Use private registries for sensitive modules

## Key Terms & Definitions

- **Module Source**: Location where module configuration files are stored
- **Registry Source**: Module hosted on Terraform Registry with namespace/name/provider format
- **Local Source**: Module stored in local filesystem relative to root module
- **Remote Source**: Module stored in external systems like GitHub or S3
- **Version Constraint**: Specification of acceptable module versions
- **Module Registry**: Repository of shared Terraform modules

## Common Exam Traps

- **Initialization Requirement**: Source changes require `terraform init`
- **Version Syntax**: Registry modules use `version` argument, Git sources use `?ref=`
- **Path Format**: Local sources must start with `./` or `../`
- **Registry Format**: Public registry uses `namespace/name/provider` format
- **GitHub Recognition**: Terraform automatically recognizes `github.com` URLs
- **Credential Requirements**: Private sources need appropriate authentication
