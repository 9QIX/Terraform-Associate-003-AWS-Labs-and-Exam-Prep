# Terraform Module Versioning

## Overview

Terraform modules, like any code, require versioning to manage enhancements, new features, and bug fixes. Each module has associated versions following Semantic Versioning 2.0 conventions. Module versioning ensures compatibility between module code and Terraform core versions, preventing breaking changes and enabling stable deployments.

## Concepts

### Versioning Fundamentals

- **Semantic Versioning**: Modules follow SemVer 2.0 format (major.minor.patch)
- **Version Constraints**: Control which module versions are acceptable
- **Registry Support**: Versioning only available for registry-sourced modules
- **Compatibility**: Module versions must align with Terraform core versions
- **Release Management**: Versions tracked through Git tags and releases

### Key Benefits

- Prevents breaking changes from automatic updates
- Enables rollback to previous working versions
- Provides compatibility guarantees
- Supports gradual migration to newer versions
- Facilitates testing and validation workflows

## Terraform Workflow

### Basic Module Versioning

```hcl
module "vpc" {
  source  = "terraform-aws-modules/vpc/aws"
  version = "3.11.0"
}
```

**Line-by-line Comments:**

```hcl
# Module block with version specification
# Registry source format
# Exact version constraint
```

**Code Walkthrough:**
The version argument specifies exactly which module version to use. This prevents automatic updates that might introduce breaking changes. Terraform downloads and caches the specified version during initialization.

### Module Installation with Versioning

## Modules & Variables

### Version Compatibility Issues

**Older Module Version (1.73.0):**

```hcl
module "vpc" {
  source  = "terraform-aws-modules/vpc/aws"
  version = "1.73.0"

  name = "my-vpc-terraform"
  cidr = "10.0.0.0/16"
  # ... other configuration
}
```

**Validation Errors:**

```bash
terraform validate

Error: Error in function call
Call to function "map" failed: the "map" function was deprecated in Terraform v0.12 and is no longer available; use tomap({ ... }) syntax to write a literal map.
```

**Code Walkthrough:**
Older module versions may use deprecated Terraform syntax that's incompatible with current Terraform versions. This demonstrates why version compatibility is crucial for maintaining working configurations.

### Version Constraints

```hcl
module "vpc" {
  source  = "terraform-aws-modules/vpc/aws"
  version = ">3.0.0"

  name = "my-vpc-terraform"
  cidr = "10.0.0.0/16"

  azs             = ["us-east-1a", "us-east-1b", "us-east-1c"]
  private_subnets = ["10.0.1.0/24", "10.0.2.0/24", "10.0.3.0/24"]
  public_subnets  = ["10.0.101.0/24", "10.0.102.0/24", "10.0.103.0/24"]

  enable_nat_gateway = true
  enable_vpn_gateway = true

  tags = {
    Name        = "VPC from Module"
    Terraform   = "true"
    Environment = "dev"
  }
}
```

**Line-by-line Comments:**

```hcl
# Module with version constraint
# Accept any version greater than 3.0.0
# VPC configuration parameters
# Availability zones for subnets
# Private subnet CIDR blocks
# Public subnet CIDR blocks
# Enable NAT gateway
# Enable VPN gateway
# Resource tagging
```

**Code Walkthrough:**
Version constraints allow flexibility while maintaining compatibility. The `>3.0.0` constraint accepts any version above 3.0.0, automatically using the latest compatible version while avoiding older, incompatible releases.

### Version Constraint Operators

| Operator | Description            | Example                |
| -------- | ---------------------- | ---------------------- |
| `=`      | Exact version          | `version = "3.11.0"`   |
| `!=`     | Exclude version        | `version = "!=1.73.0"` |
| `>`      | Greater than           | `version = ">3.0.0"`   |
| `>=`     | Greater than or equal  | `version = ">=3.0.0"`  |
| `<`      | Less than              | `version = "<4.0.0"`   |
| `<=`     | Less than or equal     | `version = "<=3.11.0"` |
| `~>`     | Pessimistic constraint | `version = "~>3.11.0"` |

## State Management

### Version Constraint Resolution

```bash
terraform init

Initializing modules...
Downloading registry.terraform.io/terraform-aws-modules/vpc/aws 3.11.0 for vpc...

```

**Code Walkthrough:**
Terraform resolves version constraints by selecting the newest available version that satisfies the constraint. If no acceptable versions are cached, it downloads the newest compatible version from the registry.

## Pitfalls & Best Practices

### Critical Considerations

- **Registry Requirement**: Version constraints only work with registry modules
- **Local Module Limitations**: Local path modules don't support versioning
- **Compatibility Testing**: Always test module version changes in non-production
- **Constraint Strategy**: Balance flexibility with stability in version constraints

### Common Mistakes

- Using modules without version constraints in production
- Not testing compatibility when updating module versions
- Assuming all module versions work with current Terraform version
- Forgetting that local modules don't support versioning
- Not checking module changelogs before version updates

### Best Practices

- Always specify version constraints for registry modules
- Use exact versions for production deployments
- Test module updates in development environments first
- Review module changelogs before updating versions
- Use pessimistic constraints (`~>`) for automatic patch updates
- Pin major versions to avoid breaking changes
- Document version choices and update rationale

## Key Terms & Definitions

- **Semantic Versioning**: Version numbering scheme using major.minor.patch format
- **Version Constraint**: Expression defining acceptable module version range
- **Registry Module**: Module sourced from Terraform Registry with version support
- **Local Module**: Module sourced from local filesystem without version support
- **Pessimistic Constraint**: Version constraint allowing patch updates but not minor/major
- **Breaking Change**: Module update that requires configuration modifications

## Common Exam Traps

- **Registry Requirement**: Only registry modules support version constraints
- **Local Module Limitation**: Local path modules cannot be versioned
- **Constraint Syntax**: Version constraints use specific operator syntax
- **Compatibility Issues**: Older module versions may be incompatible with current Terraform
- **Automatic Updates**: Without constraints, modules may update automatically
- **Semantic Versioning**: Module versions must follow SemVer format
