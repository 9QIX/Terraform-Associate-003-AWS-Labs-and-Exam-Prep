# Terraform Module Scope

## Overview

Determining what infrastructure to include within a Terraform module is one of the most challenging aspects of module design. Modules should be opinionated and designed to do one thing well. If a module's function is hard to explain, it's probably too complex. Good modules raise the level of abstraction by describing new architectural concepts constructed from provider resource types.

## Concepts

### Module Design Principles

- **Single Purpose**: Modules should do one thing well
- **Abstraction Level**: Raise abstraction by describing architectural concepts
- **Encapsulation**: Group infrastructure that deploys together
- **Privilege Boundaries**: Respect organizational responsibility boundaries
- **Volatility Separation**: Separate long-lived from short-lived infrastructure

### Key Benefits

- Simplified infrastructure deployment
- Consistent architectural patterns
- Reduced complexity through abstraction
- Reusable infrastructure components
- Clear separation of concerns

## Terraform Workflow

### Module Resource Composition

**Autoscaling Module Example:**

```hcl
module "autoscaling" {
  source  = "terraform-aws-modules/autoscaling/aws"
  version = "8.0.1"

  # Autoscaling group
  name = "myasg"

  vpc_zone_identifier = [
    aws_subnet.private_subnets["private_subnet_1"].id,
    aws_subnet.private_subnets["private_subnet_2"].id,
    aws_subnet.private_subnets["private_subnet_3"].id
  ]
  min_size         = 0
  max_size         = 1
  desired_capacity = 1

  # Launch template
  image_id      = data.aws_ami.ubuntu.id
  instance_type = "t3.micro"

  tags = {
    Name = "Web EC2 Server 2"
  }
}
```

**Line-by-line Comments:**

```hcl
# Module from public registry
# Specific version constraint
# Autoscaling group name
# Subnet placement across AZs
# Minimum instance count
# Maximum instance count
# Desired instance count
# AMI for launch template
# Instance type specification
# Resource tagging
```

**Code Walkthrough:**
This module abstracts the complexity of creating an autoscaling group by combining multiple AWS resources (autoscaling group, launch template, schedules) into a single, configurable interface. It accepts 10 inputs but could accept up to 86 different configuration parameters.

## Modules & Variables

### Module Interface Design

**Root-Child Module Relationship:**

- **Root Module**: Passes arguments to child modules
- **Child Module**: Accepts inputs via variables, returns outputs
- **Black Box Abstraction**: Internal implementation hidden from consumers
- **Input Variables**: Map to module block arguments
- **Output Values**: Map to accessible module attributes

### Module Output Access

```bash
terraform console
> module.autoscaling
```

**Console Output Example:**

```json
{
  "autoscaling_group_arn" = "arn:aws:autoscaling:us-east-1:...",
  "autoscaling_group_max_size" = 1,
  "autoscaling_group_min_size" = 0,
  "launch_template_id" = "lt-0bdc46cf90ccdad50"
}
```

**Code Walkthrough:**
The console command reveals all outputs available from a module. These outputs are the only way to access information about resources created within the module, emphasizing the importance of comprehensive output design.

### Valid Module Output Reference

```hcl
output "asg_group_size" {
  value = module.autoscaling.autoscaling_group_max_size
}
```

**Line-by-line Comments:**

```hcl
# Output block in root module
# Reference module output using dot notation
```

**Code Walkthrough:**
Module outputs are accessed using `module.<name>.<output>` syntax. This is the only supported method for retrieving information about resources within child modules.

### Invalid Module Reference

```hcl
# Invalid - Direct resource access
output "asg_group_size" {
  value = module.autoscaling.aws_autoscaling_group.this[0].max_size
}
```

**Line-by-line Comments:**

```hcl
# Attempting direct resource access (invalid)
# Cannot access internal module resources directly
```

**Code Walkthrough:**
Direct access to resources within child modules is not supported. Even though the internal implementation uses `aws_autoscaling_group.this[0].max_size`, consumers must use the exposed output `autoscaling_group_max_size`.

### Module Scope Considerations

| Factor            | Description                                 | Impact                                  |
| ----------------- | ------------------------------------------- | --------------------------------------- |
| **Encapsulation** | Group infrastructure deployed together      | Easier deployment, harder to understand |
| **Privileges**    | Respect organizational boundaries           | Prevents duty segregation violations    |
| **Volatility**    | Separate static from dynamic infrastructure | Reduces risk to stateful resources      |

## Pitfalls & Best Practices

### Critical Considerations

- **80% Rule**: Design modules for common use cases, not edge cases
- **Narrow Scope**: Modules should not do multiple things
- **Output Generosity**: Expose all potentially useful information as outputs
- **Variable Selectivity**: Only expose commonly modified arguments as variables

### Common Mistakes

- Creating overly complex modules that do too many things
- Not providing enough outputs for module consumers
- Exposing too many variables initially
- Mixing infrastructure with different volatility levels
- Ignoring privilege boundaries in module design

### Best Practices

- Start simple and expand based on actual needs
- Group resources that are always deployed together
- Separate long-lived infrastructure from short-lived
- Provide comprehensive outputs even if not immediately needed
- Document module purpose and scope clearly
- Test modules in isolation before integration

## Key Terms & Definitions

- **Module Scope**: The boundaries of what infrastructure a module includes
- **Encapsulation**: Grouping related infrastructure within module boundaries
- **Privilege Boundary**: Organizational responsibility limits for infrastructure
- **Volatility**: How frequently infrastructure changes or gets redeployed
- **Black Box Abstraction**: Hiding internal implementation details from consumers
- **Output Interface**: The contract defining what information modules expose

## Common Exam Traps

- **Direct Resource Access**: Cannot access child module resources directly
- **Output Requirement**: Module outputs are the only way to get child module information
- **Scope Complexity**: Overly complex modules violate single-purpose principle
- **Variable Exposure**: Not all internal variables should be exposed as module inputs
- **Resource Grouping**: Modules should group infrastructure that deploys together
- **Privilege Violations**: Modules crossing organizational boundaries create security risks
