# Terraform Data Blocks and Local Variables

## Overview

This lesson covers two fundamental Terraform constructs: **Data Blocks** for querying external data sources and **Local Variables** for reducing repetitive expressions. Data blocks enable dynamic infrastructure configuration by retrieving information from APIs or cloud providers, while locals simplify code maintenance by centralizing reusable values and expressions.

---

## Concepts

### Data Blocks

Data sources in Terraform query or load data from APIs, cloud providers, or other Terraform workspaces. They enable:

- Dynamic configuration based on real-time infrastructure state
- Cross-workspace data sharing (Terraform Cloud/Enterprise)
- Flexible, region-agnostic deployments

### Local Variables

Locals assign names to expressions or values for reuse throughout configurations. They:

- Reduce code repetition
- Centralize expression logic for easier maintenance
- Improve readability by replacing complex expressions with descriptive names

## Terraform Workflow

### Data Block Structure

```hcl
data "<DATA_TYPE>" "<DATA_LOCAL_NAME>" {
  # Block body
  <IDENTIFIER> = <EXPRESSION>
}
```

**Line-by-line Comments:**

```hcl
data "<DATA_TYPE>" "<DATA_LOCAL_NAME>" {  # Declares data source with type and local reference name
  # Block body                             # Configuration specific to data source type
  <IDENTIFIER> = <EXPRESSION>              # Arguments/filters for querying data
}
```

**Code Walkthrough:**

- **data**: Top-level keyword declaring a data source
- **DATA_TYPE**: Provider-prefixed resource type (e.g., `aws_ami`, `aws_region`)
- **DATA_LOCAL_NAME**: Unique identifier for referencing this data source
- **Arguments**: Type-specific filters or parameters (consult provider documentation)

**Referencing Data Sources:**

```
data.<type>.<name>.<attribute>
```

### Locals Block Structure

```hcl
locals {
  <variable_name> = <value_or_expression>
  <variable_name> = <value_or_expression>
}
```

**Line-by-line Comments:**

```hcl
locals {                                   # Declares locals block (plural)
  <variable_name> = <value_or_expression>  # Individual local variable assignment
  <variable_name> = <value_or_expression>  # Multiple variables per block allowed
}
```

**Code Walkthrough:**

- **locals**: Block type (plural) containing one or more local variables
- Multiple `locals` blocks permitted in a configuration
- Locals can reference other locals from different blocks

**Referencing Local Variables:**

```
local.<variable_name>
```

Note: Use `local` (singular) when referencing, not `locals`.

## Providers & Resources

### Data Source: AWS Region

```hcl
data "aws_region" "current" {}
```

**Line-by-line Comments:**

```hcl
data "aws_region" "current" {}  # Queries current AWS region from provider credentials
```

**Code Walkthrough:**

- Retrieves the AWS region configured in the provider
- No arguments required
- Exports attributes like `name` and `description`

**Usage Example:**

```hcl
resource "aws_vpc" "vpc" {
  cidr_block = var.vpc_cidr

  tags = {
    Name        = var.vpc_name
    Environment = "demo_environment"
    Terraform   = "true"
    Region      = data.aws_region.current.name
  }
}
```

**Line-by-line Comments:**

```hcl
resource "aws_vpc" "vpc" {                  # VPC resource definition
  cidr_block = var.vpc_cidr                 # VPC CIDR from variable

  tags = {                                  # Resource tags
    Name        = var.vpc_name              # VPC name from variable
    Environment = "demo_environment"        # Static environment tag
    Terraform   = "true"                    # Terraform-managed flag
    Region      = data.aws_region.current.name  # Dynamic region from data source
  }
}
```

### Data Source: Availability Zones

```hcl
data "aws_availability_zones" "available" {}
```

**Line-by-line Comments:**

```hcl
data "aws_availability_zones" "available" {}  # Retrieves all AZs in current region
```

**Code Walkthrough:**

- Dynamically fetches availability zones for the current region
- Enables region-agnostic configurations
- Exports `names` attribute as a list

**Usage Example:**

```hcl
resource "aws_subnet" "private_subnets" {
  for_each          = var.private_subnets
  vpc_id            = aws_vpc.vpc.id
  cidr_block        = cidrsubnet(var.vpc_cidr, 8, each.value)
  availability_zone = tolist(data.aws_availability_zones.available.names)[each.value]

  tags = {
    Name      = each.key
    Terraform = "true"
  }
}
```

**Line-by-line Comments:**

```hcl
resource "aws_subnet" "private_subnets" {                                      # Subnet resource with for_each
  for_each          = var.private_subnets                                      # Iterate over subnet map
  vpc_id            = aws_vpc.vpc.id                                           # Reference parent VPC
  cidr_block        = cidrsubnet(var.vpc_cidr, 8, each.value)                  # Calculate subnet CIDR
  availability_zone = tolist(data.aws_availability_zones.available.names)[each.value]  # Dynamic AZ selection

  tags = {                                                                     # Subnet tags
    Name      = each.key                                                       # Subnet name from map key
    Terraform = "true"                                                         # Terraform-managed flag
  }
}
```

**Code Walkthrough:**

- `for_each` iterates over a map of subnets
- `cidrsubnet()` function calculates subnet CIDR blocks
- `tolist()` converts AZ names to list for indexing
- `[each.value]` selects AZ based on subnet index
- Configuration works across regions without modification

### Data Source: Ubuntu AMI

```hcl
data "aws_ami" "ubuntu_22_04" {
  most_recent = true

  filter {
    name   = "name"
    values = ["ubuntu/images/hvm-ssd/ubuntu-jammy-22.04-amd64-server-*"]
  }

  owners = ["099720109477"]
}
```

**Line-by-line Comments:**

```hcl
data "aws_ami" "ubuntu_22_04" {                                                # AMI data source
  most_recent = true                                                           # Return latest matching AMI

  filter {                                                                     # Filter criteria
    name   = "name"                                                            # Filter by AMI name
    values = ["ubuntu/images/hvm-ssd/ubuntu-jammy-22.04-amd64-server-*"]      # Ubuntu 22.04 pattern
  }

  owners = ["099720109477"]                                                    # Canonical's AWS account ID
}
```

**Code Walkthrough:**

- Queries AWS for the most recent Ubuntu 22.04 AMI
- `most_recent = true` ensures latest version is selected
- `filter` block narrows results by AMI name pattern
- `owners` restricts results to Canonical (official Ubuntu publisher)
- Wildcard `*` matches any build number
- Exports `id` attribute for use in EC2 instances

**Usage Example:**

```hcl
resource "aws_instance" "web_server" {
  ami                         = data.aws_ami.ubuntu_22_04.id
  instance_type               = "t3.micro"
  subnet_id                   = aws_subnet.public_subnets["public_subnet_1"].id
  security_groups             = [aws_security_group.vpc-ping.id]
  associate_public_ip_address = true

  tags = {
    Name = "Web EC2 Server"
  }
}
```

**Line-by-line Comments:**

```hcl
resource "aws_instance" "web_server" {                                         # EC2 instance resource
  ami                         = data.aws_ami.ubuntu_22_04.id                   # AMI from data source
  instance_type               = "t3.micro"                                     # Instance size
  subnet_id                   = aws_subnet.public_subnets["public_subnet_1"].id  # Subnet placement
  security_groups             = [aws_security_group.vpc-ping.id]               # Security group list
  associate_public_ip_address = true                                           # Enable public IP

  tags = {                                                                     # Instance tags
    Name = "Web EC2 Server"                                                    # Instance name
  }
}
```

## Modules & Variables

### Local Variables Implementation

```hcl
locals {
  team        = "API Management Dev"
  application = "Core API"
  server_name = "EC2-${var.environment}-API-${var.variables_sub_az}"
}
```

**Line-by-line Comments:**

```hcl
locals {                                                                       # Locals block declaration
  team        = "API Management Dev"                                           # Static team identifier
  application = "Core API"                                                     # Static application name
  server_name = "EC2-${var.environment}-API-${var.variables_sub_az}"          # Dynamic server naming convention
}
```

**Code Walkthrough:**

- `team` and `application` store static organizational metadata
- `server_name` uses string interpolation with `${}` syntax
- References two variables: `var.environment` and `var.variables_sub_az`
- Creates standardized naming pattern: `EC2-<env>-API-<az>`
- Example output: `EC2-dev-API-us-east-1a`

### Required Variable Definition

```hcl
variable "environment" {
  description = "Environment for deployment (e.g., dev, qa, prod)"
  type        = string
  default     = "dev"
}
```

**Line-by-line Comments:**

```hcl
variable "environment" {                                                       # Variable declaration
  description = "Environment for deployment (e.g., dev, qa, prod)"            # Human-readable description
  type        = string                                                         # Type constraint
  default     = "dev"                                                          # Default value
}
```

**Code Walkthrough:**

- Defines SDLC environment variable (dev, qa, prod)
- `type = string` enforces string values
- `default = "dev"` provides fallback value
- Used in locals for dynamic naming

### Using Locals in Resources

```hcl
resource "aws_instance" "web_server" {
  ami                         = data.aws_ami.ubuntu_22_04.id
  instance_type               = "t3.micro"
  subnet_id                   = aws_subnet.public_subnets["public_subnet_1"].id
  security_groups             = [aws_security_group.vpc-ping.id]
  associate_public_ip_address = true

  tags = {
    Name  = local.server_name
    Owner = local.team
    App   = local.application
  }
}
```

**Line-by-line Comments:**

```hcl
resource "aws_instance" "web_server" {                                         # EC2 instance definition
  ami                         = data.aws_ami.ubuntu_22_04.id                   # AMI from data source
  instance_type               = "t3.micro"                                     # Instance type
  subnet_id                   = aws_subnet.public_subnets["public_subnet_1"].id  # Subnet reference
  security_groups             = [aws_security_group.vpc-ping.id]               # Security groups
  associate_public_ip_address = true                                           # Public IP assignment

  tags = {                                                                     # Resource tags
    Name  = local.server_name                                                  # Dynamic name from locals
    Owner = local.team                                                         # Team from locals
    App   = local.application                                                  # Application from locals
  }
}
```

**Code Walkthrough:**

- Tags reference three local variables
- `local.server_name` evaluates to computed string
- `local.team` and `local.application` provide static values
- Centralizes tag management for consistency
- Changes to locals automatically propagate to all resources

## Pitfalls & Best Practices

### Data Blocks

**Best Practices:**

- Use data sources for dynamic, environment-agnostic configurations
- Leverage data sources to avoid hardcoding region-specific values (AMIs, AZs)
- Check provider documentation for available attributes
- Use filters to narrow query results and ensure correct data retrieval

**Common Pitfalls:**

- Forgetting to reference data source attributes (e.g., `.id`, `.name`)
- Incorrect syntax: `data.<type>.<name>.<attribute>` (not `data.<name>.<type>`)
- Not handling cases where data source returns no results
- Assuming data sources are static—they query on each `terraform plan`/`apply`

### Local Variables

**Best Practices:**

- Use locals for complex expressions referenced multiple times
- Place locals blocks near the top of configuration files
- Use descriptive names that indicate purpose
- Locals can reference other locals and variables
- Prefer locals over repeating the same expression across resources

**Common Pitfalls:**

- Confusing `locals` (block declaration) with `local` (reference syntax)
- Overusing locals for simple static values better suited as variables
- Creating circular dependencies between locals
- Not understanding that locals are computed during plan phase

## Key Terms & Definitions

| Term                     | Definition                                                                                       |
| ------------------------ | ------------------------------------------------------------------------------------------------ |
| **Data Block**           | Terraform construct that queries external data sources (APIs, cloud providers, other workspaces) |
| **Data Source**          | Provider-specific resource type prefixed with provider name (e.g., `aws_ami`, `aws_region`)      |
| **Data Local Name**      | Unique identifier for referencing a data source within a configuration                           |
| **Attribute**            | Exported value from a data source (e.g., `id`, `name`, `names`)                                  |
| **Locals Block**         | Container for one or more local variable definitions (plural: `locals`)                          |
| **Local Variable**       | Named expression or value reusable throughout a configuration (referenced as `local.<name>`)     |
| **String Interpolation** | Embedding expressions within strings using `${}` syntax                                          |
| **Filter**               | Criteria for narrowing data source query results                                                 |
| **most_recent**          | Data source argument that returns the latest matching result                                     |

## Common Exam Traps

1. **Data vs. Local Syntax Confusion**

   - Data blocks use `data.<type>.<name>.<attribute>`
   - Locals use `local.<name>` (singular, not `locals`)

2. **Data Source Timing**

   - Data sources query during `plan` phase, not at configuration parse time
   - Changes in external systems affect Terraform state

3. **Locals vs. Variables**

   - Locals are computed values, not user-configurable inputs
   - Variables accept external input; locals process internal logic
   - Cannot set locals via CLI or `.tfvars` files

4. **Multiple Locals Blocks**

   - Multiple `locals` blocks are valid
   - Later blocks can reference earlier locals
   - Avoid circular dependencies

5. **Data Source Attributes**

   - Must reference specific attributes (`.id`, `.name`)
   - Referencing the data source itself without an attribute causes errors
   - Check provider documentation for available attributes

6. **AMI Owner IDs**

   - Canonical (Ubuntu): `099720109477`
   - Amazon Linux: `137112412989`
   - Using incorrect owner IDs returns no results

7. **String Interpolation**
   - Use `${}` for expressions within strings
   - Example: `"EC2-${var.environment}-API"`
   - Not valid: `"EC2-$var.environment-API"`
