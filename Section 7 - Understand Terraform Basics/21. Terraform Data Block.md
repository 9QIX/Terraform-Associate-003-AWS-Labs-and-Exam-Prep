# Terraform Data Block

## Overview

Data blocks in Terraform query or retrieve data from APIs, cloud providers, or other Terraform workspaces. They enable dynamic infrastructure configuration by fetching real-time information such as AMI IDs, availability zones, or existing resource attributes. Data sources make configurations flexible, reusable across regions, and capable of connecting multiple workspaces in Terraform Cloud and Terraform Enterprise.

---

## Concepts

### Data Sources

Data sources allow Terraform to:

- Query external APIs or cloud provider services
- Retrieve information about existing infrastructure
- Share data between Terraform workspaces
- Create region-agnostic, portable configurations
- Dynamically populate resource arguments without hardcoding values

### Data Block Components

| Component              | Description                                                     |
| ---------------------- | --------------------------------------------------------------- |
| **Data Block Keyword** | `data` - Top-level keyword declaring a data source              |
| **Data Type**          | Provider-prefixed resource type (e.g., `aws_ami`, `aws_region`) |
| **Data Local Name**    | Unique identifier for referencing the data source               |
| **Data Arguments**     | Type-specific filters or parameters for querying                |

### Data Block Structure

```hcl
data "<DATA_TYPE>" "<DATA_LOCAL_NAME>" {
  # Block body
  <IDENTIFIER> = <EXPRESSION>
}
```

**Line-by-line Comments:**

```hcl
data "<DATA_TYPE>" "<DATA_LOCAL_NAME>" {  # Declares data source with type and unique name
  # Block body                             # Configuration specific to data source
  <IDENTIFIER> = <EXPRESSION>              # Arguments/filters for query
}
```

**Code Walkthrough:**

- **data**: Keyword indicating a data source declaration
- **DATA_TYPE**: Provider-specific data source type (must match provider documentation)
- **DATA_LOCAL_NAME**: Unique name within the configuration for referencing
- **Arguments**: Query parameters, filters, or identifiers specific to the data source type
- Data sources are read-only; they query but do not create or modify resources

### Referencing Data Sources

**Syntax:**

```
data.<type>.<name>.<attribute>
```

**Example:**

```hcl
data.aws_region.current.name
```

- `data` - Keyword for data source reference
- `aws_region` - Data source type
- `current` - Local name assigned in data block
- `name` - Exported attribute from the data source

### Task 1: Query Current AWS Region

```hcl
data "aws_region" "current" {}
```

**Line-by-line Comments:**

```hcl
data "aws_region" "current" {}  # Queries AWS provider for current region configuration
```

**Code Walkthrough:**

- No arguments required - uses provider credentials
- Automatically detects region from AWS provider configuration
- Exports attributes: `name`, `description`, `endpoint`
- Useful for creating region-aware resource naming and tagging

### Task 2: Use Data Source in VPC Tags

```hcl
resource "aws_vpc" "vpc" {
  cidr_block = var.vpc_cidr

  tags = {
    Name        = var.vpc_name
    Environment = "demo_environment"
    Terraform   = "true"
    Region      = data.aws_region.current.name
  }
}
```

**Line-by-line Comments:**

```hcl
resource "aws_vpc" "vpc" {                  # VPC resource definition
  cidr_block = var.vpc_cidr                 # VPC CIDR from variable

  tags = {                                  # Resource tags
    Name        = var.vpc_name              # VPC name from variable
    Environment = "demo_environment"        # Static environment tag
    Terraform   = "true"                    # Terraform-managed flag
    Region      = data.aws_region.current.name  # Dynamic region from data source
  }
}
```

**Code Walkthrough:**

- `Region` tag dynamically populated with current AWS region
- Reference format: `data.aws_region.current.name`
- Terraform queries AWS during plan phase
- Tag value automatically updates if provider region changes
- No hardcoded region values required

### Task 3: Availability Zones Data Source

```hcl
data "aws_availability_zones" "available" {}
```

**Line-by-line Comments:**

```hcl
data "aws_availability_zones" "available" {}  # Retrieves all AZs in current region
```

**Code Walkthrough:**

- Queries all availability zones in the provider's configured region
- No arguments needed for basic query
- Exports `names` attribute as a list of AZ names
- Enables region-agnostic subnet deployment
- Different regions have varying numbers of AZs (e.g., us-east-1 has 6, us-west-2 has 3)

### Task 4: Using AZ Data in Subnet Deployment

```hcl
resource "aws_subnet" "private_subnets" {
  for_each          = var.private_subnets
  vpc_id            = aws_vpc.vpc.id
  cidr_block        = cidrsubnet(var.vpc_cidr, 8, each.value)
  availability_zone = tolist(data.aws_availability_zones.available.names)[each.value]

  tags = {
    Name      = each.key
    Terraform = "true"
  }
}
```

**Line-by-line Comments:**

```hcl
resource "aws_subnet" "private_subnets" {                                      # Subnet resource with iteration
  for_each          = var.private_subnets                                      # Iterate over subnet map
  vpc_id            = aws_vpc.vpc.id                                           # Parent VPC reference
  cidr_block        = cidrsubnet(var.vpc_cidr, 8, each.value)                  # Calculate subnet CIDR
  availability_zone = tolist(data.aws_availability_zones.available.names)[each.value]  # Dynamic AZ selection

  tags = {                                                                     # Subnet tags
    Name      = each.key                                                       # Subnet name from map key
    Terraform = "true"                                                         # Terraform-managed flag
  }
}
```

**Code Walkthrough:**

- `for_each` iterates over a map of private subnets
- `cidrsubnet()` function calculates subnet CIDR blocks dynamically
- `tolist()` converts AZ names set to list for indexing
- `[each.value]` selects AZ based on subnet index
- Same configuration works across all AWS regions without modification
- Eliminates hardcoded AZ names

### AWS AMI Data Source

```hcl
data "aws_ami" "ubuntu_22_04" {
  most_recent = true

  filter {
    name   = "name"
    values = ["ubuntu/images/hvm-ssd/ubuntu-jammy-22.04-amd64-server-*"]
  }

  owners = ["099720109477"]
}
```

**Line-by-line Comments:**

```hcl
data "aws_ami" "ubuntu_22_04" {                                                # AMI data source declaration
  most_recent = true                                                           # Return latest matching AMI

  filter {                                                                     # Filter block for search criteria
    name   = "name"                                                            # Filter by AMI name
    values = ["ubuntu/images/hvm-ssd/ubuntu-jammy-22.04-amd64-server-*"]      # Ubuntu 22.04 name pattern
  }

  owners = ["099720109477"]                                                    # Canonical's AWS account ID
}
```

**Code Walkthrough:**

- `most_recent = true` ensures latest AMI version is selected
- `filter` block narrows search by AMI name pattern
- Wildcard `*` matches any build number or date suffix
- `owners` restricts results to Canonical (official Ubuntu publisher)
- Account ID `099720109477` is Canonical's verified AWS account
- Exports `id` attribute for use in EC2 instance resources
- AMI IDs vary by region; data source handles this automatically

**Common AMI Owner IDs:**
| Publisher | Owner ID | Description |
|-----------|----------|-------------|
| Canonical | 099720109477 | Ubuntu Linux |
| Amazon | 137112412989 | Amazon Linux |
| Red Hat | 309956199498 | Red Hat Enterprise Linux |

### Using AMI Data Source in EC2 Instance

```hcl
resource "aws_instance" "web_server" {
  ami                         = data.aws_ami.ubuntu_22_04.id
  instance_type               = "t3.micro"
  subnet_id                   = aws_subnet.public_subnets["public_subnet_1"].id
  security_groups             = [aws_security_group.vpc-ping.id]
  associate_public_ip_address = true

  tags = {
    Name = "Web EC2 Server"
  }
}
```

**Line-by-line Comments:**

```hcl
resource "aws_instance" "web_server" {                                         # EC2 instance resource
  ami                         = data.aws_ami.ubuntu_22_04.id                   # AMI from data source
  instance_type               = "t3.micro"                                     # Instance type
  subnet_id                   = aws_subnet.public_subnets["public_subnet_1"].id  # Subnet placement
  security_groups             = [aws_security_group.vpc-ping.id]               # Security groups
  associate_public_ip_address = true                                           # Enable public IP

  tags = {                                                                     # Instance tags
    Name = "Web EC2 Server"                                                    # Instance name
  }
}
```

**Code Walkthrough:**

- `ami` argument references data source: `data.aws_ami.ubuntu_22_04.id`
- Changing AMI filter in data source updates all instances referencing it
- Terraform detects AMI change and replaces instance (AMI is immutable)
- Centralized AMI management - update once, apply everywhere
- No hardcoded AMI IDs that vary by region

### Finding Data Sources in Terraform Registry

**Navigation Path:**

1. Visit [Terraform Registry](https://registry.terraform.io/)
2. Select provider (e.g., AWS, Azure, GCP)
3. Click "Documentation"
4. Expand "Data Sources" section in left sidebar
5. Select specific data source for details

**Provider-Level Data Sources:**

- Located under provider documentation (not resource-specific)
- Examples: `aws_region`, `aws_availability_zones`, `aws_billing_service_account`

**Resource-Specific Data Sources:**

- Grouped by AWS service category (EC2, EKS, VPC, etc.)
- Examples: `aws_ami`, `aws_instance`, `aws_eks_cluster`

**Data Source Documentation Includes:**

- Required and optional arguments
- Exported attributes
- Example usage
- Filter syntax and options

## Pitfalls & Best Practices

### Best Practices

**Use Data Sources for Dynamic Configuration:**

- Avoid hardcoding region-specific values (AMI IDs, AZ names)
- Query existing infrastructure instead of duplicating configuration
- Enable multi-region deployments with identical code

**Centralize Data Lookups:**

- Define data sources once, reference multiple times
- Update AMI versions in one place to affect all instances
- Use descriptive local names for clarity

**Leverage Filters Effectively:**

- Use `most_recent = true` for AMI lookups to get latest versions
- Apply multiple filters to narrow results
- Verify owner IDs to ensure trusted sources

**Check Provider Documentation:**

- Review exported attributes for each data source
- Understand query behavior and limitations
- Note any required arguments or authentication

### Common Pitfalls

**Incorrect Reference Syntax:**

- ❌ `data.current.aws_region.name` (wrong order)
- ✅ `data.aws_region.current.name` (correct)

**Missing Attribute Reference:**

- ❌ `ami = data.aws_ami.ubuntu` (references entire data source)
- ✅ `ami = data.aws_ami.ubuntu.id` (references specific attribute)

**Assuming Static Data:**

- Data sources query on every `terraform plan` and `terraform apply`
- External changes affect Terraform state
- AMI IDs, AZ availability can change over time

**Forgetting Owner IDs:**

- AMI lookups without `owners` may return unexpected results
- Public AMIs from untrusted sources pose security risks
- Always specify verified owner IDs

**Hardcoding Region-Specific Values:**

- AMI IDs differ across regions
- AZ names vary by region (us-east-1a exists, but not in all regions)
- Use data sources for portability

**Not Handling Empty Results:**

- Data source queries can return no results
- Filters may be too restrictive
- Test data sources with `terraform plan` before applying

## Key Terms & Definitions

| Term                           | Definition                                                                                   |
| ------------------------------ | -------------------------------------------------------------------------------------------- |
| **Data Block**                 | Terraform construct that queries external data sources without creating resources            |
| **Data Source**                | Provider-specific query mechanism for retrieving information (e.g., `aws_ami`, `aws_region`) |
| **Data Type**                  | Provider-prefixed identifier for the kind of data to query (first argument in data block)    |
| **Data Local Name**            | Unique identifier assigned to a data source for referencing within configuration             |
| **Exported Attribute**         | Read-only value returned by a data source (e.g., `id`, `name`, `names`)                      |
| **Filter**                     | Query parameter that narrows data source results based on criteria                           |
| **most_recent**                | Boolean argument that returns the latest matching result (common in AMI lookups)             |
| **Owner ID**                   | AWS account identifier used to restrict AMI searches to trusted publishers                   |
| **Availability Zone (AZ)**     | Isolated location within an AWS region for high-availability deployments                     |
| **AMI (Amazon Machine Image)** | Pre-configured virtual machine image used to launch EC2 instances                            |

## Common Exam Traps

1. **Data Source Reference Syntax**

   - Format: `data.<type>.<name>.<attribute>`
   - Must include all four components
   - Order matters: data → type → name → attribute

2. **Data vs. Resource Blocks**

   - Data blocks query existing resources (read-only)
   - Resource blocks create/manage infrastructure (read-write)
   - Cannot use `data` keyword to create resources

3. **Attribute Requirements**

   - Must reference specific attributes (`.id`, `.name`)
   - Referencing data source without attribute causes errors
   - Check provider documentation for available attributes

4. **Data Source Timing**

   - Data sources query during plan phase
   - Results stored in state file
   - External changes detected on subsequent runs

5. **Multiple Data Blocks**

   - Can have multiple data blocks of the same type
   - Each must have unique local name
   - Local names must be unique within configuration

6. **Filter Wildcards**

   - Use `*` for pattern matching in AMI names
   - Example: `ubuntu-*-22.04-*` matches various build numbers
   - Overly broad filters may return unexpected results

7. **Region Portability**

   - AMI IDs are region-specific
   - Data sources enable cross-region portability
   - Same configuration works in different regions without modification

8. **Owner ID Verification**

   - Canonical (Ubuntu): `099720109477`
   - Amazon Linux: `137112412989`
   - Incorrect owner IDs return no results or untrusted AMIs

9. **Data Source Updates**

   - Changing data source filters triggers resource updates
   - AMI changes force EC2 instance replacement
   - Review plan output carefully before applying

10. **Empty Result Handling**
    - Data sources can return zero results
    - Terraform errors if required attribute is missing
    - Test filters with `terraform plan` first
