# Terraform Module Block

## Overview

Modules in Terraform combine frequently used resources into reusable containers, enabling code reuse and reducing duplication. A module is a collection of `.tf` files in a directory that can be called by a parent (root) module. Modules can be sourced locally or remotely from locations like the Terraform Registry, GitHub, or other version control systems. The module block defines how to call and configure these reusable components.

---

## Concepts

### Modules

**Definition:**
A module is a container for multiple resources used together. Modules enable:

- Code reusability across projects
- Abstraction of complex infrastructure patterns
- Standardization of infrastructure components
- Reduced code duplication
- Simplified maintenance and updates

### Module Hierarchy

| Term              | Description                                                                   |
| ----------------- | ----------------------------------------------------------------------------- |
| **Root Module**   | The main working directory containing `.tf` files where Terraform is executed |
| **Parent Module** | Any module that calls another module (root module is the top-level parent)    |
| **Child Module**  | A module called by another module                                             |

### Module Sources

Modules can be sourced from:

- **Local paths** - Directories on the local filesystem
- **Terraform Registry** - Public or private module registry
- **GitHub/GitLab** - Version control repositories
- **HTTP URLs** - Direct download locations
- **S3 buckets** - Cloud storage locations

### Module Structure

**Common Directory Layout:**

```
project/
├── main.tf
├── variables.tf
├── outputs.tf
└── modules/
    ├── vpc/
    │   ├── main.tf
    │   ├── variables.tf
    │   └── outputs.tf
    └── subnet/
        ├── main.tf
        ├── variables.tf
        └── outputs.tf
```

**Module Components:**

- `main.tf` - Primary resource definitions
- `variables.tf` - Input variable declarations
- `outputs.tf` - Output value definitions (exported data)

### Module Block Structure

```hcl
module "<MODULE_NAME>" {
  # Block body
  source = <MODULE_SOURCE>
  <INPUT_NAME> = <VALUE>  # Inputs
  <INPUT_NAME> = <VALUE>  # Inputs
}
```

**Line-by-line Comments:**

```hcl
module "<MODULE_NAME>" {        # Module block with unique name
  # Block body                  # Module configuration
  source = <MODULE_SOURCE>      # Required: module location
  <INPUT_NAME> = <VALUE>        # Optional: input variables
  <INPUT_NAME> = <VALUE>        # Optional: additional inputs
}
```

**Code Walkthrough:**

- `module` - Keyword declaring a module block
- `<MODULE_NAME>` - Unique identifier for this module instance
- `source` - Required argument specifying module location
- Input arguments - Variables passed to the child module
- Each module block must have a unique name within the configuration

## Terraform Workflow

### Task 1: Create Module Block for Remote Module

**Add Module Block to `main.tf`:**

```hcl
module "subnet_addrs" {
  source  = "hashicorp/subnets/cidr"
  version = "1.0.0"

  base_cidr_block = "10.0.0.0/22"
  networks = [
    {
      name     = "module_network_a"
      new_bits = 2
    },
    {
      name     = "module_network_b"
      new_bits = 2
    },
  ]
}

output "subnet_addrs" {
  value = module.subnet_addrs.network_cidr_blocks
}
```

**Line-by-line Comments:**

```hcl
module "subnet_addrs" {                          # Module block named "subnet_addrs"
  source  = "hashicorp/subnets/cidr"             # Registry module source
  version = "1.0.0"                              # Module version constraint

  base_cidr_block = "10.0.0.0/22"                # Input: base CIDR block
  networks = [                                   # Input: list of network definitions
    {                                            # First network configuration
      name     = "module_network_a"              # Network name
      new_bits = 2                               # Additional bits for subnet mask
    },
    {                                            # Second network configuration
      name     = "module_network_b"              # Network name
      new_bits = 2                               # Additional bits for subnet mask
    },
  ]
}

output "subnet_addrs" {                          # Output block to display results
  value = module.subnet_addrs.network_cidr_blocks  # Reference module output
}
```

**Code Walkthrough:**

- **Module Source**: `hashicorp/subnets/cidr` references Terraform Registry
  - Format: `<NAMESPACE>/<NAME>/<PROVIDER>`
  - Namespace: `hashicorp` (publisher)
  - Name: `subnets` (module name)
  - Provider: `cidr` (provider type)
- **Version**: `1.0.0` pins to specific module version
- **base_cidr_block**: Starting CIDR block to subdivide
- **networks**: List of network configurations
  - `new_bits = 2` adds 2 bits to subnet mask (e.g., /22 becomes /24)
- **Output**: Exports module results to CLI
  - References module output using `module.<name>.<output_attribute>`
- **Module Purpose**: Calculates subnet CIDR blocks without creating resources

**Line-by-line Comments:**

```bash
terraform init  # Initialize working directory and download modules
```

**Code Walkthrough:**

- `terraform init` downloads modules specified in configuration
- Modules stored in `.terraform/modules/` directory
- Each module gets subdirectory named after module block name
- Module download occurs before provider plugin installation

**Module Storage Location:**

```
.terraform/
└── modules/
    └── subnet_addrs/
        ├── main.tf
        ├── variables.tf
        └── outputs.tf
```

```bash

```

**Expected Output:**

```text

Outputs:

subnet_addrs = tomap({
  "module_network_a" = "10.0.0.0/24"
  "module_network_b" = "10.0.1.0/24"
})
```

**Line-by-line Comments:**

```bash
terraform apply -auto-approve  # Apply configuration without confirmation prompt
```

**Code Walkthrough:**

- Module performs calculations only (no resource creation)
- Input: `10.0.0.0/22` (1024 IP addresses)
- `new_bits = 2` adds 2 bits to mask: /22 → /24
- Output: Two /24 subnets (256 IPs each)
  - `module_network_a`: `10.0.0.0/24`
  - `module_network_b`: `10.0.1.0/24`
- Useful for subnet planning before resource deployment
- Module outputs can be referenced by other resources

## Modules & Variables

### Module Input Variables

**Passing Variables to Modules:**

```hcl
module "website_s3_bucket" {
  source = "./modules/aws-s3-static-website-bucket"

  bucket_name = var.s3_bucket_name
  aws_region  = "us-east-1"

  tags = {
    Terraform   = "true"
    Environment = "certification"
  }
}
```

**Line-by-line Comments:**

```hcl
module "website_s3_bucket" {                           # Module block declaration
  source = "./modules/aws-s3-static-website-bucket"    # Local module path

  bucket_name = var.s3_bucket_name                     # Variable from parent module
  aws_region  = "us-east-1"                            # Static string value

  tags = {                                             # Map input
    Terraform   = "true"                               # Tag key-value pair
    Environment = "certification"                      # Tag key-value pair
  }
}
```

**Code Walkthrough:**

- **Local Source**: `./modules/` indicates relative path
- **Variable Reference**: `var.s3_bucket_name` passes parent variable to child
- **Static Values**: Hardcoded strings like `"us-east-1"`
- **Complex Types**: Maps and lists can be passed as inputs
- **Flexibility**: Use variables for reusability, static values for constants

### Module Outputs

**Referencing Module Outputs:**

```hcl
# In child module (outputs.tf)
output "network_cidr_blocks" {
  value = local.calculated_subnets
}

# In parent module
output "subnet_addrs" {
  value = module.subnet_addrs.network_cidr_blocks
}
```

**Line-by-line Comments:**

```hcl
# Child module output
output "network_cidr_blocks" {              # Output declaration in child module
  value = local.calculated_subnets          # Value to export
}

# Parent module reference
output "subnet_addrs" {                     # Output in parent module
  value = module.subnet_addrs.network_cidr_blocks  # Reference child output
}
```

**Code Walkthrough:**

- Child modules export data via `output` blocks
- Parent modules reference outputs: `module.<name>.<output_name>`
- Outputs enable data flow between modules
- Can be used as inputs to other resources or modules

### Module Versioning

**Version Constraints:**

```hcl
module "example" {
  source  = "hashicorp/subnets/cidr"
  version = "1.0.0"      # Exact version
}

module "example" {
  source  = "hashicorp/subnets/cidr"
  version = ">= 1.0.0"   # Minimum version
}

module "example" {
  source  = "hashicorp/subnets/cidr"
  version = "~> 1.0"     # Pessimistic constraint
}
```

**Line-by-line Comments:**

```hcl
version = "1.0.0"       # Exact version only
version = ">= 1.0.0"    # Version 1.0.0 or newer
version = "~> 1.0"      # Any 1.x version (not 2.0)
```

**Code Walkthrough:**

- `version` argument only applies to registry modules
- Local modules do not support version constraints
- Use semantic versioning: MAJOR.MINOR.PATCH
- Pessimistic constraint `~>` allows minor updates, blocks major changes

## Pitfalls & Best Practices

### Best Practices

**Design Reusable Modules:**

- Use variables for all configurable values
- Avoid hardcoding region-specific or environment-specific values
- Design for multiple use cases, not single implementations
- Document module inputs and outputs clearly

**Module Organization:**

- Store local modules in `modules/` directory
- Name modules descriptively (e.g., `vpc`, `subnet`, `ec2-instance`)
- Include `README.md` in each module explaining purpose and usage
- Keep modules focused on single responsibility

**Version Management:**

- Always specify `version` for registry modules
- Use pessimistic constraints (`~>`) for stability
- Test module updates in non-production environments
- Pin to specific versions in production

**Input Validation:**

- Use variable validation rules in modules
- Provide sensible default values where appropriate
- Document required vs. optional inputs
- Use type constraints for input variables

**Output Strategy:**

- Export all data that consumers might need
- Use descriptive output names
- Document output values and their purpose
- Avoid exposing sensitive data in outputs

### Common Pitfalls

**Missing `terraform init` After Module Changes:**

- Adding or modifying module blocks requires re-initialization
- Terraform prompts to run `terraform init` if modules changed
- Always run `terraform init` after module updates

**Incorrect Module Source Paths:**

- Local paths must be relative (`./modules/vpc`) or absolute
- Registry format: `<NAMESPACE>/<NAME>/<PROVIDER>`
- Missing `./` prefix causes Terraform to search registry

**Circular Dependencies:**

- Module A cannot depend on Module B if B depends on A
- Causes initialization failures
- Restructure module relationships to eliminate cycles

**Hardcoded Values in Modules:**

- Reduces reusability across environments
- Use variables instead of hardcoded values
- Makes modules inflexible and difficult to maintain

**Not Using Module Outputs:**

- Modules should export useful data via outputs
- Parent modules reference outputs to pass data between modules
- Missing outputs break data flow between modules

**Version Constraint Issues:**

- Not specifying versions leads to unexpected updates
- Overly restrictive versions prevent bug fixes
- Test version updates before applying to production

**Confusing Module Names:**

- Non-descriptive names make code hard to understand
- Use clear, purpose-driven names
- Follow naming conventions consistently

## Key Terms & Definitions

| Term                | Definition                                                                                 |
| ------------------- | ------------------------------------------------------------------------------------------ |
| **Module**          | Container for multiple resources used together; a collection of `.tf` files in a directory |
| **Root Module**     | The main working directory where Terraform commands are executed                           |
| **Parent Module**   | A module that calls other modules (root module is the top-level parent)                    |
| **Child Module**    | A module called by another module                                                          |
| **Module Block**    | HCL block that calls and configures a module using the `module` keyword                    |
| **Module Source**   | Location where module code is stored (local path, registry, Git, etc.)                     |
| **Module Input**    | Variable passed from parent module to child module                                         |
| **Module Output**   | Value exported from child module to parent module                                          |
| **Module Registry** | Repository of publicly or privately shared modules (e.g., Terraform Registry)              |
| **Local Module**    | Module stored in local filesystem, referenced with relative or absolute path               |
| **Remote Module**   | Module stored externally (registry, Git, HTTP, etc.)                                       |
| **Module Version**  | Specific release of a module, following semantic versioning                                |

## Common Exam Traps

1. **Module Initialization Requirement**

   - Must run `terraform init` after adding or changing modules
   - Modules downloaded to `.terraform/modules/` directory
   - Forgetting initialization causes errors on plan/apply

2. **Module Source Syntax**

   - Local: `./modules/vpc` or `../shared/vpc`
   - Registry: `hashicorp/subnets/cidr`
   - Git: `git::https://github.com/user/repo.git`
   - Missing `./` for local paths searches registry

3. **Module Output References**

   - Syntax: `module.<module_name>.<output_name>`
   - Cannot reference module resources directly
   - Must use module outputs to access data

4. **Version Constraints**

   - Only apply to registry modules
   - Local modules ignore `version` argument
   - Use semantic versioning format

5. **Module Block Uniqueness**

   - Each module block must have unique name
   - Can call same module multiple times with different names
   - Duplicate names cause configuration errors

6. **Required Arguments**

   - `source` is the only required argument
   - All other arguments are module-specific inputs
   - Check module documentation for required inputs

7. **Module vs. Resource Blocks**

   - Modules call reusable code containers
   - Resources create infrastructure components
   - Different purposes, different syntax

8. **Data Flow Between Modules**

   - Parent passes inputs to child via module block arguments
   - Child exports data to parent via output blocks
   - Cannot directly access child module resources

9. **Module Calculation vs. Resource Creation**

   - Some modules only perform calculations (like subnet CIDR module)
   - Others create actual infrastructure resources
   - Check module documentation for behavior

10. **Module Naming Conventions**
    - Use descriptive, lowercase names with underscores
    - Avoid special characters except underscore and hyphen
    - Names should indicate module purpose

## Updated Information (as of 2025-01-XX)

### Terraform Registry Module Source Format

- **Lab demonstrates**: `hashicorp/subnets/cidr` format
- **Current format**: Same format still valid
- **Alternative sources**:
  - Private registry: `app.terraform.io/<ORG>/<NAME>/<PROVIDER>`
  - GitHub: `github.com/<USER>/<REPO>`
  - Git with subdirectory: `git::https://github.com/user/repo.git//modules/vpc`

### Module Versioning Best Practices

- **Lab uses**: Exact version `1.0.0`
- **Current recommendation**: Use pessimistic constraints for flexibility
  ```hcl
  module "subnet_addrs" {
    source  = "hashicorp/subnets/cidr"
    version = "~> 1.0"  # Allows 1.x updates, blocks 2.0
  }
  ```
- Balances stability with bug fixes and security patches

### Module Registry URL

- **Current URL**: https://registry.terraform.io/
- Browse modules by provider (AWS, Azure, GCP, etc.)
- View module documentation, inputs, outputs, and examples

### Module Testing Framework

- **New in Terraform 1.6+**: Built-in testing framework
- Create `tests/` directory with `.tftest.hcl` files
- Run `terraform test` to validate module behavior
- Not covered in lab but available in modern Terraform

### Module Composition Patterns

- **Current best practice**: Compose small, focused modules
- Avoid monolithic modules that do too much
- Use module composition to build complex infrastructure
- Example: VPC module + Subnet module + Security Group module

### Output Block Syntax

- Lab demonstrates basic output syntax (still current)
- Modern Terraform supports output descriptions and sensitive flags:
  ```hcl
  output "subnet_addrs" {
    description = "Calculated subnet CIDR blocks"
    value       = module.subnet_addrs.network_cidr_blocks
    sensitive   = false
  }
  ```

### Module Documentation

- **Current practice**: Include `README.md` in module root
- Document inputs, outputs, requirements, and examples
- Use `terraform-docs` tool to auto-generate documentation
- Improves module discoverability and usability
