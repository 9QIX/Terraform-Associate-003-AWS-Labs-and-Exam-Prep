# Terraform Basics

## Overview

This lesson covers the fundamental Terraform CLI commands and workflow that form the foundation of Infrastructure as Code operations. Understanding these basic commands is essential for the Terraform Associate 003 exam and daily Terraform usage.

## Concepts

- **CLI-Based Tool**: All Terraform interactions occur through command-line interface
- **Local Execution**: Terraform runs on the local machine, not as a service
- **Provider Ecosystem**: Extensive library of providers for cloud services and platforms
- **Module Registry**: Public and private repositories for reusable infrastructure components
- **Enterprise Solutions**: Terraform Cloud and Terraform Enterprise for team collaboration

## Terraform Workflow

### Core Commands Overview

| Command              | Purpose                                             | Safe to Run Multiple Times      |
| -------------------- | --------------------------------------------------- | ------------------------------- |
| `terraform init`     | Initialize working directory and download providers | ✅ Yes                          |
| `terraform validate` | Validate configuration syntax and consistency       | ✅ Yes                          |
| `terraform plan`     | Create execution plan (dry-run)                     | ✅ Yes                          |
| `terraform apply`    | Execute planned changes                             | ❌ No - modifies infrastructure |
| `terraform destroy`  | Destroy managed resources                           | ❌ No - destroys infrastructure |

### Command Details

**terraform init**:

- Initializes working directory containing Terraform configuration files
- Downloads required provider plugins
- Sets up backend configuration
- Creates `.terraform` directory for cached plugins and modules
- Never modifies state files or configuration files
- Safe to run multiple times

**terraform validate**:

- Validates configuration file syntax
- Checks internal consistency of configuration
- Verifies attribute names and value types
- Identifies variable reference errors
- Limited validation - some errors only caught during apply

**terraform plan**:

- Reads current state file (if exists)
- Refreshes state by querying actual infrastructure
- Compares current state with desired configuration
- Proposes set of actions to achieve desired state
- Provides dry-run preview without making changes

**terraform apply**:

- Executes actions proposed in terraform plan
- Creates, updates, or destroys infrastructure resources
- Updates state file with new resource information
- Requires user confirmation unless `-auto-approve` flag used

**terraform destroy**:

- Destroys all resources managed by Terraform
- Only affects resources tracked in state file
- Does not delete configuration files
- Requires user confirmation for safety

## Terraform Workflow

### Basic Workflow Demonstration

```bash
# Check Terraform version
terraform -version

# Get help for available commands
terraform -help
```

**Line-by-line Comments:**

```bash
# Display installed Terraform version and check for updates
# Show all available Terraform subcommands and options
```

### Configuration Example

```hcl
resource "random_string" "random" {
  length = 16
}
```

**Line-by-line Comments:**

```hcl
# Create random string resource using HashiCorp random provider
# Set string length to 16 characters
```

### Code Walkthrough

This simple configuration demonstrates:

- **Resource Declaration**: Uses `resource` block to define infrastructure component
- **Provider Usage**: Leverages `random` provider maintained by HashiCorp
- **Resource Naming**: Uses two-part naming: resource type and local name
- **Attribute Configuration**: Sets `length` parameter to control string generation

### Complete Workflow Example

```bash
# Initialize working directory
terraform init

# Validate configuration syntax
terraform validate

# Generate execution plan
terraform plan

# Save plan to file for review
terraform plan -out myplan

# Apply saved plan
terraform apply myplan

# Apply with interactive confirmation
terraform apply

# Plan destruction
terraform plan -destroy

# Destroy resources
terraform destroy
```

**Line-by-line Comments:**

```bash
# Download providers and initialize backend
# Check configuration for syntax errors
# Preview changes without execution
# Save execution plan to file for later use
# Execute specific saved plan without confirmation
# Execute changes with user confirmation prompt
# Preview resource destruction
# Destroy all managed resources with confirmation
```

## State Management

### Initialization Effects

- Creates `.terraform` directory (hidden)
- Downloads provider plugins to `.terraform/providers/`
- Creates `.terraform.lock.hcl` file for provider version locking
- Establishes backend configuration for state storage

### State File Interaction

- **terraform plan**: Reads state, compares with configuration
- **terraform apply**: Updates state with resource changes
- **terraform destroy**: Uses state to identify resources for deletion

## Providers & Resources

### Provider Management

- Providers downloaded during `terraform init`
- Stored in `.terraform/providers/` directory
- Version constraints managed through lock file
- Registry path: `registry.terraform.io/hashicorp/random`

### Resource Lifecycle

1. **Plan Phase**: Resource changes calculated and displayed
2. **Apply Phase**: Resources created, updated, or destroyed
3. **State Update**: Resource metadata stored in state file
4. **Destroy Phase**: Resources removed based on state information

## Pitfalls & Best Practices

### Command Safety

- **Always Plan First**: Run `terraform plan` before `terraform apply`
- **Review Changes**: Carefully examine plan output before applying
- **Save Plans**: Use `-out` flag to save and review plans
- **Validate Regularly**: Use `terraform validate` to catch syntax errors early

### Configuration Management

- **Version Control**: Store configuration files in version control
- **Provider Versions**: Pin provider versions for consistency
- **State Security**: Protect state files containing sensitive information
- **Backup Strategy**: Implement state file backup procedures

### Common Mistakes

- **Skipping Validation**: Not running `terraform validate` before planning
- **Ignoring Plan Output**: Applying changes without reviewing plan
- **State File Conflicts**: Multiple users modifying same state simultaneously
- **Provider Version Drift**: Not pinning provider versions causing inconsistencies

## Key Terms & Definitions

- **CLI (Command Line Interface)**: Text-based interface for interacting with Terraform
- **Provider**: Plugin that enables Terraform to interact with specific platforms or services
- **Resource**: Infrastructure component managed by Terraform (VMs, networks, etc.)
- **State File**: JSON file tracking current infrastructure state and metadata
- **Working Directory**: Local directory containing Terraform configuration files
- **Execution Plan**: Preview of changes Terraform will make to infrastructure
- **Dry Run**: Preview mode that shows changes without executing them

## Common Exam Traps

- **Command Order**: Understanding proper sequence of Terraform commands
- **State File Safety**: Knowing which commands modify state vs. configuration
- **Plan vs. Apply**: Distinguishing between preview and execution phases
- **Provider Downloads**: Understanding when and how providers are installed
- **Validation Limitations**: Recognizing what `terraform validate` can and cannot check
- **Destroy Scope**: Understanding that destroy only affects Terraform-managed resources
