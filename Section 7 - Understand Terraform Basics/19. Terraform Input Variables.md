# Terraform Input Variables

## Overview

Input variables enable parameterization of Terraform configurations, allowing customization without modifying source code. Variables promote code reusability, following the DRY (Don't Repeat Yourself) principle, and enable sharing configurations across teams and organizations.

## Concepts

- **Input Variables**: Parameterized values that customize module or configuration behavior
- **Variable Declaration**: Defining variables with type, description, default, and validation
- **Variable Reference**: Accessing variable values using `var.<variable_name>` syntax
- **Variable Precedence**: Order in which Terraform evaluates variable value sources
- **Reusability**: Writing code once and customizing through variable values

## Modules & Variables

### Variable Declaration Syntax

```hcl
variable "<VARIABLE_NAME>" {
  description = "Description of the variable"
  type        = <TYPE>
  default     = <DEFAULT_VALUE>
  sensitive   = <true|false>
  validation {
    # Validation rules
  }
}
```

**Line-by-line Comments:**

```hcl
# Variable block with unique name
# Human-readable description
# Data type constraint (string, number, bool, list, map, etc.)
# Default value if none provided
# Mark as sensitive to hide in output
# Optional validation rules block
```

### Variable Components

| Component        | Required | Purpose           |
| ---------------- | -------- | ----------------- |
| `variable` block | ✅ Yes   | Declares variable |
| Variable name    | ✅ Yes   | Unique identifier |
| `description`    | ❌ No    | Documentation     |
| `type`           | ❌ No    | Type constraint   |
| `default`        | ❌ No    | Default value     |
| `sensitive`      | ❌ No    | Hide in logs      |
| `validation`     | ❌ No    | Custom validation |

### Variable Types

**Primitive Types**:

- `string`: Text values
- `number`: Numeric values
- `bool`: Boolean (true/false)

**Complex Types**:

- `list(<TYPE>)`: Ordered collection
- `map(<TYPE>)`: Key-value pairs
- `set(<TYPE>)`: Unordered unique values
- `object({...})`: Structured data
- `tuple([...])`: Fixed-length collection

## Terraform Workflow

### Static Resource Configuration (Before Variables)

```hcl
resource "aws_subnet" "variables_subnet" {
  vpc_id                  = aws_vpc.vpc.id
  cidr_block              = "10.0.250.0/24"
  availability_zone       = "us-east-1a"
  map_public_ip_on_launch = true

  tags = {
    Name      = "sub-variables-us-east-1a"
    Terraform = "true"
  }
}
```

**Line-by-line Comments:**

```hcl
# Subnet resource with static values
# Reference to VPC resource
# Hardcoded CIDR block (not reusable)
# Hardcoded availability zone
# Static boolean value
# Hardcoded tags
```

**Problems with Static Values**:

- Not reusable across environments
- Requires code modification for changes
- Difficult to maintain multiple similar resources
- No flexibility for different deployments

### Variable Declaration

```hcl
variable "variables_sub_cidr" {
  description = "CIDR Block for the Variable Subnet"
  type        = string
  default     = "10.0.202.0/24"
}

variable "variables_sub_az" {
  description = "Availability Zone used Variable Subnet"
  type        = string
  default     = "us-east-1a"
}

variable "variables_sub_auto_ip" {
  description = "Set Automatic IP Assignments for Variables Subnet"
  type        = bool
  default     = true
}
```

**Line-by-line Comments:**

```hcl
# CIDR block variable declaration
# Documentation for variable purpose
# String type constraint
# Default value if none provided
# Availability zone variable
# Boolean variable for IP assignment
```

### Variable Usage in Resources

```hcl
resource "aws_subnet" "variables_subnet" {
  vpc_id                  = aws_vpc.vpc.id
  cidr_block              = var.variables_sub_cidr
  availability_zone       = var.variables_sub_az
  map_public_ip_on_launch = var.variables_sub_auto_ip

  tags = {
    Name      = "sub-variables-${var.variables_sub_az}"
    Terraform = "true"
  }
}
```

**Line-by-line Comments:**

```hcl
# Subnet resource with variable references
# Reference VPC resource
# Use variable for CIDR block
# Use variable for availability zone
# Use variable for IP assignment
# String interpolation with variable
```

### Code Walkthrough

The variable-based configuration demonstrates:

- **Variable Reference**: `var.<variable_name>` syntax accesses variable values
- **Type Safety**: Type constraints ensure correct value types
- **String Interpolation**: `${var.variable_name}` embeds variables in strings
- **Default Values**: Terraform uses defaults when no value provided
- **Reusability**: Same code creates different resources with different variable values

### Variable Value Precedence Order

Terraform evaluates variable values in the following order (lowest to highest priority):

1. **Variable Defaults** (lowest priority)
2. **Environment Variables** (`TF_VAR_<variable_name>`)
3. **terraform.tfvars** file
4. **terraform.tfvars.json** file
5. **\*.auto.tfvars** or **\*.auto.tfvars.json** files
6. **-var** or **-var-file** CLI flags (highest priority)

**Example**:

```bash
# Environment variable (priority 2)
export TF_VAR_variables_sub_cidr="10.0.200.0/24"

# CLI flag (priority 6 - highest)
terraform apply -var="variables_sub_cidr=10.0.210.0/24"
```

### Interactive Variable Input

When no value is provided, Terraform prompts interactively:

```bash
terraform plan
```

**Output**:

## State Management

### Variable Impact on State

- **Value Changes**: Modifying variable values triggers resource updates
- **Immutable Properties**: Some changes force resource replacement
- **State Comparison**: Terraform compares desired state (with variables) to current state
- **Plan Output**: Shows how variable changes affect infrastructure

## Pitfalls & Best Practices

### Variable Organization

- **Separate File**: Use `variables.tf` for all variable declarations
- **Descriptive Names**: Use clear, meaningful variable names
- **Documentation**: Always include descriptions for variables
- **Type Constraints**: Specify types to prevent errors

### Default Values

- **Sensible Defaults**: Provide defaults for common use cases
- **Environment-Specific**: Use different values per environment
- **Security**: Never default sensitive values (passwords, keys)
- **Documentation**: Document why specific defaults chosen

### Variable Naming

- **Consistency**: Follow naming conventions across project
- **Uniqueness**: Each variable name must be unique
- **Clarity**: Names should indicate purpose and usage
- **Avoid Conflicts**: Don't use Terraform reserved words

### Common Mistakes

- **Missing Descriptions**: Omitting variable documentation
- **Wrong Types**: Type mismatches cause errors
- **Hardcoded Secrets**: Never hardcode sensitive values
- **Duplicate Names**: Variable names must be unique

## Key Terms & Definitions

- **Input Variable**: Parameterized value that customizes Terraform behavior
- **Variable Block**: HCL block declaring a variable
- **Variable Reference**: Accessing variable value using `var.<name>` syntax
- **Default Value**: Value used when no other value provided
- **Variable Precedence**: Order Terraform evaluates variable value sources
- **Type Constraint**: Specification of allowed variable value types
- **String Interpolation**: Embedding variables within strings using `${}`
- **DRY Principle**: Don't Repeat Yourself - write reusable code

## Common Exam Traps

- **Variable Syntax**: Correct syntax is `var.<variable_name>`, not `variable.<name>`
- **Precedence Order**: Understanding which value source takes priority
- **Type Constraints**: Knowing primitive vs. complex types
- **Default Behavior**: Variables without defaults require input
- **String Interpolation**: Proper syntax `${var.name}` within strings
- **Uniqueness**: Variable names must be unique within configuration
- **File Organization**: Variables typically in `variables.tf` but not required
