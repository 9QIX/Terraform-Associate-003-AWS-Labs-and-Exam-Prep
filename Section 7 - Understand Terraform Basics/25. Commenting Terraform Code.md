# Commenting Terraform Code

## Overview

Comments in Terraform enable developers to document code purpose, provide instructions, and improve readability for team members and future maintenance. Terraform supports three comment syntaxes: single-line comments using `#` or `//`, and multi-line comments using `/* */`. Comments are ignored during execution and do not affect infrastructure deployment or state.

---

## Concepts

### Purpose of Comments

**Use Cases:**

- Document code functionality and intent
- Provide reminders for future code modifications
- Explain complex logic or non-obvious decisions
- Add instructions for other developers
- Temporarily disable code during testing
- Improve code maintainability and readability

### Comment Types

| Syntax  | Type        | Description                        | Common Usage                   |
| ------- | ----------- | ---------------------------------- | ------------------------------ |
| `#`     | Single-line | Begins comment, ends at line break | Most common in Terraform       |
| `//`    | Single-line | Alternative single-line syntax     | Less common, valid alternative |
| `/* */` | Multi-line  | Spans multiple lines               | Block comments, headers        |

## Terraform Workflow

### Task 1: Add Single-Line Comment

**Using Hash Symbol (`#`):**

```hcl
# IaC Buildout for Terraform Associate Exam

# Configure the AWS Provider
provider "aws" {
  region = "us-east-1"
}

# Define the VPC
resource "aws_vpc" "vpc" {
  cidr_block = var.vpc_cidr

  tags = {
    Name = var.vpc_name
  }
}
```

**Line-by-line Comments:**

```hcl
# IaC Buildout for Terraform Associate Exam  # Single-line comment with hash

# Configure the AWS Provider                 # Comment describing provider block
provider "aws" {                             # Provider configuration
  region = "us-east-1"                       # AWS region setting
}

# Define the VPC                             # Comment describing resource
resource "aws_vpc" "vpc" {                   # VPC resource block
  cidr_block = var.vpc_cidr                  # VPC CIDR from variable

  tags = {                                   # Resource tags
    Name = var.vpc_name                      # VPC name tag
  }
}
```

**Code Walkthrough:**

- `#` symbol starts single-line comment
- Comment extends to end of line only
- Most commonly used comment syntax in Terraform
- Can appear on its own line or after code
- Terraform parser ignores all text after `#` on that line

**Using Double Forward Slash (`//`):**

```hcl
// Alternative single-line comment syntax

// Configure the AWS Provider
provider "aws" {
  region = "us-east-1"  // Region configuration
}
```

**Line-by-line Comments:**

```hcl
// Alternative single-line comment syntax     // Double-slash comment

// Configure the AWS Provider                 // Comment before provider block
provider "aws" {                              // Provider configuration
  region = "us-east-1"  // Region configuration  // Inline comment
}
```

**Code Walkthrough:**

- `//` provides alternative single-line comment syntax
- Functionally identical to `#` comments
- Less common in Terraform community
- Valid and supported syntax
- Useful for developers familiar with C-style languages

**Verify Configuration:**

```bash
terraform plan
```

**Expected Output:**

```text
No changes. Your infrastructure matches the configuration.

Terraform has compared your real infrastructure against your configuration and found no
differences, so no changes are needed.
```

**Code Walkthrough:**

- `terraform plan` validates configuration including comments
- Comments do not affect plan output
- No infrastructure changes from adding comments
- Terraform ignores comments during parsing

### Task 2: Add Multi-Line Comment

**Multi-Line Comment Syntax:**

```hcl
/*
Name: IaC Buildout for Terraform Associate Exam
Description: AWS Infrastructure Buildout
Contributors: Bryan and Gabe
*/

# Configure the AWS Provider
provider "aws" {
  region = "us-east-1"
}
```

**Line-by-line Comments:**

```hcl
/*                                                    # Start multi-line comment
Name: IaC Buildout for Terraform Associate Exam      # Project name
Description: AWS Infrastructure Buildout             # Project description
Contributors: Bryan and Gabe                         # Author credits
*/                                                    # End multi-line comment

# Configure the AWS Provider                         # Single-line comment
provider "aws" {                                     # Provider block
  region = "us-east-1"                               # Region setting
}
```

**Code Walkthrough:**

- `/*` starts multi-line comment block
- All lines between `/*` and `*/` are comments
- `*/` ends multi-line comment block
- Useful for file headers, documentation blocks
- Can span any number of lines
- Common for copyright notices, module descriptions

**Verify Configuration:**

```bash
terraform plan
```

**Expected Output:**

```text
No changes. Your infrastructure matches the configuration.

Terraform has compared your real infrastructure against your configuration and found no
differences, so no changes are needed.
```

**Code Walkthrough:**

- Multi-line comments also ignored by Terraform
- No impact on infrastructure state
- Safe to add extensive documentation
- Comments do not increase execution time

## Pitfalls & Best Practices

### Best Practices

**Use Comments Liberally:**

- Document non-obvious logic and decisions
- Explain why code exists, not just what it does
- Add context for future maintainers
- Include TODO items for incomplete work

**Choose Consistent Comment Style:**

- Use `#` for single-line comments (Terraform convention)
- Use `/* */` for multi-line blocks
- Maintain consistency across project
- Follow team or organization standards

**Document Complex Expressions:**

```hcl
# Calculate subnet CIDR by adding 8 bits to VPC CIDR and using subnet index
# Example: 10.0.0.0/16 + 8 bits = 10.0.X.0/24 where X is subnet index
cidr_block = cidrsubnet(var.vpc_cidr, 8, each.value)
```

- Explain complex functions and calculations
- Provide examples of expected values
- Help others understand logic quickly

**Add File Headers:**

```hcl
/*
Module: VPC Infrastructure
Purpose: Creates VPC with public and private subnets across multiple AZs
Author: Infrastructure Team
Last Updated: 2025-01-15
*/
```

- Include module purpose and metadata
- Document authors and update dates
- Provide high-level overview

**Comment Temporarily Disabled Code:**

```hcl
# Temporarily disabled for testing
# resource "aws_instance" "test" {
#   ami           = data.aws_ami.ubuntu.id
#   instance_type = "t3.micro"
# }
```

- Use comments to disable code blocks
- Explain why code is commented out
- Remove commented code before production deployment

**Document Variable Constraints:**

```hcl
variable "instance_count" {
  description = "Number of instances to create"
  type        = number
  default     = 3

  # Must be between 1 and 10 for cost control
  validation {
    condition     = var.instance_count >= 1 && var.instance_count <= 10
    error_message = "Instance count must be between 1 and 10."
  }
}
```

- Explain validation rules and constraints
- Document business logic behind limits
- Clarify expected value ranges

### Common Pitfalls

**Over-Commenting Obvious Code:**

```hcl
# Bad: Obvious comment
# Set region to us-east-1
region = "us-east-1"

# Good: Explains why
# Using us-east-1 for proximity to primary data center
region = "us-east-1"
```

- Avoid stating the obvious
- Focus on "why" not "what"
- Add value with context

**Outdated Comments:**

```hcl
# Bad: Comment doesn't match code
# Creates t2.micro instance
resource "aws_instance" "web" {
  instance_type = "t3.micro"  # Code changed, comment didn't
}
```

- Update comments when code changes
- Outdated comments mislead developers
- Review comments during code reviews

**Leaving Commented-Out Code:**

```hcl
# Bad: Dead code left in repository
# resource "aws_instance" "old" {
#   ami           = "ami-12345"
#   instance_type = "t2.micro"
# }
```

- Remove commented code before committing
- Use version control for history
- Commented code clutters files

**Nested Multi-Line Comments:**

```hcl
# Invalid: Cannot nest multi-line comments
/*
  Outer comment
  /*
    Inner comment - This will cause errors
  */
*/
```

- Multi-line comments cannot be nested
- Use single-line comments within multi-line blocks
- Causes parsing errors

**Missing Comment Terminators:**

```hcl
# Invalid: Missing closing */
/*
  This comment never ends

resource "aws_vpc" "vpc" {
  cidr_block = "10.0.0.0/16"
}
```

- Always close multi-line comments with `*/`
- Missing terminator comments out remaining file
- Causes unexpected behavior

## Key Terms & Definitions

| Term                    | Definition                                                                   |
| ----------------------- | ---------------------------------------------------------------------------- |
| **Comment**             | Non-executable text in code that documents functionality or provides context |
| **Single-Line Comment** | Comment that spans only one line, using `#` or `//` syntax                   |
| **Multi-Line Comment**  | Comment spanning multiple lines, enclosed in `/* */`                         |
| **Inline Comment**      | Comment appearing on the same line as code                                   |
| **Block Comment**       | Multi-line comment used for documentation blocks or headers                  |
| **Comment Syntax**      | The characters used to denote comments (`#`, `//`, `/* */`)                  |
| **Code Documentation**  | Practice of adding comments to explain code purpose and logic                |

## Common Exam Traps

1. **Comment Syntax Recognition**

   - Three valid syntaxes: `#`, `//`, `/* */`
   - All three are supported in Terraform
   - `#` is most common in Terraform community

2. **Single-Line vs. Multi-Line**

   - `#` and `//` are single-line only
   - `/* */` can span multiple lines
   - Single-line comments end at line break

3. **Comments Do Not Affect Execution**

   - Comments ignored by Terraform parser
   - No impact on plan, apply, or state
   - Safe to add without infrastructure changes

4. **Inline Comments**

   - Comments can appear after code on same line
   - Example: `region = "us-east-1"  # Primary region`
   - Useful for brief explanations

5. **Comment Nesting**

   - Multi-line comments cannot be nested
   - `/* /* nested */ */` causes errors
   - Use single-line comments within multi-line blocks

6. **Temporarily Disabling Code**

   - Commenting out code disables it
   - Useful for testing and debugging
   - Remove before production deployment

7. **Comments in Strings**

   - Comment syntax inside strings is literal text
   - Example: `description = "# This is not a comment"`
   - Only comments outside strings are parsed as comments

8. **HCL vs. JSON Syntax**

   - HCL supports all three comment syntaxes
   - JSON format does not support comments
   - Use HCL (`.tf`) for commented configurations

9. **Comment Best Practices**

   - Document "why" not "what"
   - Keep comments up-to-date
   - Remove commented-out code

10. **Terraform Formatting**
    - `terraform fmt` preserves comments
    - Comments maintain position relative to code
    - Formatting does not remove comments

## Updated Information (as of 2025-01-XX)

### Comment Syntax Unchanged

- All three comment syntaxes (`#`, `//`, `/* */`) remain valid
- No changes to comment parsing in recent Terraform versions
- Syntax consistent from Terraform 0.12 through current versions

### Terraform fmt Behavior

- `terraform fmt` command preserves all comments
- Comments maintain their position relative to code
- Formatting adjusts indentation but keeps comment content
- No changes to comment handling in formatting

### IDE Support

- Modern IDEs (VS Code, IntelliJ, Vim) recognize all Terraform comment syntaxes
- Syntax highlighting works for all comment types
- Auto-completion and linting respect comments
- Extensions like HashiCorp Terraform extension provide enhanced comment support

### Documentation Best Practices

- **Current trend**: Use `#` for consistency with Terraform community
- **Module documentation**: Use multi-line comments for file headers
- **Inline documentation**: Use single-line comments for brief explanations
- **Generated documentation**: Tools like `terraform-docs` extract comments for README generation

### Comment-Based Documentation Tools

- **terraform-docs**: Generates documentation from comments and variable descriptions
- Extracts `description` fields from variables and outputs
- Can include file-level comments in generated docs
- Standard tool for module documentation

### HCL2 Comment Handling

- HCL2 (Terraform 0.12+) maintains backward compatibility with comment syntax
- No breaking changes to comment parsing
- All legacy comment styles continue to work
