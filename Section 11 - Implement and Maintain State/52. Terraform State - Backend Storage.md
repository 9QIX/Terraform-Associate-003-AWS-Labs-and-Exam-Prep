# Terraform State — Backend Storage

## Overview

Terraform stores the state of managed infrastructure to track resource mappings and metadata. A **backend** defines where state is stored and how operations are performed. Standard backends store state remotely while executing Terraform operations locally via the CLI. Configuring a backend is essential for security (encryption, access control) and collaboration (locking, versioning).

A Terraform configuration can specify only **one backend** at a time. Changing the backend requires running `terraform init -reconfigure`.

---

## Concepts

- **Standard Backend** — Stores state remotely; all Terraform operations (`plan`, `apply`, `destroy`) run locally.
- **State Versioning** — Retains historical revisions of the state file, enabling rollback.
- **State Encryption** — Protects state data at rest (AES-256) and in transit (TLS/SSL).
- **State Locking** — Prevents concurrent modifications that could corrupt state.

---

## Terraform Workflow

1. Configure the backend block inside the `terraform {}` block.
2. Run `terraform init -reconfigure` whenever the backend configuration changes.
3. Perform normal operations (`plan`, `apply`, `destroy`) — state is read/written to the remote backend automatically.
4. Before switching backends, either migrate state or destroy existing resources.

## State Management

### S3 Backend Configuration

```hcl
terraform {
  backend "s3" {
    bucket         = "myterraformstate"
    key            = "path/to/my/key"
    region         = "us-east-1"
    dynamodb_table = "terraform-locks"
    encrypt        = true
  }
}
```

```text
# Line-by-line Comments
terraform {                          # Opens the terraform settings block
  backend "s3" {                     # Declares S3 as the state backend
    bucket         = "myterraformstate"   # S3 bucket name for state storage
    key            = "path/to/my/key"     # Object key (path) within the bucket
    region         = "us-east-1"          # AWS region of the bucket
    dynamodb_table = "terraform-locks"    # DynamoDB table for state locking
    encrypt        = true                 # Enables server-side encryption
  }
}
```

#### Code Walkthrough

- The `bucket` and `key` together form the unique location of the state file in S3.
- `region` must match the bucket's actual AWS region.
- `dynamodb_table` enables state locking via a DynamoDB table with a partition key named `LockID`.
- `encrypt = true` ensures the state file is encrypted at rest using S3 server-side encryption (SSE-S3 / AES-256).
- **Dependency**: The S3 bucket and DynamoDB table must exist before running `terraform init`.

---

### Enabling Versioning

Enable bucket versioning via the AWS Console (or IaC) on the S3 bucket. Once enabled, every `terraform apply` creates a new version of the state object. Previous versions can be restored if state becomes corrupted.

```bash
terraform apply
```

After apply, navigate to the S3 object and toggle **Show Versions** to see historical state revisions.

---

### Enabling Encryption

Enable **Default Encryption** on the S3 bucket (SSE-S3 with AES-256 or SSE-KMS). This ensures:

- Data encrypted **at rest** on disk.
- Data encrypted **in transit** — Terraform uses TLS when communicating with S3.

> Users with bucket access can still read state in unencrypted form through the console/API. Restrict bucket permissions via IAM policies.

---

### Enabling State Locking

State locking prevents concurrent `apply` or `destroy` operations from corrupting state.

| Step | Action |
|------|--------|
| 1 | Create a DynamoDB table (e.g., `terraform-locks`) with partition key `LockID` (String). |
| 2 | Add `dynamodb_table` to the backend block. |
| 3 | Run `terraform init -reconfigure`. |

During an active operation, a lock item appears in the DynamoDB table containing the lock holder's identity, operation type, and timestamp.

> **Deprecation Notice**: State locking via DynamoDB is deprecated and will be removed in a future minor version. The recommended approach is to set `use_lockfile = true` in the `s3` backend block, which uses S3-native conditional writes for locking without requiring DynamoDB. See [S3 backend state locking documentation](https://developer.hashicorp.com/terraform/language/backend/s3#state-locking).

### HTTP Backend Configuration (Optional)

The `http` backend stores state via a simple REST API (GET to fetch, POST to update, DELETE to purge).

```hcl
terraform {
  backend "http" {
    address        = "http://localhost:5000/terraform_state/my_state"
    lock_address   = "http://localhost:5000/terraform_lock/my_state"
    lock_method    = "PUT"
    unlock_address = "http://localhost:5000/terraform_lock/my_state"
    unlock_method  = "DELETE"
  }
}
```

```text
# Line-by-line Comments
terraform {
  backend "http" {                                                    # Declares HTTP as the state backend
    address        = "http://localhost:5000/terraform_state/my_state" # URL for state GET/POST
    lock_address   = "http://localhost:5000/terraform_lock/my_state"  # URL to acquire lock
    lock_method    = "PUT"                                            # HTTP method to create lock
    unlock_address = "http://localhost:5000/terraform_lock/my_state"  # URL to release lock
    unlock_method  = "DELETE"                                         # HTTP method to release lock
  }
}
```

#### Code Walkthrough

- `address` is the endpoint where Terraform reads (GET) and writes (POST) state.
- Locking is optional but recommended; configured via `lock_address` / `unlock_address`.
- The HTTP server must be running before any Terraform operation — if the server is unreachable, operations (including `destroy`) will fail.
- **Dependency**: A running HTTP server that implements the expected REST contract.

---

### Reconfiguring Backends

```bash
terraform init -reconfigure
```

Use `-reconfigure` to switch backends without attempting state migration. Terraform will reinitialize using the new backend configuration.

---

## Comparison: S3 vs. HTTP Backend

| Feature | S3 Backend | HTTP Backend |
|---------|-----------|--------------|
| State storage | AWS S3 bucket | Any REST-compatible HTTP server |
| Encryption at rest | Native (SSE-S3 / SSE-KMS) | Depends on server implementation |
| Encryption in transit | TLS (built-in) | Depends on HTTPS configuration |
| Versioning | Native S3 versioning | Must be implemented by server |
| State locking | S3 native lock or DynamoDB | Custom via PUT/DELETE endpoints |
| Managed service | Yes (AWS) | Self-hosted |
| Setup complexity | Low | Medium–High |

## Pitfalls & Best Practices

- **Always enable encryption** — State files can contain secrets (passwords, keys, tokens) in plaintext.
- **Always enable locking** — Concurrent modifications corrupt state.
- **Enable versioning** — Allows rollback if state is accidentally modified or deleted.
- **Restrict bucket access** — Encryption alone does not prevent authorized users from reading sensitive state data; use IAM policies.
- **Do not stop the backend server before `destroy`** — Terraform must read state to plan destruction; an unreachable backend causes failures.
- **Only one backend per working directory** — You cannot configure multiple backends simultaneously.
- **Clean up local state files** — After migrating to a remote backend, remove local `terraform.tfstate` and `terraform.tfstate.backup` to avoid confusion.
- **Run `terraform init -reconfigure`** after any backend configuration change.

## Common Exam Traps

| Trap | Correct Understanding |
|------|----------------------|
| "Standard backends run operations remotely" | **False** — Standard backends store state remotely but run operations locally. Only enhanced backends (HCP Terraform) run operations remotely. |
| "S3 backend natively supports locking" | Previously required DynamoDB; now supports native locking via `use_lockfile = true`. Exam may reference DynamoDB — know both approaches. |
| "Encryption prevents all unauthorized access to state" | **False** — Users with bucket/API access can still read state. Encryption protects data at rest and in transit only. |
| "You can configure multiple backends" | **False** — Only one backend block is allowed per configuration. |
| "Changing the backend block requires only `terraform plan`" | **False** — You must run `terraform init -reconfigure` (or `-migrate-state`) after any backend change. |
| "Destroying resources requires the backend to be reachable" | **True** — Terraform must read state from the backend to plan a destroy. |

## Key Terms & Definitions

| Term | Definition |
|------|-----------|
| **Backend** | A configuration that determines where Terraform state is stored and where operations are executed. |
| **Standard Backend** | A backend type that stores state remotely while running all operations locally. |
| **State File** | A JSON file (`terraform.tfstate`) that maps real-world resources to your configuration. |
| **State Locking** | A mechanism that prevents concurrent state modifications by acquiring an exclusive lock. |
| **DynamoDB Table** | An AWS NoSQL database table used (historically) by the S3 backend for state locking. |
| **SSE-S3** | Server-Side Encryption with Amazon S3-managed keys (AES-256). |
| **`terraform init -reconfigure`** | Reinitializes the backend without migrating existing state. |
| **Partition Key** | The primary key attribute in a DynamoDB table; for Terraform locking, it must be `LockID`. |

## Updated Information (as of 2025-07-14)

| Change | Details |
|--------|---------|
| **S3 state locking without DynamoDB** | As of Terraform v1.10+, the S3 backend supports native state locking using S3 conditional writes (`use_lockfile = true`). The `dynamodb_table` attribute for locking is deprecated and will be removed in a future minor version. The lab's DynamoDB approach remains functional but is no longer the recommended method. |
| **Backend terminology** | HashiCorp documentation now refers to "HCP Terraform" (formerly Terraform Cloud) as the enhanced backend. The term "remote backend" for Terraform Cloud is deprecated in favor of the `cloud` block. |
| **Python SimpleHTTPServer** | The lab references `python -m SimpleHTTPServer 8000` (Python 2). For Python 3, use `python3 -m http.server 8000`. The actual lab server uses Flask (`stateserver.py`), not the built-in HTTP module. |
| **S3 bucket encryption default** | Since January 2023, AWS enables SSE-S3 encryption by default on all new S3 buckets. Explicit enablement is no longer required for new buckets but remains a best practice to verify. |
