# Terraform State — Backend Partial Configuration

## Overview

Terraform backend configuration is defined within the `terraform {}` block and supports only **one backend per working directory**. Not all required arguments must be specified directly in the configuration file — omitted arguments can be supplied via files, command-line flags, or interactive prompts. When some or all backend arguments are omitted from the main configuration, this is called a **partial configuration**.

Partial configurations enable:
- Automation pipelines to inject environment-specific values at runtime.
- Separation of sensitive values (bucket names, credentials) from version-controlled code.
- Reuse of a single Terraform configuration across multiple environments (dev, test, prod).

> **Key constraint**: Backend blocks do not support interpolation — variables and expressions cannot be used as values within the `backend` block.

---

## Concepts

- **Partial Configuration** — A backend block with some or all required arguments omitted, to be supplied externally at `terraform init` time.
- **`-backend-config` flag** — Supplies partial backend configuration via a file path or inline key/value pair during `terraform init`.
- **Configuration Merge Order** — Command-line options override main configuration values; later `-backend-config` flags override earlier ones.
- **Interactive Prompts** — If a required backend value is missing from all sources, Terraform prompts interactively (unless input is disabled).

---

## Terraform Workflow

### Partial Configuration Methods

| Method | Syntax | Use Case |
|--------|--------|----------|
| Full inline | All values in `backend` block | Simple, single-environment setups |
| File-based partial | `-backend-config=PATH` | Environment-specific configs, CI/CD pipelines |
| CLI key/value | `-backend-config="KEY=VALUE"` | Quick overrides, automation scripts |
| Interactive prompt | Omit required value | Manual workflows (not recommended for automation) |
| Multiple files | Multiple `-backend-config` flags | Split bucket config from key/path config |

### Initialization Flow

1. Define the `backend` block (can be empty or partial).
2. Create `.hcl` files with partial configuration values.
3. Run `terraform init -backend-config=<file_or_key=value> -migrate-state`.
4. Terraform merges all configuration sources and initializes the backend.
5. Proceed with `terraform plan` and `terraform apply`.

## State Management

### Task 1: Explicit Local Backend

```hcl
terraform {
  backend "local" {
    path = "terraform.tfstate"
  }
}
```

```text
# Line-by-line Comments
terraform {
  backend "local" {               # Explicitly declares the local backend (same as default)
    path = "terraform.tfstate"    # Path to the state file within the working directory
  }
}
```

#### Code Walkthrough

Without a `backend` block, Terraform defaults to `local` with state in `terraform.tfstate`. This explicit declaration is functionally identical to the default but makes the backend choice visible in code.

### Task 2: Partial Configuration via File (Local Backend)

Directory structure:

```text
|--- main.tf
|--- modules/
|--- state_configuration/
|   |--- dev_local.hcl
|   |--- test_local.hcl
|--- state_data/
|--- terraform.tf
|--- variables.tf
```

`state_configuration/dev_local.hcl`:

```hcl
path = "state_data/terraform.dev.tfstate"
```

`state_configuration/test_local.hcl`:

```hcl
path = "state_data/terraform.test.tfstate"
```

```bash
terraform init -backend-config="state_configuration/dev_local.hcl" -migrate-state
terraform plan
terraform apply
```

```text
# Line-by-line Comments
terraform init -backend-config="state_configuration/dev_local.hcl" -migrate-state
# -backend-config: supplies the partial config file with the state path
# -migrate-state: copies existing state to the new location

terraform plan    # Generates execution plan using the dev state file
terraform apply   # Applies changes, writing state to state_data/terraform.dev.tfstate
```

#### Code Walkthrough

- The `backend "local"` block in `terraform.tf` omits the `path` argument.
- The `path` is supplied externally via `-backend-config`, pointing to the dev-specific `.hcl` file.
- Switching environments requires re-running `init` with a different partial config file.
- `-migrate-state` ensures existing state data is copied to the new location.

### Task 3: Partial Configuration via CLI Key/Value

```bash
terraform init -backend-config="path=state_data/terraform.prod.tfstate" -migrate-state
```

```text
# Line-by-line Comments
terraform init -backend-config="path=state_data/terraform.prod.tfstate" -migrate-state
# Provides the backend path directly as a key=value pair on the command line
# Useful for one-off overrides or automation scripts
```

> **Security note**: Many shells retain command-line flags in history files. Do not use this method for secrets.

```bash
terraform init -migrate-state
```

#### 4.3 — Empty Backend Block + Multiple Partial Files

`state_configuration/s3-state-bucket.hcl`:

```hcl
bucket = "my-terraform-state-ghm"
region = "us-east-1"
```

`state_configuration/dev-s3-state-key.hcl`:

```hcl
key = "dev/aws_infra"
```

```bash
terraform init \
  -backend-config="state_configuration/s3-state-bucket.hcl" \
  -backend-config="state_configuration/dev-s3-state-key.hcl" \
  -migrate-state
```

```text
# Line-by-line Comments
terraform init \
  -backend-config="state_configuration/s3-state-bucket.hcl" \   # Supplies bucket + region
  -backend-config="state_configuration/dev-s3-state-key.hcl" \  # Supplies key (state path)
  -migrate-state                                                  # Migrates state to merged config
```

#### Code Walkthrough

- The backend block is empty — all configuration comes from external files.
- Multiple `-backend-config` flags are merged in order (later values override earlier ones for the same key).
- This pattern separates shared infrastructure config (bucket, region) from environment-specific config (key).
- Enables reuse: the same `s3-state-bucket.hcl` works for dev, test, and prod by swapping only the key file.

### Task 5: Interactive Prompt for Missing Required Values

```bash
terraform init -backend-config="state_configuration/s3-state-bucket.hcl" -migrate-state
```

Output when `key` is missing:

```text
key
  The path to the state file inside the bucket

  Enter a value: dev/aws_infra
```

- Terraform prompts **only for required values** that are not supplied by any configuration source.
- Optional values are not prompted — they use provider defaults.
- Interactive prompts are disabled when input is disabled (e.g., `-input=false` in CI/CD).

### Task 6: Configuration Merge Priority

When backend settings are provided from multiple locations, the merge order is:

| Priority (highest → lowest) | Source |
|-----------------------------|--------|
| 1 (highest) | Later `-backend-config` flags |
| 2 | Earlier `-backend-config` flags |
| 3 (lowest) | `backend` block in `.tf` file |

Example — overriding the key from `dev` to `prod`:

`terraform.tf` (specifies `key = "dev/aws_infra"`):

```hcl
terraform {
  backend "s3" {
    bucket = "my-terraform-state-ghm"
    key    = "dev/aws_infra"
    region = "us-east-1"
  }
}
```

`state_configuration/prod-s3-state-key.hcl`:

```hcl
key = "prod/aws_infra"
```

```bash
terraform init \
  -backend-config=state_configuration/s3-state-bucket.hcl \
  -backend-config=state_configuration/prod-s3-state-key.hcl \
  -migrate-state
```

```text
# Line-by-line Comments
# The key "dev/aws_infra" in terraform.tf is overridden by
# "prod/aws_infra" from prod-s3-state-key.hcl (CLI takes priority)
```

#### Code Walkthrough

- The main `terraform.tf` defines `key = "dev/aws_infra"`.
- The CLI-supplied `prod-s3-state-key.hcl` provides `key = "prod/aws_infra"`.
- CLI values override the main configuration — state is stored under the `prod/` prefix.
- This enables a single codebase to deploy to different environments by changing only the init command.

## Comparison: Partial Configuration Approaches

| Approach | Pros | Cons | Best For |
|----------|------|------|----------|
| Full inline (all in `.tf`) | Simple, self-contained | Cannot vary per environment without code changes | Single-environment projects |
| Single partial file | Separates config from code; easy env switching | Extra file to manage | Multi-environment with CI/CD |
| Multiple partial files | Maximum flexibility; shared + env-specific split | Complexity; many files | Large teams with shared infra |
| CLI key/value | No files needed; good for automation | Secrets visible in shell history | Non-sensitive overrides |
| Interactive prompt | No pre-configuration needed | Blocks automation; manual only | Development/debugging |

---

## Pitfalls & Best Practices

- **No interpolation in backend blocks** — Variables, locals, and functions cannot be used. Use partial configuration files instead.
- **Understand `-migrate-state` vs. `-reconfigure`** — Use `-migrate-state` to copy state to the new backend; use `-reconfigure` to start fresh without copying.
- **Do not combine `-migrate-state` and `-reconfigure`** — These are mutually exclusive intents (the lab shows both flags together in Task 7, but current Terraform versions treat them separately).
- **Secure partial config files containing secrets** — Store them in a secrets manager; download at runtime. Do not commit to version control.
- **Avoid CLI key/value for secrets** — Shell history exposes sensitive values.
- **Document your merge order** — When multiple partial configs are used, the override behavior may not be obvious to new team members.
- **One backend per working directory** — Attempting to define multiple backends causes an error.
- **Always validate after backend changes** — Run `terraform validate` before `init` to catch syntax errors early.
- **Clean up local state after remote migration** — Remove `terraform.tfstate` and `.backup` files once state is confirmed in the remote backend.

## Common Exam Traps

| Trap | Correct Understanding |
|------|----------------------|
| "Variables can be used in backend blocks" | **False** — Backend blocks do not support interpolation. Use partial configuration files or CLI flags instead. |
| "Partial configuration is only for remote backends" | **False** — Partial configuration works with any backend type, including `local`. |
| "Multiple `-backend-config` files are not allowed" | **False** — You can specify multiple `-backend-config` flags; values are merged in order. |
| "The `.tf` file always takes priority over CLI flags" | **False** — CLI `-backend-config` values override values in the `.tf` file. |
| "Terraform prompts for all omitted backend values" | **False** — Terraform only prompts for **required** values. Optional values use defaults silently. |
| "`-migrate-state` and `-reconfigure` do the same thing" | **False** — `-migrate-state` copies state to the new backend; `-reconfigure` ignores existing state. |
| "Changing the backend block does not require `terraform init`" | **False** — Any backend change requires re-running `terraform init`. |
| "Partial config files must use `.tf` extension" | **False** — Partial config files typically use `.hcl` extension and contain only key/value assignments (no block syntax). |

## Key Terms & Definitions

| Term | Definition |
|------|-----------|
| **Partial Configuration** | A backend block with incomplete arguments, supplemented at init time via files or CLI flags. |
| **`-backend-config`** | A `terraform init` flag that supplies backend configuration from a file or key/value pair. |
| **`-migrate-state`** | A `terraform init` flag that copies existing state to the newly configured backend. |
| **`-reconfigure`** | A `terraform init` flag that reinitializes the backend without copying state. |
| **Configuration Merge** | The process of combining backend values from `.tf` files and CLI flags, with CLI taking priority. |
| **Backend Block** | The `backend "type" {}` block inside `terraform {}` that configures state storage. |
| **Interpolation** | Use of variables, functions, or expressions within HCL — not supported in backend blocks. |
| **Working Directory** | The directory containing `.tf` files where Terraform commands are executed; limited to one backend. |

| Change | Details |

| **`-migrate-state` and `-reconfigure` are mutually exclusive** | Task 7 shows `terraform init -migrate-state -reconfigure`. | **Provider versions outdated** | The lab pins `hashicorp/aws` to `~> 3.0`. Current major version is 5.x. `http`, `random`, `local`, and `tls` providers also have newer major versions available. Update version constraints for current projects. |

| **`cloud` block recommendation** | For HCP Terraform users, the `cloud {}` block (introduced in Terraform v1.1) is the recommended replacement for `backend "remote"`. Partial configuration concepts apply similarly via environment variables and CLI flags. |
