# Terraform State — Migration

## Overview

As Terraform usage matures, organizations may need to change backend types — onboarding new team members, consolidating after a merger/acquisition, or upgrading from a standard backend to an enhanced backend. Terraform provides the `terraform init -migrate-state` command to transfer state data (including all tracked resources) between backends without destroying infrastructure.

This lab demonstrates a full migration cycle: `local` → `s3` → `remote` → `local`.

---

## Concepts

- **State Migration** — Copying the contents of a state file from one backend to another while preserving all resource mappings and metadata.
- **`-migrate-state` flag** — An option for `terraform init` that detects backend changes and prompts to copy existing state to the new backend.
- **`-reconfigure` flag** — Reinitializes the backend _without_ migrating state (starts with empty state on the new backend).
- **Single Backend Rule** — A Terraform working directory can only have one backend configured at a time.

---

## Terraform Workflow

### Migration Process (All Backend Transitions)

1. Update the `backend` block in `terraform.tf` (or remove it to revert to `local`).
2. Run `terraform validate` to confirm syntax.
3. Run `terraform init -migrate-state`.
4. When prompted, answer `yes` to copy existing state or `no` to start empty.
5. Verify with `terraform state list`.
6. Optionally remove local `terraform.tfstate` / `terraform.tfstate.backup` after migrating to a remote backend.

### Migration Path Demonstrated

```text
local → s3 (standard) → remote (enhanced/HCP Terraform) → local
```

| Step | From          | To       | Key Action                                                       |
| ---- | ------------- | -------- | ---------------------------------------------------------------- |
| 1    | (none/remote) | `local`  | Remove `backend` block, run `init -migrate-state`                |
| 2    | `local`       | `s3`     | Add `backend "s3"` block, run `init -migrate-state`              |
| 3    | `s3`          | `remote` | Replace with `backend "remote"` block, run `init -migrate-state` |
| 4    | `remote`      | `local`  | Remove `backend` block, run `init -migrate-state`                |

## State Management

### Task 1: Local Backend (Default)

Removing the `backend` block entirely reverts Terraform to its default `local` backend, storing state in `terraform.tfstate` within the working directory.

```hcl
terraform {
  required_version = ">= 1.0.0"
  required_providers {
    aws = {
      source  = "hashicorp/aws"
      version = "~> 3.0"
    }
    http = {
      source  = "hashicorp/http"
      version = "2.1.0"
    }
    random = {
      source  = "hashicorp/random"
      version = "3.1.0"
    }
    local = {
      source  = "hashicorp/local"
      version = "2.1.0"
    }
    tls = {
      source  = "hashicorp/tls"
      version = "3.1.0"
    }
  }
}
```

```text
# Line-by-line Comments
terraform {
  required_version = ">= 1.0.0"       # Minimum Terraform CLI version
  required_providers {
    aws = {
      source  = "hashicorp/aws"        # AWS provider from HashiCorp registry
      version = "~> 3.0"              # Any 3.x version
    }
    http = {
      source  = "hashicorp/http"       # HTTP data source provider

    }

      source  = "hashicorp/random"     # Random resource generation provider
      version = "3.1.0"              # Pinned version
    }
    local = {
      source  = "hashicorp/local"      # Local file operations provider
      version = "2.1.0"              # Pinned version
    }
    tls = {
      source  = "hashicorp/tls"        # TLS/SSH key generation provider
      version = "3.1.0"              # Pinned version
    }
  }
}
# No backend block = Terraform uses the default "local" backend
```

#### Code Walkthrough

Without a `backend` block, Terraform defaults to the `local` backend. State is stored in `terraform.tfstate` in the working directory. This is suitable for individual use but lacks collaboration features (locking, versioning, encryption, remote access).

```bash
terraform validate
terraform init -migrate-state
```

```text
# Line-by-line Comments
terraform validate             # Confirms HCL syntax and configuration validity
terraform init -migrate-state  # Reinitializes backend; prompts to copy state from previous backend
```

### Task 2: Migrate to S3 Backend

```hcl
terraform {
  backend "s3" {
    bucket         = "my-terraform-state-ghm"
    key            = "prod/aws_infra"
    region         = "us-east-1"
    dynamodb_table = "terraform-locks"
    encrypt        = true
  }
}
```

```text
# Line-by-line Comments
terraform {
  backend "s3" {
    bucket         = "my-terraform-state-ghm"  # S3 bucket name (must exist)
    key            = "prod/aws_infra"           # Object path within the bucket
    region         = "us-east-1"               # AWS region of the bucket
    dynamodb_table = "terraform-locks"          # DynamoDB table for state locking
    encrypt        = true                      # Enable SSE-S3 encryption at rest
  }
}
```

#### Code Walkthrough

- The `bucket` and `key` must be updated to match your pre-existing S3 bucket and desired state path.
- `dynamodb_table` enables state locking (table must exist with partition key `LockID`).
- `encrypt = true` enables server-side encryption.
- **Dependencies**: S3 bucket and DynamoDB table must already exist.

```bash
terraform validate
terraform init -migrate-state
```

When prompted with "Do you want to copy existing state to the new backend?", answering `yes` copies all resource data from the local state file to the S3 object. After successful migration, local `terraform.tfstate` files can be deleted.

### Task 3: Migrate to Remote (HCP Terraform) Backend

```hcl
terraform {
  backend "remote" {
    hostname     = "app.terraform.io"
    organization = "Enterprise-Cloud"

    workspaces {
      name = "my-aws-app"
    }
  }
}
```

```text
# Line-by-line Comments
terraform {
  backend "remote" {
    hostname     = "app.terraform.io"    # HCP Terraform host (or Terraform Enterprise URL)
    organization = "Enterprise-Cloud"    # Your organization name
    workspaces {
      name = "my-aws-app"               # Target workspace for state and operations
    }
  }
}
```

#### Code Walkthrough

- Migrating from `s3` to `remote` transitions from a standard backend (local execution) to an enhanced backend (remote execution in HCP Terraform).
- `hostname` defaults to `app.terraform.io` for HCP Terraform; use your Terraform Enterprise URL if applicable.
- **Authentication required**: Must have a valid API token (via `terraform login`) before running `init`.
- The workspace is created automatically in HCP Terraform if it does not exist.

```bash
terraform validate
terraform init -migrate-state
```

Terraform detects the backend type changed from `s3` to `remote` and prompts for state copy confirmation.

---

### Task 4: Migrate Back to Local

Remove the `backend` block entirely (same as Task 1), then run:

```bash
terraform validate
terraform init -migrate-state
```

Terraform detects the `remote` backend is being unconfigured and prompts to copy state to the new `local` backend. A `terraform.tfstate` file is created in the working directory containing the migrated state.

## Comparison: `-migrate-state` vs. `-reconfigure`

| Flag             | Behavior                                      | State Data                                   | Use Case                                  |
| ---------------- | --------------------------------------------- | -------------------------------------------- | ----------------------------------------- |
| `-migrate-state` | Detects backend change, prompts to copy state | Preserved (copied to new backend)            | Changing backends while keeping resources |
| `-reconfigure`   | Reinitializes with new backend config         | **Not copied** (starts empty on new backend) | Fresh start or state managed elsewhere    |

---

## Pitfalls & Best Practices

- **Always use `-migrate-state` when resources exist** — Using `-reconfigure` with active state causes Terraform to lose track of resources (orphaned infrastructure).
- **Validate before migrating** — Run `terraform validate` to catch syntax errors before attempting migration.
- **Only one backend per working directory** — Replace the existing backend block; do not add a second one.
- **Authentication must be in place** — For the `remote` backend, ensure `terraform login` has been completed before `init`.
- **Clean up local state after remote migration** — Remove `terraform.tfstate` and `terraform.tfstate.backup` once state is confirmed in the remote backend.
- **Pre-existing infrastructure required** — The S3 bucket, DynamoDB table, and HCP Terraform organization/workspace must exist before migration.
- **State migration does not modify infrastructure** — Migration only moves the state file; no resources are created, changed, or destroyed.
- **Answering "no" to migration prompt starts with empty state** — This effectively orphans all existing resources from Terraform's perspective.

## Common Exam Traps

| Trap                                                                    | Correct Understanding                                                                                                                                               |
| ----------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| "`terraform init` alone migrates state"                                 | **False** — You must use `terraform init -migrate-state` to trigger the migration prompt. Plain `init` after a backend change will error or prompt for reconfigure. |
| "State migration destroys and recreates resources"                      | **False** — Migration only transfers the state file; infrastructure remains untouched.                                                                              |
| "`-reconfigure` preserves state data"                                   | **False** — `-reconfigure` does not copy state. Use `-migrate-state` to preserve resource tracking.                                                                 |
| "You can have multiple backends configured"                             | **False** — Only one `backend` block is permitted per working directory.                                                                                            |
| "Removing the backend block deletes remote state"                       | **False** — Removing the block reverts to `local`; remote state remains on the previous backend (S3, HCP Terraform, etc.) but is no longer used.                    |
| "Migration between any two backends requires `terraform destroy` first" | **False** — `terraform init -migrate-state` handles the transition without destroying resources.                                                                    |
| "The local backend requires explicit configuration"                     | **False** — `local` is the default; simply omitting the `backend` block activates it.                                                                               |
| "State can be migrated without authentication to the target backend"    | **False** — Valid credentials are required for both the source (to read) and destination (to write) backends.                                                       |

## Key Terms & Definitions

| Term                   | Definition                                                                                                    |
| ---------------------- | ------------------------------------------------------------------------------------------------------------- |
| **State Migration**    | The process of moving Terraform state data from one backend to another using `terraform init -migrate-state`. |
| **`-migrate-state`**   | An `init` flag that copies existing state to a newly configured backend.                                      |
| **`-reconfigure`**     | An `init` flag that reinitializes the backend without copying state.                                          |
| **Local Backend**      | Terraform's default backend; stores state in `terraform.tfstate` in the working directory.                    |
| **Standard Backend**   | Stores state remotely; operations execute locally (e.g., S3, GCS, Azure Storage).                             |
| **Enhanced Backend**   | Stores state remotely _and_ executes operations remotely (e.g., `remote` / HCP Terraform).                    |
| **Working Directory**  | The directory containing `.tf` files where Terraform commands are executed.                                   |
| **Orphaned Resources** | Cloud resources that exist but are no longer tracked in any Terraform state file.                             |

## Updated Information (as of 2025-07-14)

| Change                                        | Details                                                                                                                                                                                                                                            |
| --------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **`cloud` block replaces `backend "remote"`** | The `backend "remote"` block is deprecated. The recommended approach is the `cloud {}` block within `terraform {}`. Functionality is equivalent; `cloud` is the forward-compatible syntax. Migration commands work identically with either syntax. |
| **S3 locking via DynamoDB deprecated**        | The `dynamodb_table` attribute for state locking is deprecated (Terraform v1.10+). Use `use_lockfile = true` for native S3 conditional-write locking without DynamoDB.                                                                             |
| **Provider versions outdated**                | The lab pins `hashicorp/aws` to `~> 3.0`. Current major version is 5.x. Similarly, `http`, `random`, `local`, and `tls` providers have newer major versions. Update version constraints when using current Terraform.                              |
| **S3 bucket encryption default**              | Since January 2023, AWS applies SSE-S3 encryption by default on all new buckets. `encrypt = true` in the backend block remains valid but is now redundant for new buckets.                                                                         |
