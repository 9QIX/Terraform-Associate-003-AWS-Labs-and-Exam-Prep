# Terraform State - Default Local Backend

## Overview

Terraform stores the state of managed infrastructure to plan and execute changes correctly. The **backend** determines where and how state is stored. By default, Terraform uses the **local backend**, storing state in a JSON file named `terraform.tfstate` within the working directory. This state file must remain synchronized before any Terraform operation to prevent incorrect actions or unexpected results.

---

## Concepts

### What is Terraform State?

- A JSON file tracking all resources managed by Terraform
- Records resource metadata, dependencies, and current configuration
- Must be up-to-date before each Terraform execution
- Enables Terraform to determine what changes are needed

### Local Backend Characteristics

- **Default behavior**: No configuration required
- **Storage location**: Working directory (`terraform.tfstate`)
- **Format**: JSON
- **Backup**: Automatically creates `terraform.tfstate.backup` after changes
- **Scope**: Single-user, local filesystem operations

### State File Structure

```
project/
├── main.tf
├── terraform.tf
├── variables.tf
├── terraform.tfstate          # Current state
├── terraform.tfstate.backup   # Previous state
└── terraform.tfstate.d/       # Workspace states (if using workspaces)
    └── development/
        ├── terraform.tfstate
        └── terraform.tfstate.backup
```

## State Management

### Task 2: State File Location

The local backend stores state in the working directory:

| File                       | Purpose                                 |
| -------------------------- | --------------------------------------- |
| `terraform.tfstate`        | Current state of all managed resources  |
| `terraform.tfstate.backup` | Previous state before last modification |

**State File Format:**

- JSON structure containing resource metadata
- **Never modify manually**—use Terraform CLI commands only
- Out-of-sync state causes incorrect operations

---

### Task 3: Backend Configuration

#### Default Behavior (No Configuration)

```hcl
terraform {
  required_version = ">= 1.0.0"
  required_providers {
    aws = {
      source  = "hashicorp/aws"
      version = "~> 3.0"
    }
  }
}
```

**Line-by-line Comments:**

```hcl
# Terraform configuration block
# No backend specified—defaults to local backend
# State stored in terraform.tfstate automatically
```

**Code Walkthrough:**

- Absence of `backend` block triggers default local backend
- Terraform automatically creates `terraform.tfstate` in working directory
- No additional configuration required for single-user workflows

---

#### Explicit Local Backend Configuration (Optional)

```hcl
terraform {
  backend "local" {
    path = "terraform.tfstate"
  }
}
```

**Line-by-line Comments:**

```hcl
# Explicitly declares local backend
# Specifies state file path (default: terraform.tfstate)
# Optional—Terraform uses this by default
```

**Code Walkthrough:**

- Makes backend configuration explicit for documentation purposes
- Does not change default behavior
- Useful for clarity in team environments
- **Requires `terraform init`** after adding backend configuration

**Re-initialization:**

```bash
terraform init
```

**Line-by-line Comments:**

```bash
# Re-initializes working directory after backend changes
# Configures the local backend explicitly
```

### Task 4: Modify Configuration and Update State

#### Add New Resource

```hcl
# Terraform Resource Block - To Build EC2 instance in Public Subnet
resource "aws_instance" "web_server_2" {
  ami           = data.aws_ami.ubuntu.id
  instance_type = "t3.micro"
  subnet_id     = aws_subnet.public_subnets["public_subnet_2"].id
  tags = {
    Name = "Web EC2 Server"
  }
}
```

**Line-by-line Comments:**

```hcl
# Defines second EC2 instance resource
# Uses Ubuntu AMI from data source
# Deploys to public_subnet_2
# Tags instance for identification
```

**Code Walkthrough:**

- Adds new resource to existing configuration
- References existing data sources and resources
- Terraform detects this as a new resource (not in state)
- Plan will show `1 to add, 0 to change, 0 to destroy`

## Pitfalls & Best Practices

### Common Mistakes

| Mistake                     | Consequence                            | Solution                                   |
| --------------------------- | -------------------------------------- | ------------------------------------------ |
| Manually editing state file | State corruption, incorrect operations | Use `terraform state` commands only        |
| Out-of-sync state           | Wrong resources modified/destroyed     | Always pull latest state before operations |
| Deleting state file         | Terraform loses track of resources     | Maintain backups; use remote backends      |
| Concurrent modifications    | State conflicts, race conditions       | Use remote backends with locking           |
| Ignoring state backups      | No recovery from bad state changes     | Preserve `.backup` files; version control  |

---

### Best Practices

- **Never modify `terraform.tfstate` manually**—use CLI commands
- **Re-run `terraform init`** after changing backend configuration
- **Use `terraform state list`** for quick resource summaries
- **Use `terraform state show`** for detailed resource inspection
- **Preserve state backups** for rollback scenarios
- **Transition to remote backends** for team collaboration
- **Use `.gitignore`** to exclude state files from version control:
  ```
  terraform.tfstate
  terraform.tfstate.backup
  ```

## Key Terms & Definitions

| Term                   | Definition                                                                         |
| ---------------------- | ---------------------------------------------------------------------------------- |
| **Backend**            | Configuration determining where and how Terraform state is stored                  |
| **Local Backend**      | Default backend storing state in `terraform.tfstate` within the working directory  |
| **State File**         | JSON file tracking all resources managed by Terraform                              |
| **State Backup**       | Automatic copy of previous state (`terraform.tfstate.backup`)                      |
| **Stateful Execution** | Terraform's ability to track existing resources and apply only incremental changes |
| **State Drift**        | Discrepancy between state file and actual infrastructure                           |

## Common Exam Traps

- **Trap:** Believing local backend is suitable for team collaboration  
  **Reality:** Local backend lacks locking and remote access—use remote backends for teams

- **Trap:** Assuming state files should be committed to version control  
  **Reality:** State files contain sensitive data and should be excluded via `.gitignore`

- **Trap:** Thinking `terraform init` is only needed once  
  **Reality:** Re-initialization required after backend configuration changes

- **Trap:** Confusing `terraform show` with `terraform state show`  
  **Reality:** `terraform show` displays all resources; `terraform state show` targets one resource

- **Trap:** Believing state backups are optional  
  **Reality:** Backups are automatically created and critical for recovery

- **Trap:** Assuming deleted state files have no impact  
  **Reality:** Terraform loses track of resources, requiring manual cleanup or import
